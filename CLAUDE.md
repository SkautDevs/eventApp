# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Modular support web app for Czech scout events (Obrok). Built on Slim 4 (PHP >= 8.3). One codebase serves multiple events — each event is a config + content directory under `events/<slug>/` plus public assets under `www/events/<slug>/`, selected at runtime by the first path segment: every event lives under `/{slug}/`, and `/` is a picker of the listed ones. Code is in English — comments, docblocks, exception messages, identifiers. Czech is reserved for what users actually read: UI strings in `templates/`, per-event content under `events/<slug>/content/`, user-facing notices and flash messages, and the weekday names in `Kernel`. Every surface a reader sees addresses them as *ty*: templates, notices and flash messages, push status lines, ARIA labels, `<title>`s. The admin page is for organisers and stays neutral and imperative, and per-event content is the organisers' own text. Commit messages and `docs/` are in English without AI-authorship trailers (the existing `docs/kissj-contract.md` predates this and is still Czech).

## Commands

- `docker-compose up` — run the dev server (PHP built-in server inside `php:8.3-alpine`, with `bin/router.php`), then visit `localhost:8080`
- `composer start` — alternative: run locally via `php -S localhost:8080 -t www/ bin/router.php`. The router is not optional: without it the built-in server 404s any missing path with a dot in it (`/<slug>/precache.json`) before PHP runs
- `composer test` / `vendor/bin/phpunit` — run tests (PHPUnit 11, config in `phpunit.xml`, suites `unit`, `functional`, `browser`). Without a Chrome every `browser`-group test skips itself ("OK, but some tests were skipped!"); CI sets `PANTHER_NO_SKIP=1`, where that is a failure
- `vendor/bin/phpunit --exclude-group browser` — the fast run, no Chrome tests. There is no host PHP: run it as `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine vendor/bin/phpunit --exclude-group browser` and again with `php:8.5-alpine` — 8.3 is the lowest supported PHP and 8.5 is what CI and production run (`.github/php-version`, read by every workflow; `deploy.yml` deploys every push to `master` over FTP once `ci.yml` passes, see `docs/deployment.md`)
- `docker compose --profile browser run --rm --use-aliases test vendor/bin/phpunit --group browser` — the Chrome tests: `symfony/panther` drives `selenium/standalone-chrome` (the `chrome` service), and the test case serves the app itself from the `test` container (`--use-aliases` makes it reachable as `test`). `docker compose --profile browser stop chrome` afterwards, and `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine sh -c 'rm -rf var/twig/* var/sessions var/cache'`, because the `test` service runs as root. There is no Node anywhere

The workbook has no date, so every talk sits on the invented `MiquikRozvrh::DATE`

Before running, copy `.env.example` to `.env`, set `APP_DEBUG=1` for dev and fill in a VAPID pair — `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/generate-vapid.php` prints the two lines; every event has push, and a push event refuses to boot without valid keys (tests generate their own per run in `tests/bootstrap.php`). There is no event to choose, the URL does (`localhost:8080/obrok19/`, the reference event).

Five events ship: `obrok19` (the reference), `obrok27`, `korbo26` (the former `korbo`), `navigamus25` and `miquik26` (unlisted: its lecture data is in, its date is invented). Two of them are **unlisted**, i.e. absent from the picker but reachable by URL: `miquik26` and `obrok19`, neither of which has a `listed` key at all, so both default to unlisted (obrok19 is served at `/obrok19/`). **korbo26, navigamus25 and miquik26 wear kissj's design**, adjusted to eventApp's contrast rules. A slug matches `/^[a-z0-9-]+$/` and ends in a two-digit year; the fixture TIE code is the slug without its digits, upper-cased, plus `1` (`KORBO1`, unchanged by the rename). That rule covers the pipeline events; obrok19 has no source in the pipeline and its fixture TIE code `ABC123` predates the rule. An event's `config.php` may also carry `listed` and `dates` (`start`/`end`), which the picker uses to split upcoming from past; the three listed events carry both, while `miquik26` and `obrok19` carry neither.

## Architecture

`www/index.php` is a 3-line front controller: it requires the Composer autoloader and calls `App\Kernel::boot($_SERVER['REQUEST_URI'] ?? '/')->run()`, which picks the event from the first path segment (see `Kernel::boot()` below). All bootstrap logic lives in `src/Kernel.php` — no `settings.php`/`dependencies.php`/`middleware.php`/`routes.php` split, no route closures scattered across a routes file.

`Kernel::boot($_SERVER['REQUEST_URI'])` loads `.env` (if present) and looks at the first path segment: if `EventCatalog` knows it, `Kernel::create()` builds the app for that event; otherwise `Kernel::createInstance()` builds the instance-level app that serves the picker at `/` and Slim's 404 for the rest. Nothing is configured per deployment about which event is served. Env vars are per event where they are secrets or choices of an event — `<NAME>_<SLUG>` with the slug upper-cased and `-` turned into `_` (`PROGRAM_PROVIDER_OBROK27`, `KISSJ_API_KEY_OBROK27`, `ADMIN_TOKEN_OBROK27`), read through `EventConfig::env()` (which falls back from `$_ENV` to `getenv`, because php-fpm may leave `$_ENV` empty); `APP_DEBUG`, `KISSJ_BASE_URL`, `PROGRAM_CACHE_TTL`, `VAPID_*`, `PUSH_DB_PATH`, `SESSION_PATH` (`Kernel::sessionPath()`, default `var/sessions`, relative paths against the project root like `PUSH_DB_PATH`; the browser tests point it at a temp dir), `PUSH_ENDPOINT_HOSTS`, `TRUSTED_PROXY_COUNT`, `TRUSTED_PROXIES`, `SENTRY_DSN`, `SENTRY_TRACES_SAMPLE_RATE` (`.env.example`: 0.05), `SENTRY_PROFILES_SAMPLE_RATE` and `APP_RELEASE` are instance-wide and read from `$_ENV` (`TRUSTED_PROXIES` falls back to `getenv`). The reader's address is `Http\ClientIp::of()`: `X-Forwarded-For` is read, `TRUSTED_PROXY_COUNT` hops from its right end, only when the connection comes from a loopback or private address (an IPv4-mapped one judged as its IPv4) or from one `TRUSTED_PROXIES` names (comma-separated addresses or CIDRs, a malformed entry skipped; only the immediate peer is matched, the inner hops are trusted by the count); otherwise it is `REMOTE_ADDR`. Both limits — the TIE login's and the push subscribe one — count by `ClientIp::throttleKey()`, which is that address for IPv4 and its /64 for IPv6, with `::ffff:` unwrapped. A 404 or 405 is not logged (`src/QuietErrorHandler.php`), and `Kernel::TIMEZONE` is `Europe/Prague`.

Observability is Sentry, wired like kissj's. `Telemetry\Telemetry::init()` runs in `boot()` only, right after `.env` — tests build apps through `Kernel::create()`, so no test ever binds a client, and `phpunit.xml` forces `SENTRY_DSN` empty for the few that call `boot()`. With an empty `SENTRY_DSN` every piece below is a no-op. `Telemetry\Collector::collect()` files an exception (`QuietErrorHandler` calls it for everything but a 404/405), `Telemetry\Tracer::span($op, $description, $fn, $data)` wraps a child span (`kissj.list`, `kissj.participant`, `kissj.programme-participants`, `program.cache`, `push.send`, `push.welcome`, `push.subscribe`, `push.unsubscribe`, `auth.tie`) whose failure status comes from the HTTP answer when there is one (`Tracer::statusFor()`: kissj's 404 is `not_found`, not `internal_error`, and so is the `UnknownParticipantException` made from it) and whose `$data` becomes span data — a `Tracer::FROM_RESULT` closure adds data computed from the result; `Tracer::spanTag()` instead tags the running span. The push counters `push.outcome` (on `push.welcome`), `push.target` (on `push.send`), `push.new` (on `push.subscribe`) and `push.found` (on `push.unsubscribe`) are such tags, while the cache outcome `cache.result` (`hit`, `miss`, `stale`, `locked` for an expired entry served while another request refetches it, or `bypass` for the uncached programme-participants call) with `cache.age`, and the send counts `push.recipients`, `push.sent`, `push.removed` and `push.failed` (refused other than 404/410, or thrown), are span data — none of them is an issue. `TransactionMiddleware` opens one transaction per request and `RouteNameMiddleware` names it by route pattern (`POST /admin/notify/{id:[0-9]+}/hidden`) and tags the event; a request no route matched (a 404 or 405) keeps the fixed name `unmatched` (`TransactionMiddleware::UNMATCHED`), and the instance app names its routes too (`RouteNameMiddleware(null)`, which tags no event). `Telemetry\Scrubber` strips the `token` query parameter, `tieCode`/`token` body fields, a whole `/push/subscribe` or `/push/unsubscribe` body, a whole `/admin/notify` form body and the `Authorization`/`Cookie` headers before anything leaves; exception messages are left alone, so none may carry a secret (`UnknownParticipantException` says just `Unknown TIE code` and chains nothing, and any other failed participant call is rethrown as `Program\KissjTransferException` — a `TransferException` that names the endpoint, never the URI, and chains nothing either). There are two Monolog loggers: `Psr\Log\LoggerInterface` (`eventapp`: stdout from info up, a Sentry issue from warning up through `LogToSentryIssueHandler`) and `Kernel::ERRORS_LOGGER` (`errors`: stdout only, for the error handler, so an exception is not filed twice); the app log lines are `push.sent` (info) and, from `WebPushSender`, one `push.failed` warning per batch with failures — counts only, filed in Sentry as an issue; a throwable the sender swallows goes to `Collector::collect()`. `GET /health` on the instance app opens the push database, runs `SELECT 1` and answers `200 {"ok":true}` or `503 {"ok":false}` — no migration, no log, no Sentry. The SDK's default integrations stay on, as in kissj (`Telemetry::options()`), so PHP warnings and deprecations reach Sentry as events too. The one routine message, web-push's "GMP or BCMath" advice, is no longer a PHP notice: `WebPushSender::webPush()` hands the library (`minishlink/web-push` ~10.1.0, which also cleared its PHP 8.5 deprecation and requires `ext-mbstring`) the app logger wrapped in `Push\PlatformAdviceFilter`, which drops that one line and passes every real platform warning through.

`Kernel::create()`:
- Builds a PHP-DI container (`ContainerBuilder`) with the event, the program provider, `Session`, `Auth\Authenticator` and Twig as definitions.
- Creates the Slim 4 `App`, adds body-parsing/routing middleware, Twig middleware, and error middleware (`APP_DEBUG` controls whether error details are shown), and then the session-cookie and screen middleware, *outside* the error middleware rather than inside it; the security headers, `Http\CspMiddleware` and `Telemetry\TransactionMiddleware` now wrap it in turn (the next bullet has the full order). A thrown 404 or 500 is answered by the error middleware without ever reaching the route, so a `Vary: X-Screen` set further in would be missing from exactly the responses a shared cache is most likely to keep.
- The middleware stack, innermost to outermost: body parsing, routing (with `Telemetry\RouteNameMiddleware` added before it, i.e. inside it, so the route is known), Twig, error, session cookie (`addSessionCookieMiddleware()`: a `GET` answered 200 with a full HTML page, not a fragment, for a logged-in reader calls `Session::refreshCookie()`), screen (which also sets `Cache-Control: Kernel::PAGE_CACHE_CONTROL`, `no-store, no-cache, must-revalidate`, on every HTML page and fragment that states no policy of its own, cookie or not), security headers (each set only if the response has none, which is how the admin routes keep `Referrer-Policy: no-referrer`), `Http\CspMiddleware`, and `Telemetry\TransactionMiddleware` last — outermost, so the error middleware's 500 is measured. `createInstance()` has the same order without the Twig, session-cookie and screen layers (its route naming is `RouteNameMiddleware(null)`).
- Registers core routes (`GET /<slug>/` homepage, the TIE-code login/logout on `/profil`, the offline page `/offline` and the worker's `/precache.json`) directly, then iterates `$event->features` and registers one module per enabled feature.

`EventConfig` (`src/EventConfig.php`) loads and validates `events/<slug>/config.php` (requires `name`, `colors`, `features`; also carries arbitrary `raw` data via `get()`, and `dir` for locating fixtures/content). `EventConfig::content(string $name)` loads `events/<slug>/content/<name>.php`, a plain PHP file returning an array (e.g. `content/links.php`), which the Odkazy screen renders as a `<ul class="link-list">` of `.link-card`s (the handbook first and tonal, a `highlight` entry tonal too, an optional `note` as a second line, an outward mark on absolute URLs) while the home screen still shows only the `highlight` ones as `.highlight` CTAs — these are per-event, not code. `content/emergency.php` (`contacts`: `label`, `phone`, optional `note`; `info`: lines) is the optional "V nouzi" box the homepage route passes to `homepage.twig` as `emergency`, rendered under the logo with each number a `tel:` link (spaces stripped) so it dials from the worker's offline copy; an event without the file shows no box, and obrok27 ships the mock `000 000 000` until the organisers give the real line. News has no content file: it is the list of sent notifications (below).

Modules implement `App\Module\ModuleInterface` (`key()`, `menuItem()`, `registerRoutes()`) and live in `src/Module/`. `ModuleRegistry::classFor($feature)` maps a feature-flag string (from the event's `features` array in its config) to a module class — this is how features are toggled per event, e.g. `NewsModule`, `LinksModule`, `MapModule`, `HandbookModule`, `ProgramsModule`. `PushModule` (web push notifications) is implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and `GET/POST /admin/notify` sends notifications — the shared link `?token=<ADMIN_TOKEN_<SLUG>>` logs the browser in for 24 hours (session key `admin` = `['since' => int]`) and redirects to the bare URL; the pages after it carry no token and the forms carry a CSRF field (`csrf`), and every admin response is `Cache-Control: no-store` and `Referrer-Policy: no-referrer` — the error page of an exception thrown under the admin routes included, which their middleware renders itself through the container's `ErrorMiddleware` so it is reported once; the send form also carries a one-time `nonce`, issued each time the form renders (up to fifty stay valid in the session, for several open tabs) and consumed under the session lock in `Session::transact()` only right before the send, after validation and the TIE-code fetch, so a double tap or a re-send after a 504 sends nothing and answers 409 with the typed text and a neutral notice ("Tento formulář už byl jednou odeslán, nebo je zastaralý…"); its submit button is disabled on submit and re-enabled on `pageshow`; a refused POST (expired day or stale CSRF) answers 403 with a Czech "link expired" page (`templates/admin-expired.twig`) that echoes the typed title and text, and re-opening the link keeps a well-formed `csrf` so a form open in another tab stays valid — through `App\Push\PushSenderInterface`/`WebPushSender`, either to everyone or to one programme — whose participants `ProgramProviderInterface::getTieCodesForProgramme()` names. Every send needs a Podpis (log only, never in the notification) and is written to the `messages` log (`App\Push\MessageRepository`, same database) **before** it is sent — `begin()` stores it with NULL counts and `finish()` fills `sent`, `removed`, `failed` and `unreached` when the send returns, so a send that dies half-way still leaves the message on News, with `–` for the counts in the admin log; the result line adds `nedoručeno: N` when anything failed. The log is kept forever: the admin page lists it and can hide a message from readers or show it again, recording who and when, but nothing is ever deleted. Subscriptions carry an `event` column and a send reaches only that event's subscribers; each also carries the TIE code of the session that saved it, which `www/push.js` keeps in step by re-sending the subscription after a login or logout, so a programme send reaches exactly the subscribed browsers of its registered participants. Storage is one `PDO` per request from `Storage\Database::open()` (WAL, `busy_timeout` 5000, foreign keys), the container's `\PDO::class`, migrated on first use by `Storage\Migrator` — numbered steps tracked in `PRAGMA user_version`, one `BEGIN IMMEDIATE` transaction each, `Migrator::VERSION` the highest (5: the schema, `tie_attempts`, `subscriptions.failures`, `subscribe_attempts`, and `messages` rebuilt with nullable counts and a `failed` column, ids and the AUTOINCREMENT high-water mark kept); append a step, never edit a shipped one. Both repositories, `Auth\LoginThrottle` and `Push\SubscribeThrottle` take that `PDO` and run no DDL. Subscriptions are keyed `(event, endpoint)`, so the same browser may subscribe to two events and `delete($event, $endpoint)` touches only its own; `POST /push/subscribe` accepts only endpoints on the known push services (`Push\EndpointPolicy`, extended by `PUSH_ENDPOINT_HOSTS`), because the welcome is a POST to that URL; only keys `Push\SubscriptionKeys::valid()` accepts — a 16-byte auth secret and a `p256dh` that OpenSSL parses as a point on P-256, since a 65-byte `0x04…` value off the curve passes every shape check and then throws inside the library's batch encryption — or it answers 400 `{"saved":false,"error":"invalid-key"}`; and at most `SubscribeThrottle::LIMIT` (300, room for a camp behind one NAT) **new** subscriptions per `(event, throttleKey)` in 10 minutes, then 429 `{"saved":false,"error":"too-many"}` — a known one never counts, a new one counts once saved even if its welcome is then rejected. `PushSenderInterface::sendToSubscription()` returns `Push\SendOutcome` — `Delivered`, `Rejected` (the push service answered 404 or 410, or the row can never be delivered: refused by the allow-list, malformed keys, or no longer stored) or `Failed` (a timeout, any other status, an exception) — and `POST /push/subscribe` answers a new subscription accordingly: 201 `{"saved":true,"welcome":true}`; 201 `{"saved":true,"welcome":false}` with the row kept, because a failure proves nothing about it; or, for `Rejected`, the row deleted and 502 `{"saved":false,"welcome":false,"error":"subscription-rejected"}`. A known subscription (the re-send after a login or logout) is 201 `{"saved":true,"welcome":null}` and sends nothing. `POST /push/unsubscribe` `{endpoint}` deletes `(event, endpoint)` and answers 204 whether or not the endpoint existed (400 without a string `endpoint`; an empty string is a string, so it is a 204 that deletes nothing), so the unauthenticated route tells nobody which endpoints exist. `WebPushSender` gives every push request a 5 s timeout (`TIMEOUT_SECONDS`; the library's 30 s could outlast nginx's 45 s on an admin batch), deletes at send time any row whose endpoint the allow-list refuses (rows from before it existed) or whose keys fail `SubscriptionKeys::valid()`, sends through `Push\IsolatingWebPush` — the library with `prepare()` per notification, so a row whose encryption still throws is set aside and deleted instead of taking the whole batch down (only when *every* row is set aside is it the platform's fault: all count as failed, none is deleted, the first error is reported) — and keeps strikes: a `Failed` send adds one to the row's `failures` — but only when the row's push-service host delivered at least one other notification of the same batch (`WebPushSender::strikable()`), so a send where nothing arrived, or one service's outage, strikes nobody — `MAX_FAILURES` (5) in a row delete it (counted as failed, not removed), and a delivery resets it, as do new keys on a re-subscribe (`save()` upserts and keeps the count when the keys are the same). `sendToEvent()` returns `{recipients, sent, removed, failed}`. It validates `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` in its constructor, and gets its repository as a closure resolved on the first send. `Kernel::create()` builds the sender at boot for every push event, so a misconfigured instance fails on the first request, not on the first tap — and since every event has push, `.env` needs a VAPID pair even in development; `AppTestCase` gives every app a `SpyPushSender`, and `tests/bootstrap.php` generates a throwaway pair per run for the tests that boot the real one. `www/push.js` is one toggle: subscribed, the button reads `Vypnout notifikace` (class `btn`, `btn-primary` dropped), and a tap unsubscribes in the browser first and then posts to `/push/unsubscribe`, ignoring that POST's failure; turning it on registers the worker, shows `Připravuji…` and waits up to 10 s (`READY_TIMEOUT`) for `serviceWorker.ready`, because the browser subscribes only through an active worker and on a first visit it may still be installing; a 429 from the subscribe says `Teď si notifikace zapíná moc lidí najednou, zkus to za chvíli.` and keeps the browser's subscription (the next page re-sends it), a 400 `invalid-key` says `Prohlížeč poslal neplatné údaje, zkus notifikace zapnout znovu.` and drops it like any other failure; without `serviceWorker`/`PushManager` the button is hidden, and on iOS (Safari outside a home-screen app has no `PushManager`) the status line points to "Přidat na plochu". Nothing in it calls `alert()`. `www/sw.js` stays at the docroot root and is registered at scope `/<slug>/` (the `event-base` meta tag) by `www/shell.js` on every page — and again by `push.js`, harmlessly, since `register()` is idempotent — so two events in one browser keep separate workers. After showing a notification it posts `{type: 'news-updated', programme}` to the event's open windows; `programme` (an id or null) travels in the payload from `PushSenderInterface::sendToEvent(…, programme:)` (`WebPushSender::payload()`).

`NewsModule` (`/novinky`) is that log as readers see it: every visible message, newest first. A message for everyone is there for every reader; a programme message appears on News only to a logged-in participant whose `getProgramsForIdentity()` includes that programme (a failing call just leaves those out — News never logs anybody out), and in that programme's sheet on `/programy` for everyone. Because of that `news` requires `push`: `EventConfig::load()` refuses an event that enables one without the other, and every shipped event carries both.

Program/schedule data goes through `App\Program\ProgramProviderInterface` (`getPrograms()`, `getSections()`, `getProgramsForIdentity()`, `getTieCodesForProgramme()`). `StubProgramProvider` reads `events/<slug>/fixtures/programs.json`, `fixtures/sections.json` and `fixtures/registered.json` — no network calls, safe for dev and tests. `KissjProgramProvider` (Guzzle-based) talks to the real kissj registration API. `Kernel` switches between them via `PROGRAM_PROVIDER_<SLUG>=stub|kissj` in `.env` (default `stub`); `kissj` additionally requires `KISSJ_BASE_URL` (the kissj root) and `KISSJ_API_KEY_<SLUG>` (`Kernel` throws a `RuntimeException` if either is empty); the key is sent as `Authorization: Bearer` on every request and is what tells kissj which event is asking, so no event slug is configured anywhere. `docs/kissj-contract.md` is the agreed contract, but kissj does not serve those endpoints yet — do not flip a production event to `kissj` until it does. The provider also supplies the programme **sections** through `getSections()` — id, title, display order and the optional `subTitle`, map `image` and `attachment` — from the `sections` of kissj's list response, or from the stub's `fixtures/sections.json`, which is that same list in kissj's shape (`App\Program\Sections` maps both). The event config carries no `sections` key any more. `Kernel` wraps the kissj provider — never the stub, whose fixture files already are a local copy — in `Program\CachingProgramProvider`, backed by `Cache\FileCache` under `var/cache/<slug>/`: one JSON file per entry, `{"fetchedAt": "<DATE_ATOM>", "data": …}`, written to a temp file and renamed over the old one; the entries are `list` (`{sections, programmes}` from one list response) and `tie-<first 32 hex of sha256(code)>` (one participant's programmes — the code is a secret and is in no filename). An entry younger than `PROGRAM_CACHE_TTL` seconds (instance-wide, `Kernel::programCacheTtl()`, whole seconds, default 300 for anything else; `0` always refetches) is served without asking kissj; an older or missing one is fetched and rewritten; an expired one is served **however old** when kissj throws `TransferException` or `ProgramDataException` (stale-if-error), and the failure goes to `Collector::collect()` instead of the reader. Only a missing entry lets kissj's trouble reach the modules' notices. `UnknownParticipantException` — which `KissjProgramProvider` makes only from a 404 with an **empty body**, the contract's "unknown code"; any other 404 (a maintenance page, a wrong base path) is a `KissjTransferException` like any outage, or a NAT's worth of readers would be logged out — is an answer, not an outage: the entry is deleted and the exception rethrown — but only once it is asked, so a fresh `tie-…` entry keeps a participant kissj has since deleted marked for up to the TTL (the spec accepts this; kissj's 404 clears the entry only when the expired entry is refetched). `getTieCodesForProgramme()` is never cached. The decorator memoises every resolved read per request (keyed by `Freshness::generation()`) and remembers the inner provider's first failure for the same request, after which an expired entry is served stale and a missing one rethrows that failure without asking kissj again — so an outage costs one timeout per request however many entries a page reads. Across requests three more rules keep kissj from being asked by every request at once, all kept as files beside the entries: **single-flight** — `FileCache::tryLock()` takes a non-blocking `flock` on `<key>.lock`, and while another request holds it a request with an expired entry serves it as `locked` (not marked stale, unless `kissj-down` exists) and one with no entry waits up to 12 s (`$lockWait`; kissj's own timeout is 10 s) via `waitLock()`, then serves the holder's fresh entry, rethrows if the holder failed meanwhile, or fetches itself — a filesystem that cannot lock at all yields a no-op lock rather than "held", and the empty lock files accumulate, one per entry; a **60 s breaker** (`BREAKER_SECONDS`) — a failure writes the `kissj-down` entry and for a minute after it an expired entry is served stale without asking, while a missing one still asks, and a success deletes the marker (one participant's bad answer opens it for the whole event); and **one report per 5 minutes** (`REPORT_SECONDS`, the `kissj-reported` entry, which a success leaves alone, so a flapping kissj is not reported on every flap). An unwritable `var/cache/` makes all three quietly do nothing. An entry of the wrong shape (or a file that is not JSON or has no `fetchedAt`) counts as missing, and a failed write is reported, not thrown. Every read updates the request-scoped `Program\Freshness` (the oldest fetch time served, and whether anything was stale), which the screen middleware resets per request.

Login lives under `src/Auth/`: `Authenticator` (session-backed login state), `Identity` (value object for a logged-in TIE-code participant), `UnknownParticipantException`. **The TIE code is the only login** — there is no external SSO to register an app with. Each event resolves a code against its own provider, so a code typed into another event is rejected as `Neplatný TIE kód.`. Unknown codes are counted per `(event, ip)` by `Auth\LoginThrottle`; at 60 in 10 minutes the form answers `Příliš mnoho pokusů, zkus to za chvíli.` without asking the provider. Nothing else counts — not a success, an empty code or a provider outage — and the address is `Http\ClientIp::throttleKey()` (above). A `ProgramDataException` on login is an outage like a `TransferException`. `POST /profil/tie` and `/profil/tie-logout` first ask `Http\SameOrigin::allows()`: `Sec-Fetch-Site` decides when present (`same-origin` or `none`), only without it is `Origin` compared — by host alone, because behind a TLS-terminating proxy PHP sees neither the browser's scheme nor its port, which is why a reverse proxy must pass the original `Host` — and a request carrying neither header is allowed, since no browser form sends neither; a refusal is a 403 rendered from `error.twig` with its own Czech line ("Přihlášení se nepodařilo. Načti stránku a zkus to znovu.", or "Odhlášení…" for the logout, which leaves the reader logged in) and a link back to `/profil`, so a cross-site form can neither log a reader in as the attacker — whose code `push.js` would then bind to the reader's subscription — nor out.

Sessions are `App\Session`, built per event as `new Session($slug, Kernel::sessionPath($root), appRoot: $root)`, and nothing about them depends on the host's ini (the FTP host's handler and defaults are unknown): before every start it sets the files handler and its path **as a pair** — `var/sessions` (or `SESSION_PATH`; created 0700, refused as a symlink, and outside the app root also refused unless owned by the process user with no group/other bits), else a private `eventapp-sessions-<8 hex of the app root's sha256>` under the system temp dir under the same ownership rules, else the host's own handler *and* path untouched (`Session::storage()`; a fallback is reported through `Collector` once per process) — plus a 30-day `gc_maxlifetime` with its own GC at 1/1000, strict mode, cookie-only IDs, `lazy_write`, `cache_limiter` `''` (the screen middleware states the pages' cache policy instead) and a host-only cookie `eventapp` that is `HttpOnly`, `SameSite=Lax` and `Secure` on HTTPS. `session.auto_start` is the one thing it cannot set at run time and must be off on the host. Reads use `read_and_close`, so a slow kissj call never holds the session lock against the reader's next request (`SessionLockTest`), and a request without the cookie — or, on the app's own files store, with a cookie whose session file does not exist — reads nothing and starts nothing (no file, no `Set-Cookie`); every write goes through `transact()`, which reopens the session, applies the change to freshly read values under the handler's lock and closes it again — also what makes the admin nonce's check-and-consume atomic — and a reopen resumes the stored ID without sending the cookie again. A cookie the store does not know (collected, invented) still gets a new cookie and an empty file under strict mode — accepted. The cookie lasts `Session::LIFETIME` (30 days) and slides: `refreshCookie()`, called by Kernel's session-cookie middleware on every full logged-in page, re-sends it with a fresh expiry and touches the session file once a day (not on the host's store), because `read_and_close` never updates it and the GC would otherwise count from the last write. There is one session cookie per host, so `Session` namespaces its values per event slug: logging in to one event shows nothing in another, and a logout is local to its event. Login and logout rotate the session ID with `session_regenerate_id(false)` — rotated before the identity is stored, cleared before the rotation on logout — so the old ID is left holding the logged-out session rather than destroyed: the worker's install and refill bursts send up to ~26 requests with the cookie of the moment, and under strict mode a destroyed ID would answer one of them with a new empty session and a `Set-Cookie` that logs the reader out (`SessionRotationTest` checks it against a real server). The TIE form (`templates/_tie_form.twig`) sits both on `/profil` and, logged out, in Můj program itself; the latter posts `return=programy`, so the login redirects to `/programy#muj-program` (which `programs.js` opens on the list) and a failed code is explained there — any other `return` value falls back to `/profil`.

Theming: each event's `config.php` has a `colors` map (e.g. `base`, `darker`, `primary`, `text`, `text-invert`, and the optional `nav-active`) and an `assets` map (logo/favicon paths under `www/events/<slug>/`). `Kernel` exposes the whole event config as the `event` Twig global; `_layout.twig` emits the colors as `--color-*` CSS custom properties in an inline `<style>` block, and `www/style.css` consumes them (`var(--color-base)`, etc.) — no per-event CSS files, one shared stylesheet. `EventConfig::REQUIRED_COLORS` is checked at boot, so a half-themed event fails to start rather than rendering with unset properties. `www/style.css` must never name a colour itself; `ThemingTest::testCoreStylesheetHasNoColorLiterals` enforces that. Type is a seven-step `rem` scale in `:root` (`--fs-2xs` 11 … `--fs-2xl` 24 at a 16px root); two kinds of rule stay in px and `ThemingTest` names them: the chrome glyphs in the fixed-height bars, whose heights `www/programs.js` reads as plain pixel numbers, and the timeline grid's type (`.tl-tick`, `.tl-stage`, `.tl-card`), whose geometry is frozen. The focus ring is one global two-tone `:focus-visible` rule in the ground pair (`--on-ground` outline, `--ground` halo); `.tabs-tab`, `.tl-card` and `.sheet-close` move it inside their clipping box; the two dialog containers and the screen section (programmatic focus targets) draw none.

Next to `colors` sits an optional `theme` map (`EventConfig::$theme`, always an array) for the look-and-feel that is not colour — `font`, `font-display`, `font-display-weight`, `radius`/`radius-pill`/`radius-sheet`/`radius-card`, and `motion`. It is emitted as `--theme-*` in the same inline `<style>` block. There is no `font-url` any more: **every font and the icon font are self-hosted**. The `@font-face` rules for themix (400, 700), skautbold and Montserrat (latin and latin-ext, Google's v31 variable files with Google's `unicode-range`) live at the top of `www/style.css`, one woff2 `src` each, the files under `www/fonts/<family>/`; Font Awesome Free 5.8.1 is `www/vendor/fontawesome-free-5.8.1/` (its `all.min.css` byte-for-byte with its licence header, the three `.woff2` files it names, `LICENSE.txt`), linked by `_layout.twig` as `/vendor/fontawesome-free-5.8.1/css/all.min.css`. So `theme.font` may name only a family `www/style.css` declares (or a system font). `EventConfig::fontFamilies()` is what the event renders with — the first family of `theme.font` and `theme.font-display`, quotes stripped, or `themix`/`skautbold` where unset, plus `Font Awesome` always — and `App\Http\Fonts` is the plain table family → web paths that `Precache` puts into the offline set; `Tests\Unit\FontsTest` keeps that table, the `@font-face` rules and Font Awesome's own `url()`s in step.

The Content-Security-Policy is enforced by `Http\CspMiddleware`: `script-src 'self' 'nonce-…'` with a fresh nonce per request in the Twig global `cspNonce`, so every inline `<script>` carries `nonce="{{ cspNonce }}"` and no element may carry an `on*=` handler (the homepage push button is `data-push-toggle`, bound in `www/push.js`). Styles stay `'unsafe-inline'`: the timeline's per-programme `style` attributes cannot be hashed and must lay the screen out without JS, and an inline style can neither run code nor read data. Fonts and icons are `'self'` (self-hosted, above), so `style-src` is `'self' 'unsafe-inline'` and `font-src` `'self'`; the event's map origin is added automatically; anything else goes in the optional config key `csp` (`EventConfig::$csp`, `['frame-src' => ['https://…']]`, validated at load). `CspTest` renders every participating route and fails on a missing nonce.

Colour is **semantic roles**, not palette keys. No rule in `www/style.css` names a `--color-*` any more; every one reads a role, and the role definitions in `:root` are the only place the palette is touched (`ThemingTest::testNoRuleInTheStylesheetNamesAPaletteKey` enforces exactly that). The rule that keeps the system honest is **one colour, one role** — if an event's lime is `state`, lime is not also a ground, a surface or a piece of chrome. The set is sized for a 60:30:10 budget: `ground`/`on-ground` with `surface`/`on-surface` as its one block tier (60), `structure`/`on-structure` for the bars, the sheet, the buttons and the timeline's cards (30), and `action`/`on-action`/`action-link` plus `tonal`/`on-tonal` and `state`/`on-state` sharing the 10, with `edge`, `edge-width`, `heading`, `emphasis` and `scrim` in support. `structure` defaults to `--color-darker` rather than `--color-base`: it is the one role that is a filled ground under inverted type at body size, and obrok19's base carries `--color-text-invert` at 3.85:1 where its darker green reaches 6.84:1. Three scopes **rebind** the core roles rather than adding names: a text field, `.sheet-card` and `.tl-scroll` are each their own little surface with their own structure on it, so the grid's cards are simply `structure` in the grid's scope. The rebinding sits on `.tl-scroll` and not on `.pg` because custom properties inherit — on `.pg` it would also reach the pager, the day panel and the view tabs.

**Light mode is light and dark mode is dark, all the way through.** `structure` grounds every bar, sheet and card, so in a light set it is the palest thing on the screen and in a dark set the darkest; a filled near-black app bar in light mode is the "black element in the light mode" the system exists to prevent, and a lifted mid-grey card at night is the same mistake upside down (`ThemingTest::testTheLargeFilledAreasFollowTheMode` measures the relative luminance of every role that names a large fill and holds each mode to its own end of the ramp). Two things follow. First, an accent can only be **ink or a small area filled under dark ink**, never a large fill: obrok27's lime is 1.25:1 on a pale ground and obrok19's `#2a9272` is 3.49:1, so the **active tab is filled with the event's colour and carries `on-state`** (13.4:1 and 4.8:1 under near-black ink) rather than tinted type — the fill is the whole tab, not a chip behind the glyph, because tinted type at those ratios is the regression this rule exists to prevent — and `state` has one shape in both modes; the **app bar is the one other surface filled with `state`**, and everything on it — title, profile link, mode toggle — therefore takes `on-state` too, because that fill does not flip with the mode while `on-structure` does (it used to take `on-structure`, which put obrok27's pale dark-mode ink on lime at 1.12:1 and obrok19's body grey on green at 2.56:1); a secondary `.btn`, a `.highlight` link CTA, a `.notice` and the active day are **`tonal`** — the accent washed almost all the way into the ground, carrying the accent itself at full strength as ink. `.btn-primary` is unchanged in kind, a filled accent under inverted ink. Second, separation cannot come from a tone step alone, because content scrolls under a bar of very nearly its own colour, so **every bar, sheet and card also carries a hairline, in both modes** — `--edge-width`, still 0 for an event that declares nothing. Light hairlines are neutral and dark ones keep the accent tint; each clears 3:1 against both sides of itself, which is what the 1px content-block outlines replaced the old 4px frames for.

One role sits beside `structure` rather than inside it: `signature`/`on-signature`, **structure that carries the identity**. It behaves like structure — a filled band of chrome with type on it — but its value is a quiet cast of the event's own colour, and the **hour ruler is its only use in the app**; painting a second surface with it would return the screen to the state where nothing could read as an accent (`ThemingTest::testTheIdentityRoleIsUsedByTheHourRulerAndNothingElse` holds it to one). It is deliberately *not* the accent at full strength: a saturated slab is the loudest thing on a light screen and a lit panel at night, and the ruler is chrome. The stage column has its own pair (`stage`/`on-stage`) in the grid's scope because the card and the column want different tones out of the same tier — the card separates from the grid by a step plus its hairline, the column is a band behind bold names — but its value is a **plain neutral in both modes**; the lime cast round 9 gave it is withdrawn, because a hue on the largest block of the screen is how accents stop reading. Both pairs fall back to the grid's own `structure`, so an event that declares neither renders exactly as it did. The registered card has a pair of its own in the same scope: `registered-bg` (with `registered-line`/`registered-width`) and its ink **`on-registered`** (`--reg-fg`, falling back to `on-structure`), because on an accent fill the grid's card ink can fall far below AA (navigamus25's light set was 2.0:1); every kissj-design event names it in both sets. korbo26's dark set, likewise, carries a lighter orange (`#f08a3c`) as its `action-link`, `heading` and `emphasis` ink, its fill colour `#dd6700` being 4.39:1 on the dark surface.

Every role falls back to exactly the expression its rules used before roles existed, and those **built-in fallbacks are frozen** — they are the pre-round-10 look, dark chrome and all, and the fixture events under `tests/fixtures/events/` are what still exercise them (`testEveryRoleFallsBackToThePalette`, `testStructureDefaultsToThePalettesDeeperTone`). No shipped event uses them: **obrok19 hand-authors a `light` set of its own** and is no longer the frozen control — its tab bar is white, its green fills the app bar, the active tab and the registered programmes, its red is `action`, and `docs/baseline/obrok19/` is re-taken by `bin/baseline.php` at the end of every round, so a diff against it is still how a round shows it disturbed nothing. obrok19 stays **light-only**: no `dark` set, no toggle. An event that wants its own colours declares `roles` as two **hand-authored** sets, `light` and `dark` (`EventConfig::$roles`) — accents do not survive mechanical inversion, so changing a colour is deliberately a two-place edit. `_layout.twig` emits light as the base, then the dark set twice: once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-mode="light"])` so the device's setting works without JS, and once under `:root[data-mode="dark"]` so an explicit choice wins. A tiny **inline script in `<head>`**, before the stylesheet link, sets `data-mode` from `localStorage['obrokColorMode']` (global, not per event) or from `prefers-color-scheme` — never the deferred script at the foot of the page, or the reader sees a frame of the wrong theme. A sun/moon `<button>` in the app bar flips it, and appears only for an event that declares a dark set; its tap handler is in `www/app.js`, its name is the constant `Tmavý režim` and `aria-pressed` carries the state.

Colour reaches the **assets** too, because a bar that follows the mode cannot carry one fixed drawing. `assets.menuLogo` is the tab-bar mark and `menuLogoDark` its dark-mode twin (`.mode-light-only`/`.mode-dark-only` swap them; obrok27 is purple by day and lime at night), while `menuLogoOnState` is the drawing for a surface filled with `state` — that fill is the event's own colour, so a mark in that same colour disappears on it. Which drawing goes where follows from what the surface is filled with, and **the tab bar and the app bar are not the same kind of surface**: the tab bar is `structure` and flips with the mode, so it takes the mode pair, but the app bar is `state` and does not, so it takes `menuLogoOnState` exactly as the active tab does. Giving the app bar the mode pair is what put obrok27's lime ghost on lime and left the mark invisible at night. Each asset is optional and the classes are only emitted when the second drawing exists, so an event with one logo keeps showing it everywhere. `mainLogo`/`mainLogoDark` do the same job on the homepage.

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link; the logo's link to the homepage carries a visually hidden `<event name> – úvod`, since the logo is decorative and the link would otherwise be announced as the current screen's title) and a fixed bottom tab bar built from the enabled features and sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Login lives on `/profil` (core routes, not a module) and the app bar reads the current identity through the `auth_identity()` Twig function rather than a global, because a handler can log the user out during the same request that renders the bar.

Switching screens does not load a document. `<main>` is a **stack of screens** — `<section class="screen" data-screen data-title data-doc-title data-tab data-fetched-at [data-stale] tabindex="-1">`, emitted identically by `_layout.twig` (the first one, server-rendered) and by `_screen.twig` (every one after it). A request carrying `X-Screen: 1` gets the second parent: every participating template picks its own with `{% extends fragment ? '_screen.twig' : '_layout.twig' %}`, against a Twig global that `Kernel`'s screen middleware sets per request. `data-fetched-at` (always, `DATE_ATOM` in Europe/Prague) is when the provider data on the screen was fetched — the request time on a screen that used none, and on every stub event — and `data-stale="1"` marks an old copy served because kissj failed; both come from the Twig function `data_freshness()` (a function, like `auth_identity()`, because the handler fills it before the layout renders). `www/shell.js` renders the freshness line ("aktualizováno HH:MM", "offline · z HH:MM", below) from them. A background revalidation compares `innerHTML`, which leaves the section's own attributes out, so `app.js`'s `syncFreshness()` carries the two attributes over on both the unchanged and the morphed path. Next to `fragment` the middleware sets `screenPath`, which exists because slim/twig-view resolves `get_uri()`'s runtime exactly once and then keeps it for the life of the `App` — the path would be stale from the second request on, which no single-request web server notices and every test does. A plain request stays byte-identical to what it was, which is what keeps deep links, crawlers, the back button against a cold cache and a reader with JS off working, and `Vary: X-Screen` keeps the two responses apart in anything that caches them.

`www/app.js` fetches a screen **once**, inserts it hidden, and from then on navigation is show/hide. Nothing is ever removed, so state is *live* rather than restored: the map's Google iframe keeps running, the timeline keeps its zoom *and* its horizontal scroll, a half-typed TIE code stays typed. Hidden and not detached is the whole point — re-inserting a detached `<iframe>` re-fetches it, which is also why neither `hx-preserve` nor `data-turbo-permanent` could have done this: both persist a node present in *both* documents, and the map exists on one screen only. Order matters, **insert → show → init**: the ruler's label-width measurement and every `scrollLeft` calculation return 0 inside a `hidden` subtree. Showing a cached screen is instant, always; one fetched more than five minutes ago is revalidated in the background, and a screen whose HTML has actually changed is **morphed** into the new one rather than replaced — `innerHTML` would throw away the very state the cache exists to keep. The morph is hand-rolled and small (no diffing library, and deliberately not a vendored Idiomorph): children match on `id`, then `data-key`, then position among same-tag siblings; a subtree already equal to its counterpart is skipped outright; a matched `<iframe>` is never written to *and never moved*, because a move re-inserts it and a re-inserted iframe reloads. It writes only the attributes the fresh markup states — one it does not carry at all belongs to the client (`--hour-width` lives in `.pg`'s `style`, `data-hour-step`, `data-pg-ready`, `disabled`) — and one the markup names in **`data-morph-keep`**, for the attributes the server writes without owning: `.pg`'s `data-view` and `data-step`, `.tl-page`'s `class`. Without that the screen would be put back on the server's default view and page, and a layout landing in the gap before the screen restores itself would take the reader's scroll with it. What the screen does own it puts back on a `screen:morphed` event, dispatched synchronously in the same task. A morph, like a replacement before it, never happens while the reader is in the middle of a screen — an open sheet, an open day panel or focus in a form field defer it to the next time that screen is shown, and it then runs *after* the screen is visible again, for the same reason the wiring does. Measured on the Program screen: a revalidation that finds no change touches **zero** nodes; one that finds a renamed, re-timed programme touches seven, on a screen holding sixty cards. Screens slide **by tab order** through the View Transitions API: the loader only sets `data-nav` on the root and the animations live in `www/style.css`'s one reduced-motion block, so where the API is missing — or reduced motion is asked for — the swap is instant rather than animated by hand. There is deliberately **no swipe gesture**: a horizontal drag on the timeline means "scroll the hours".

A response that is not a 200 is not a screen: the loader falls back to a plain navigation, so the reader gets the server's own error page instead of an app bar injected into a `<section>`. So does a screen the reader is waiting for that has not arrived after 8 s (`LOAD_TIMEOUT`, an `AbortController` on `load()`'s fetch), because on lie-fi a fetch that never ends would leave the tap hanging for minutes. `show()` dispatches `screen:hidden` (bubbling) on the section it hides, so a screen's own dialogs do not outlive it. The skip link is the one same-origin link the loader handles itself: it names the path the document was first served for, which after a swap is another screen, so a click on it focuses the visible screen's section and navigates nowhere. The participating set is read off the rendered shell — the tab bar's own links plus the profile one, in that order, which is what makes `/profil` count as forward — so it is the five tab destinations and `/profil` and nothing else. The handbook PDF, external links, `/admin/notify` and **every non-GET** stay plain navigations, so logging in reloads the document and empties the cache with it; that is the correctness rule rather than laziness, because login changes both the app bar identity and the registered marking on every programme. Every link stays a real `<a href>` and the loader is an enhancement layer, not a client router: with `www/app.js` absent the app behaves exactly as it did.

**The worker is the offline copy.** Its `install` fetches `/<slug>/precache.json` (with `cache: 'no-store'`; core route `precache`, built by `App\Http\Precache`: `documents` = the homepage, every tab in tab order (`Kernel::menu()`), `/profil` and `/offline`; `assets` = the stylesheet and scripts through `AssetVersion` (`programs.js` only for an event with the `programs` feature, as the layout loads it), the manifest, the layout's icons, every non-empty `assets` path, `homepage.footerLogo`, the manifest's icons and `Fonts::files(EventConfig::fontFamilies())` — the event's own fonts and Font Awesome, nothing it does not render with — a file missing on disk is left out, because one 404 fails the whole install; `optional` = the handbook when its file exists; `version` = 8 hex of sha256 over the sorted `documents`, `assets` and `optional` lists, so an enabled tab or a new handbook is a new version too) and fills the cache `eventapp-<slug>-<version>` with every document in both forms and every asset, writes the list itself into that cache **last** — after the documents and assets, before the optional entries, which may fail one by one — and then calls `skipWaiting()`. The stored `precache.json` is the completion marker: a fill that fails deletes its own half-filled cache, a target cache that already holds the marker is adopted as it is (a redeployed `sw.js` with an unchanged list reuses it rather than refetching), and `currentCache()` and `activate` adopt only the newest of the event's caches that holds it — never one still filling, or abandoned when the browser killed a worker mid-fill. Two fills of one version (a new worker's install and an old worker's `checkVersion()`) could delete the cache under each other's handle, so `adopt()` first re-checks through a fresh handle that the cache still exists and holds the marker (`isComplete()`: `caches.has()` plus the marker) and deletes the other caches only then, `install` fails when its own fill was lost that way, `activate` clears `cacheName` when nothing was adopted, and a failed fill deletes its cache only if the marker is still missing. `activate` then deletes the event's other caches, `clients.claim()`s and posts `sw-activated` (nothing reloads); when no complete cache exists it deletes nothing. `sw.js` itself is never versioned, so a deploy that changes an asset but not the worker never reaches `install` — the browser reinstalls a worker only when its script changes. That is `checkVersion()`'s job: once per worker lifetime, after a page was served from the network, it fetches `precache.json` with `cache: 'no-cache'` and, on a different `version`, fills the new cache, adopts it, deletes the others and posts `sw-activated` — unless a newer worker has become the active one meanwhile, whose cache it would otherwise delete; it does not run at all (and does not count as done) while a worker is `installing` or `waiting`, because that one fills the version itself; any failure leaves the current cache. The Cache API keys on the URL alone, so a fragment is stored under its URL plus `?x-screen=1` — in the cache only; no page links to it. Strategies: a hashed asset (a root `*.css`/`*.js` with `?v=`) and anything under `/fonts/` or `/vendor/` cache-first; an unversioned file under `/events/<slug>/` stale-while-revalidate, its network leg fetched with `cache: 'no-cache'` because nginx and `.htaccess` give the extension-matched files there (png, svg, jpg, webp, ico, woff2, css, js — not `site.webmanifest`) a year of `immutable` and a plain fetch would never get past the HTTP cache; a page (`navigate`) network-first — after 3 s the cached copy is shown if there is one (without one it keeps waiting), a failed fetch or `navigator.onLine` false goes to the cache, and `/offline` (`templates/offline.twig`) answers when there is neither — a page carries the identity, so it never comes from the cache while the network answers; a fragment from `load()` stale-while-revalidate, posting `screen-updated {path}` to that window when the server's copy differs (compared without `data-fetched-at`/`data-stale`, or every stub screen would differ on every fetch); a fragment from `revalidate()` (`cache: 'no-cache'`) network-first, its cache fallback carrying `X-From-Cache: 1` so the loader does not take an offline answer for a confirmation — it neither resets the screen's `fetchedAt` nor skips the real check for five minutes once the signal is back. Every successful page and fragment is stored. Every same-scope non-GET except under `/admin/` and `/push/` deletes every `text/html` entry, from **every** `eventapp-<slug>-*` cache (a fill still running holds pages of the identity before too), once the server has answered it and before that answer reaches the page — a POST that fails offline, a login tapped with no signal, purges nothing and is answered by the worker with a 503 inline page of its own (`OFFLINE_WRITE`: "Jsi offline", "Přihlášení i odhlášení potřebuje signál…", a link home; no stylesheet or script), never the cached `/offline`, whose "not saved yet" is not what happened, and never the browser's error page, which an installed iOS app has no Back button out of (purge on write: a login or a logout never serves a screen rendered for the other identity; a push subscribe or unsubscribe changes no rendered HTML, and purging there would empty the offline copy with nothing to refill it until the next navigation), and the next page that arrives from the network refills the missing documents for the identity now in the cookie. A purge also bumps a counter that every page and fragment write captures when its request starts, and a write that started before a purge is dropped rather than stored for the old identity (a login during the very first install is a POST the not-yet-active worker never sees — accepted; the next login or logout repairs it). A page whose network answer is a 5xx gets the cached copy when there is one and the server's error page when there is none — never `/offline` while the server answers. A fragment that turns out changed costs two network fetches (the worker's background fetch, then the loader's `no-cache` revalidation after `screen-updated`); an unchanged one costs one. `/admin/*`, `/push/*`, `/precache.json`, `/health`, other events and other origins (only the map's iframe is left) are never touched. Rollback is a `sw.js` with the push handlers and an `activate` that deletes every `eventapp-<slug>-*` cache.

The loader and the worker: `revalidate()` sends `cache: 'no-cache'` and `load()` does not. `go()` dispatches `screen:loading`/`screen:loaded` on `document` around a fetch the reader waits for, never around a background revalidation (and `screen:loaded` once more on an instant show, so the bar of an overtaken tap goes). The loader listens to the worker: `screen-updated {path}` and `news-updated {programme}` set the entry's `fetchedAt` to 0 (Novinky always, the Program screen too for a programme message) and revalidate the one on show, so a new `.news[data-key]` is morphed in at the top; a path reported before the loader has it waits in `staleOnArrival`. `syncFreshness()` dispatches `screen:freshness` on the section whenever it changes either attribute.

`www/shell.js` holds the installed-app concerns and talks to the loader only through those events. It registers the worker; fills each screen's `<p class="freshness" data-freshness hidden>` — emitted by both parents right after the `<h1>`, unless the template sets `showFreshness` false: the Program screen when the programme list could not be read at all (`programmesUnavailable`), the error and offline pages — from the section's `data-fetched-at`/`data-stale`, re-read every time it draws (`DOMContentLoaded`, `screen:shown`, `screen:morphed`, `screen:freshness`, `online`/`offline`): `aktualizováno HH:MM`, `naposledy načteno HH:MM` when stale, `offline · z HH:MM` when `navigator.onLine` is false, the time formatted by hand on the reader's clock; toggles `data-loading` on the root for the 2px `.progress` bar at the tab bar's top edge (`var(--on-structure)`, the bar's own ink, because `state` is under 3:1 on a pale bar; a static bar under reduced motion); and keeps `beforeinstallprompt` (default-prevented, so Chrome shows nothing by itself) for the hidden `Přidat na plochu` button (`.install`, `.install-btn`) on `/profil`, which shows the kept offer once and is hidden again after the tap, on `appinstalled` and in `display-mode: standalone`. It also minds the map offline: Google's iframe is a blank box without a network, so `map.twig` puts a `<p class="empty map-offline" data-map-offline hidden>Mapa potřebuje připojení.</p>` right after the `[data-map]` box, and `shell.js` (on `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `online`, `offline`) hides a map that never loaded behind that note while `navigator.onLine` is false and reloads its iframe once the signal is back; a map that did load (one capture-phase `load` listener marks it `data-map-loaded` while online) stays as it is, with no note. The one-screenful screens give the line's 20px back through `--freshness-space`. `_layout.twig` also carries `<noscript><p class="noscript">` as `<main>`'s first child; nothing else is promised without JS. Stylesheet and scripts are linked through the Twig function `asset_version('style.css')` → `style.css?v=<first 8 hex of sha256>` (`App\Http\AssetVersion`, memoised per process by path, mtime and size): nothing is bumped by hand, and `sw.js` is never versioned. The self-hosted fonts and icons under `www/fonts/` and `www/vendor/` carry no hash and follow one rule instead: **a changed file gets a new name** (a new Montserrat is `montserrat-v<N+1>-…`, a new Font Awesome a new `fontawesome-free-<version>/` directory), never new bytes under the old one — nginx and `.htaccess` give both prefixes a year of `immutable` and the worker serves them cache-first, so a file replaced in place would never reach a returning reader. Each `site.webmanifest` carries `id`, `lang`, `orientation`, a maskable 512 icon and `shortcuts` for the enabled Program/Novinky; `<link rel="mask-icon">` is emitted only for an event whose config has `assets.pinnedTab` (obrok19 only; obrok27's pinned-tab mask was drawn from the 2019 shield and is gone). The three head icons default to `events/<slug>/favicon-16x16.png`, `favicon-32x32.png` and `apple-touch-icon.png`; the optional `assets.favicon16`, `favicon32` and `appleTouch` override them, which is how obrok27 serves the set `bin/event-icons.php` generates from its ghost: content-hashed `icon-<hash8>-<size>.png` names (nginx and `.htaccess` serve PNGs under `www/events/` as immutable for a year, so new bytes under an old name would never reach a returning browser), transparent favicons, opaque home-screen icons on the background colour (iOS paints transparency black) and a maskable one inside the 80 % safe zone, with the manifest's icons rewritten in place.

Errors render through `App\Http\TwigErrorRenderer`, registered for `text/html` and as the default on `QuietErrorHandler`: the event's `templates/error.twig` extends the layout — 404 and 405 read "Tohle tady není.", anything else "Něco se pokazilo. Zkus to za chvíli.", both with a link home, and under `APP_DEBUG` a `<details class="error-details">` with Slim's detail set; the instance app uses the plain `templates/instance-error.twig`. A fragment request that errors gets the whole document. An error page that itself fails to render falls back to `TwigErrorRenderer::FALLBACK` and is reported through `Collector`; JSON clients keep Slim's JSON.

Two rules the shell depends on. `<main>` must **never** carry a `view-transition-name`, however natural it looks: naming an element makes it a stacking context, and the sheet and the day panel are fixed children of `<main>` that have to keep painting over the fixed tab bar. Only `.appbar` and `.tabbar` are named, which takes them *out* of the root snapshot so the shell sits still while the screen under it slides. And the per-screen layout rules key off the section (`.screen[data-tab="map"]`, `"programs"`, `"homepage"`) rather than the old `body.screen-*` classes, with `main > .screen[hidden]` restating `display: none` loudly enough to out-specify them.

`ProgramsModule` (`/programy`) is the single Program screen. Its behaviour is `www/programs.js`, not an inline `<script>`: it used to sit in `{% block header %}`, i.e. in `<head>`, which no screen swap can reach. The file exposes one idempotent `window.pgInit(scope)`; the shell loads it for any event carrying the `programs` feature, the loader calls it by dispatching `screen:shown` on the section it has just made visible, and a server-rendered Program screen wires itself on `DOMContentLoaded` so the screen keeps working even if the loader never runs. The hand-authored schedule (`content/schedule.php`) and the separate harmonogram screen are gone: everything the screen shows comes from `ProgramProviderInterface`. When a participant is logged in, the module also calls `getProgramsForIdentity()` and marks their programs `registered` — that marking is the only thing login affects, so keep it working when the screen changes. The API is expected to grow to carry the non-registerable items too (budíček, nástupy, táborák), which is what the old schedule file used to hold.

The screen holds two views of that one data set, built from the Figma flows *Registrace programů* and *Burza (Var. 2)*, and a floating pill above the tab bar switches between them client-side. **Harmonogram** (the timeline) is a Gantt grid: rows are the distinct `location` values (`location` is reused as the stage axis — the contract has no `stage` field, and programs with a null location fall into a `Bez lokace` row), columns are hours, one page per **day** holds every section's programmes (key `page-YYYYMMDD`), and it is the one place in the app allowed to scroll horizontally. Overlapping programs in one location are packed into sub-tracks by a greedy interval fit. A programme that runs over several days sits on the page of **every calendar day it overlaps**, each piece clipped to its day (`ProgramsModule::segments()`, at most `MAX_DRAWN_DAYS`), so no piece can stretch a day's axis; an end at exactly 00:00 belongs to the day before, so 23:45–00:00 stays one card on its evening. Every piece carries the programme id as its `data-key` — unique among siblings, which is all the morph matches on, because a page holds one piece per programme — opens the one sheet, and has the same registered state and label; a label names both days whenever the run spans more than one. The sheet, and with it the deep link, belongs to the start day's page, and Můj program lists the programme once, under that day. The hour scale is zoomable: everything on the grid is positioned as `calc(var(--hour-width) * n)`, so setting that one property rescales the time axis and nothing else — never `transform: scaleX()`, which would distort the programme names. `--hour-width` runs between `--hour-width-min` and `--hour-width-max` (40–200px, declared in `www/style.css` next to the property), opens at 80px, and is driven by a −/+ pair at the right end of the timeline's pager row, by a two-finger pinch on the grid (`touch-action: pan-x pan-y` on `.tl-scroll` keeps the browser's own pinch out of it; the viewport meta is deliberately left alone so page zoom still works everywhere) and by ctrl+wheel. Every step recomputes `scrollLeft` so the moment under the anchor — the midpoint between the fingers, or the centre of the visible grid for a button — stays put. The scale is kept in `sessionStorage` under `pgZoom:<slug>`, so paging and view switching preserve it and a fresh visit starts at 80px. Below a threshold the ruler thins its text to every second hour while every hour keeps its mark — the script sets `data-hour-step` on the root from the live scale and `www/style.css` hides `.tl-tick:nth-child(even) .tl-tick-label`, so tick positions never move and the leftmost hour is never blanked. The threshold is the rendered label's width plus 19px, measured on the page rather than hardcoded because themix and Montserrat differ by 6px at 14px/700. **Můj program** is a plain list of `getProgramsForIdentity()` only, grouped by **day**, like the timeline — `ProgramsModule::buildDays()` is the one that does it. It does not page at all: every day is in the document, first to last, under its own **sticky heading**, and the reader scrolls the lot. Only that view's strip changed shape — Harmonogram keeps its `‹ ›` and its zoom pair, and the two strips are separate elements. The list's is an **orientation instrument**: its label names the day being read rather than a page being shown, `↑` goes to the start of the day being read and only then to the day before it (the rule a music player's "previous track" uses) while `↓` goes to the next day's start, both smooth-scrolled unless reduced motion is asked for, and both disabled at their end of the list; tapping the label still opens the day menu, which now scrolls instead of switching. Nothing of this runs on a scroll event: an `IntersectionObserver` watches the day sections against a band starting one pixel below the strip — one pixel, because a day scrolled to its own start puts its top edge and the previous day's bottom edge on the same line and an observer asked about that line answers "both" — and each crossing costs one coalesced `requestAnimationFrame` that reads no geometry. The day owning the top of that band is the day whose heading is stuck there, so the strip and the heading cannot disagree — which holds only because `.pl-head`'s dock line, `bandTop()` and the observer's `rootMargin` all read the **same three tokens**, `--appbar-height` + `--appbar-inset` + `--pager-height`. Leaving the safe-area inset out of any one of them docks the heading behind the strip on a notched install (34px, measured). The observer fixes its margin at creation, so an inset that changed at runtime would leave the band stale until it is rebuilt; nothing does that yet. `.pl-day:last-child` carries a `min-height` of the reading band, or the last day could never dock under the strip and `↓` would land short of it. The screen's scroll offset is live state like everything else, so leaving Můj program and coming back lands where the reader was; switching to Harmonogram and back does too, because that view is exactly one screenful and the browser clamps the window's scroll while it is up, so `showView` saves and restores it. When a participant's personal list was actually read (`mineRead`), programs they are not registered for are dimmed with `opacity` — never a colour, because `www/style.css` may not name one; logged out, or logged in while `getProgramsForIdentity()` failed, nothing is dimmed and Můj program shows no "Zatím nemáš přihlášený žádný program." line (the notice explains), since "not chosen" would be a guess; nor does the timeline say "Program zatím není k dispozici." when the list could not be read at all (`programmesUnavailable`). A perex is plain text whose `\n`s are meant (`docs/kissj-contract.md`), so `.sheet-perex` and `.pl-perex` are `white-space: pre-line` and the template puts nothing but the escaped text inside them. Tapping a program opens a modal, and the `#section-<id>-program-<id>` deep link opens the right one, puts the timeline on its page, and parks the personal list on that programme for when the reader switches to it. An open `.sheet` or `.pager-menu` is a real dialog: everything outside it goes `inert` — the app bar, the tab bar, the skip link, the sibling screens — and Tab rings inside the card, because a modal a reader can tab straight out of is not one. The trap remembers exactly which elements it marked, so closing clears its own and nothing else, and it releases *before* the focus returns to the opener, since an inert element cannot take focus. Opening the sheet or the day panel also pushes a history entry (`{pgOverlay: true}`, replaced rather than stacked when one is already up), so Android's Back closes the dialog instead of leaving the screen with the rest of the app inert, and closing it any other way goes back over that entry once — a day picked from the panel scrolls only after that traversal has landed, with `history.scrollRestoration` held at `manual` while an overlay entry is up so the browser does not restore the scroll it saved; an open asked for while a close's `history.back()` is still in flight waits for it. Chrome's history-manipulation intervention may let Back skip an entry pushed without a user gesture (the sheet a deep link opens on landing), so the entry is no guarantee; the backstop is that `popstate` on any entry and `screen:hidden` on the Program screen close both dialogs and release the trap, which can leave an orphan entry costing one idle Back — accepted. The sheet's elements are looked up on every use rather than held from the first render, and every child of `.pg` carries a `data-key` (`notice`, `pager-<kind>`, `menu-<kind>`, `tabs`, `sheet`) or an id (the two views), because the morph matches unkeyed siblings by position and once turned a reference to the sheet into the day panel. Everything is read-only: the screen never registers anybody for anything, which is why the Figma heart/favourite component is deliberately absent, along with its photo, capacity and attendee-count fields. `ProgramsModule` does all the grouping in PHP and hands Twig a finished view model; every page is rendered into the DOM so the `#section-<id>-program-<id>` deep link can open a modal on any of them.
