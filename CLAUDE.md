# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Modular support web app for Czech scout events (Obrok). Built on Slim 4 (PHP >= 8.3). One codebase serves multiple events — each event is a config + content directory under `events/<slug>/` plus public assets under `www/events/<slug>/`, selected at runtime by the first path segment: every event lives under `/{slug}/`, and `/` is a picker of the listed ones. Code is in English — comments, docblocks, exception messages, identifiers. Czech is reserved for what users actually read: UI strings in `templates/`, per-event content under `events/<slug>/content/`, user-facing notices and flash messages, and the weekday names in `Kernel`. Commit messages and `docs/` are in English without AI-authorship trailers (the existing `docs/kissj-contract.md` predates this and is still Czech).

## Commands

- `docker-compose up` — run the dev server (PHP built-in server inside `php:8.3-alpine`), then visit `localhost:8080`
- `composer start` — alternative: run locally via `php -S localhost:8080 -t www/`
- `composer test` / `vendor/bin/phpunit` — run tests (PHPUnit 11, config in `phpunit.xml`, suites `Unit` + `Functional`)
- `vendor/bin/phpunit --filter testGetHomepage` — run a single test
- `docker run -d --name eventapp-korbo --rm -p 8081:8080 -v "$PWD":/app -w /app -e PROGRAM_PROVIDER_KORBO26=stub -e APP_DEBUG=1 php:8.3-alpine php -S 0.0.0.0:8080 -t www/` — serve the `korbo26` dev event (the realistic Korbo camp data through the stub provider) on `localhost:8081/korbo26/programy`; the `-e` values override `.env`, and TIE code `KORBO1` logs in as the participant with 8 programmes
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/kissj-fixtures.php <slug> [--clamp-all-day=HH:MM-HH:MM]` — regenerate `events/<slug>/fixtures/` from `tests/fixtures/kissj/<slug>/` through the real `KissjProgramProvider` mapping; `--clamp-all-day` narrows programmes that kissj stores as whole-day runs to the given window
- Local only, not in the repo (`.gitignore`): the mock events' source material under `docs/` and the two converters that read it, with their tests. Only the JSON they produced is committed, so the two commands below work only on a machine that still has those files.
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/obrok-harmonogram.php "docs/Harmonogram celé akce.xlsx"` — convert the organisers' harmonogram spreadsheet into `tests/fixtures/kissj/obrok27/`; then run `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/kissj-fixtures.php obrok27` to regenerate the served `events/obrok27/fixtures/` from it
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/miquik-rozvrh.php "docs/MQ-Přednášky - data.xlsx"` — convert Miquik's lecture workbook (the `Rozvrh` room grid joined to the speakers' form answers) into `tests/fixtures/kissj/miquik26/`; then `bin/kissj-fixtures.php miquik26`. The workbook has no date, so every talk sits on the invented `MiquikRozvrh::DATE`

Before running, copy `.env.example` to `.env` and set `APP_DEBUG=1` for dev; there is no event to choose, the URL does (`localhost:8080/obrok19/`, the reference event).

Five events ship: `obrok19` (the reference), `obrok27`, `korbo26` (the former `korbo`), `navigamus25` and `miquik26` (unlisted: its lecture data is in, its date is invented). Two of them are **unlisted**, i.e. absent from the picker but reachable by URL: `miquik26` (`listed` false) and `obrok19` (no `listed` key at all, so it defaults to unlisted; it is served at `/obrok19/`). **korbo26, navigamus25 and miquik26 wear kissj's design**, adjusted to eventApp's contrast rules. A slug matches `/^[a-z0-9-]+$/` and ends in a two-digit year; the fixture TIE code is the slug without its digits, upper-cased, plus `1` (`KORBO1`, unchanged by the rename). That rule covers the pipeline events; obrok19 has no source in the pipeline and its fixture TIE code `ABC123` predates the rule. An event's `config.php` also carries `listed` and `dates` (`start`/`end`), which the picker uses to split upcoming from past.

## Architecture

`www/index.php` is a 3-line front controller: it requires the Composer autoloader and calls `App\Kernel::boot($_SERVER['REQUEST_URI'] ?? '/')->run()`, which picks the event from the first path segment (see `Kernel::boot()` below). All bootstrap logic lives in `src/Kernel.php` — no `settings.php`/`dependencies.php`/`middleware.php`/`routes.php` split, no route closures scattered across a routes file.

`Kernel::boot($_SERVER['REQUEST_URI'])` loads `.env` (if present) and looks at the first path segment: if `EventCatalog` knows it, `Kernel::create()` builds the app for that event; otherwise `Kernel::createInstance()` builds the instance-level app that serves the picker at `/` and Slim's 404 for the rest. Nothing is configured per deployment about which event is served. Env vars are per event where they are secrets or choices of an event — `<NAME>_<SLUG>` with the slug upper-cased and `-` turned into `_` (`PROGRAM_PROVIDER_OBROK27`, `KISSJ_API_KEY_OBROK27`, `ADMIN_TOKEN_OBROK27`), read through `EventConfig::env()` (which falls back from `$_ENV` to `getenv`, because php-fpm may leave `$_ENV` empty); `APP_DEBUG`, `KISSJ_BASE_URL`, `VAPID_*` and `PUSH_DB_PATH` are instance-wide and read from `$_ENV`. A 404 or 405 is not logged (`src/QuietErrorHandler.php`), and `Kernel::TIMEZONE` is `Europe/Prague`.

`Kernel::create()`:
- Builds a PHP-DI container (`ContainerBuilder`) with the event, the program provider, `Session`, `Auth\Authenticator` and Twig as definitions.
- Creates the Slim 4 `App`, adds body-parsing/routing middleware, Twig middleware, and error middleware (`APP_DEBUG` controls whether error details are shown), and then the screen middleware — added *last*, so it is the outermost layer of the stack. A thrown 404 or 500 is answered by the error middleware without ever reaching the route, so a `Vary: X-Screen` set further in would be missing from exactly the responses a shared cache is most likely to keep.
- Registers core routes (`GET /<slug>/` homepage, the TIE-code login/logout on `/profil`) directly, then iterates `$event->features` and registers one module per enabled feature.

`EventConfig` (`src/EventConfig.php`) loads and validates `events/<slug>/config.php` (requires `name`, `colors`, `features`; also carries arbitrary `raw` data via `get()`, and `dir` for locating fixtures/content). `EventConfig::content(string $name)` loads `events/<slug>/content/<name>.php`, a plain PHP file returning an array (e.g. `content/links.php`) — these are per-event, not code. News has no content file: it is the list of sent notifications (below).

Modules implement `App\Module\ModuleInterface` (`key()`, `menuItem()`, `registerRoutes()`) and live in `src/Module/`. `ModuleRegistry::classFor($feature)` maps a feature-flag string (from the event's `features` array in its config) to a module class — this is how features are toggled per event, e.g. `NewsModule`, `LinksModule`, `MapModule`, `HandbookModule`, `ProgramsModule`. `PushModule` (web push notifications) is implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and a token-gated `GET/POST /admin/notify` (shareable link with `?token=<ADMIN_TOKEN_<SLUG>>`) sends notifications through `App\Push\PushSenderInterface`/`WebPushSender`, either to everyone or to one programme — whose participants `ProgramProviderInterface::getTieCodesForProgramme()` names. Every send needs a Podpis (log only, never in the notification) and is written to the `messages` log (`App\Push\MessageRepository`, same database), which is kept forever: the admin page lists it and can hide a message from readers or show it again, recording who and when, but nothing is ever deleted. Subscriptions carry an `event` column and a send reaches only that event's subscribers; each also carries the TIE code of the session that saved it, which `www/push.js` keeps in step by re-sending the subscription after a login or logout, so a programme send reaches exactly the subscribed browsers of its registered participants; `SubscriptionRepository` adds the column to an older database, and rows from before it belong to no event and are never sent. `www/sw.js` stays at the docroot root and is registered at scope `/<slug>/` (the `event-base` meta tag), so two events in one browser keep separate workers.

`NewsModule` (`/novinky`) is that log as readers see it: every visible message, newest first. A message for everyone is there for every reader; a programme message appears on News only to a logged-in participant whose `getProgramsForIdentity()` includes that programme (a failing call just leaves those out — News never logs anybody out), and in that programme's sheet on `/programy` for everyone. Because of that `news` requires `push`: `EventConfig::load()` refuses an event that enables one without the other, and every shipped event carries both.

Program/schedule data goes through `App\Program\ProgramProviderInterface` (`getPrograms()`, `getSections()`, `getProgramsForIdentity()`, `getTieCodesForProgramme()`). `StubProgramProvider` reads `events/<slug>/fixtures/programs.json`, `fixtures/sections.json` and `fixtures/registered.json` — no network calls, safe for dev and tests. `KissjProgramProvider` (Guzzle-based) talks to the real kissj registration API. `Kernel` switches between them via `PROGRAM_PROVIDER_<SLUG>=stub|kissj` in `.env` (default `stub`); `kissj` additionally requires `KISSJ_BASE_URL` (the kissj root) and `KISSJ_API_KEY_<SLUG>` (`Kernel` throws a `RuntimeException` if either is empty); the key is sent as `Authorization: Bearer` on every request and is what tells kissj which event is asking, so no event slug is configured anywhere. `docs/kissj-contract.md` is the agreed contract, but kissj does not serve those endpoints yet — do not flip a production event to `kissj` until it does. The provider also supplies the programme **sections** through `getSections()` — id, title, display order and the optional `subTitle`, map `image` and `attachment` — from the `sections` of kissj's list response, or from the stub's `fixtures/sections.json`, which is that same list in kissj's shape (`App\Program\Sections` maps both). The event config carries no `sections` key any more.

Login lives under `src/Auth/`: `Authenticator` (session-backed login state), `Identity` (value object for a logged-in TIE-code participant), `UnknownParticipantException`. **The TIE code is the only login** — there is no external SSO to register an app with. Each event resolves a code against its own provider, so a code typed into another event is rejected as `Neplatný TIE kód.`. There is one session cookie per host, so `Session` namespaces its values per event slug: logging in to one event shows nothing in another, and a logout is local to its event. The TIE form (`templates/_tie_form.twig`) sits both on `/profil` and, logged out, in Můj program itself; the latter posts `return=programy`, so the login redirects to `/programy#muj-program` (which `programs.js` opens on the list) and a failed code is explained there — any other `return` value falls back to `/profil`.

Theming: each event's `config.php` has a `colors` map (e.g. `base`, `darker`, `primary`, `text`, `text-invert`, and the optional `nav-active`) and an `assets` map (logo/favicon paths under `www/events/<slug>/`). `Kernel` exposes the whole event config as the `event` Twig global; `_layout.twig` emits the colors as `--color-*` CSS custom properties in an inline `<style>` block, and `www/style.css` consumes them (`var(--color-base)`, etc.) — no per-event CSS files, one shared stylesheet. `EventConfig::REQUIRED_COLORS` is checked at boot, so a half-themed event fails to start rather than rendering with unset properties. `www/style.css` must never name a colour itself; `ThemingTest::testCoreStylesheetHasNoColorLiterals` enforces that.

Next to `colors` sits an optional `theme` map (`EventConfig::$theme`, always an array) for the look-and-feel that is not colour — `font`, `font-display`, `font-display-weight`, `font-url` (which becomes a stylesheet `<link>` instead of a property), `radius`/`radius-pill`/`radius-sheet`/`radius-card`, and `motion`. It is emitted as `--theme-*` in the same inline `<style>` block.

Colour is **semantic roles**, not palette keys. No rule in `www/style.css` names a `--color-*` any more; every one reads a role, and the role definitions in `:root` are the only place the palette is touched (`ThemingTest::testNoRuleInTheStylesheetNamesAPaletteKey` enforces exactly that). The rule that keeps the system honest is **one colour, one role** — if an event's lime is `state`, lime is not also a ground, a surface or a piece of chrome. The set is sized for a 60:30:10 budget: `ground`/`on-ground` with `surface`/`on-surface` as its one block tier (60), `structure`/`on-structure` for the bars, the sheet, the buttons and the timeline's cards (30), and `action`/`on-action`/`action-link` plus `tonal`/`on-tonal` and `state`/`on-state` sharing the 10, with `edge`, `edge-width`, `heading`, `emphasis` and `scrim` in support. `structure` defaults to `--color-darker` rather than `--color-base`: it is the one role that is a filled ground under inverted type at body size, and obrok19's base carries `--color-text-invert` at 3.85:1 where its darker green reaches 6.84:1. Three scopes **rebind** the core roles rather than adding names: a text field, `.sheet-card` and `.tl-scroll` are each their own little surface with their own structure on it, so the grid's cards are simply `structure` in the grid's scope. The rebinding sits on `.tl-scroll` and not on `.pg` because custom properties inherit — on `.pg` it would also reach the pager, the day panel and the view tabs.

**Light mode is light and dark mode is dark, all the way through.** `structure` grounds every bar, sheet and card, so in a light set it is the palest thing on the screen and in a dark set the darkest; a filled near-black app bar in light mode is the "black element in the light mode" the system exists to prevent, and a lifted mid-grey card at night is the same mistake upside down (`ThemingTest::testTheLargeFilledAreasFollowTheMode` measures the relative luminance of every role that names a large fill and holds each mode to its own end of the ramp). Two things follow. First, an accent can only be **ink or a small area filled under dark ink**, never a large fill: obrok27's lime is 1.25:1 on a pale ground and obrok19's `#2a9272` is 3.49:1, so the **active tab is filled with the event's colour and carries `on-state`** (13.4:1 and 4.8:1 under near-black ink) rather than tinted type — the fill is the whole tab, not a chip behind the glyph, because tinted type at those ratios is the regression this rule exists to prevent — and `state` has one shape in both modes; the **app bar is the one other surface filled with `state`**, and everything on it — title, profile link, mode toggle — therefore takes `on-state` too, because that fill does not flip with the mode while `on-structure` does (it used to take `on-structure`, which put obrok27's pale dark-mode ink on lime at 1.12:1 and obrok19's body grey on green at 2.56:1); a secondary `.btn`, a `.highlight` link CTA, a `.notice` and the active day are **`tonal`** — the accent washed almost all the way into the ground, carrying the accent itself at full strength as ink. `.btn-primary` is unchanged in kind, a filled accent under inverted ink. Second, separation cannot come from a tone step alone, because content scrolls under a bar of very nearly its own colour, so **every bar, sheet and card also carries a hairline, in both modes** — `--edge-width`, still 0 for an event that declares nothing. Light hairlines are neutral and dark ones keep the accent tint; each clears 3:1 against both sides of itself, which is what the 1px content-block outlines replaced the old 4px frames for.

One role sits beside `structure` rather than inside it: `signature`/`on-signature`, **structure that carries the identity**. It behaves like structure — a filled band of chrome with type on it — but its value is a quiet cast of the event's own colour, and the **hour ruler is its only use in the app**; painting a second surface with it would return the screen to the state where nothing could read as an accent (`ThemingTest::testTheIdentityRoleIsUsedByTheHourRulerAndNothingElse` holds it to one). It is deliberately *not* the accent at full strength: a saturated slab is the loudest thing on a light screen and a lit panel at night, and the ruler is chrome. The stage column has its own pair (`stage`/`on-stage`) in the grid's scope because the card and the column want different tones out of the same tier — the card separates from the grid by a step plus its hairline, the column is a band behind bold names — but its value is a **plain neutral in both modes**; the lime cast round 9 gave it is withdrawn, because a hue on the largest block of the screen is how accents stop reading. Both pairs fall back to the grid's own `structure`, so an event that declares neither renders exactly as it did.

Every role falls back to exactly the expression its rules used before roles existed, and those **built-in fallbacks are frozen** — they are the pre-round-10 look, dark chrome and all, and the fixture events under `tests/fixtures/events/` are what still exercise them (`testEveryRoleFallsBackToThePalette`, `testStructureDefaultsToThePalettesDeeperTone`). No shipped event uses them: **obrok19 hand-authors a `light` set of its own** and is no longer the frozen control — its bars are white, its green is the `state` chip and the registered fill, its red is `action`, and `docs/baseline/obrok19/` was re-taken at the end of round 10, so a diff against it is still how a round shows it disturbed nothing. obrok19 stays **light-only**: no `dark` set, no toggle. An event that wants its own colours declares `roles` as two **hand-authored** sets, `light` and `dark` (`EventConfig::$roles`) — accents do not survive mechanical inversion, so changing a colour is deliberately a two-place edit. `_layout.twig` emits light as the base, then the dark set twice: once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-mode="light"])` so the device's setting works without JS, and once under `:root[data-mode="dark"]` so an explicit choice wins. A tiny **inline script in `<head>`**, before the stylesheet link, sets `data-mode` from `localStorage['obrokColorMode']` (global, not per event) or from `prefers-color-scheme` — never the deferred script at the foot of the page, or the reader sees a frame of the wrong theme. A sun/moon `<button>` in the app bar flips it, and appears only for an event that declares a dark set.

Colour reaches the **assets** too, because a bar that follows the mode cannot carry one fixed drawing. `assets.menuLogo` is the tab-bar mark and `menuLogoDark` its dark-mode twin (`.mode-light-only`/`.mode-dark-only` swap them; obrok27 is purple by day and lime at night), while `menuLogoOnState` is the drawing for a surface filled with `state` — that fill is the event's own colour, so a mark in that same colour disappears on it. Which drawing goes where follows from what the surface is filled with, and **the tab bar and the app bar are not the same kind of surface**: the tab bar is `structure` and flips with the mode, so it takes the mode pair, but the app bar is `state` and does not, so it takes `menuLogoOnState` exactly as the active tab does. Giving the app bar the mode pair is what put obrok27's lime ghost on lime and left the mark invisible at night. Each asset is optional and the classes are only emitted when the second drawing exists, so an event with one logo keeps showing it everywhere. `mainLogo`/`mainLogoDark` do the same job on the homepage.

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link) and a fixed bottom tab bar built from the enabled features and sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Login lives on `/profil` (core routes, not a module) and the app bar reads the current identity through the `auth_identity()` Twig function rather than a global, because a handler can log the user out during the same request that renders the bar.

Switching screens does not load a document. `<main>` is a **stack of screens** — `<section class="screen" data-screen data-title data-doc-title data-tab tabindex="-1">`, emitted identically by `_layout.twig` (the first one, server-rendered) and by `_screen.twig` (every one after it). A request carrying `X-Screen: 1` gets the second parent: every participating template picks its own with `{% extends fragment ? '_screen.twig' : '_layout.twig' %}`, against a Twig global that `Kernel`'s screen middleware sets per request. Next to it the middleware sets `screenPath`, which exists because slim/twig-view resolves `get_uri()`'s runtime exactly once and then keeps it for the life of the `App` — the path would be stale from the second request on, which no single-request web server notices and every test does. A plain request stays byte-identical to what it was, which is what keeps deep links, crawlers, the back button against a cold cache and a reader with JS off working, and `Vary: X-Screen` keeps the two responses apart in anything that caches them.

`www/app.js` fetches a screen **once**, inserts it hidden, and from then on navigation is show/hide. Nothing is ever removed, so state is *live* rather than restored: the map's Google iframe keeps running, the timeline keeps its zoom *and* its horizontal scroll, a half-typed TIE code stays typed. Hidden and not detached is the whole point — re-inserting a detached `<iframe>` re-fetches it, which is also why neither `hx-preserve` nor `data-turbo-permanent` could have done this: both persist a node present in *both* documents, and the map exists on one screen only. Order matters, **insert → show → init**: the ruler's label-width measurement and every `scrollLeft` calculation return 0 inside a `hidden` subtree. Showing a cached screen is instant, always; one fetched more than five minutes ago is revalidated in the background, and a screen whose HTML has actually changed is **morphed** into the new one rather than replaced — `innerHTML` would throw away the very state the cache exists to keep. The morph is hand-rolled and small (no diffing library, and deliberately not a vendored Idiomorph): children match on `id`, then `data-key`, then position among same-tag siblings; a subtree already equal to its counterpart is skipped outright; a matched `<iframe>` is never written to *and never moved*, because a move re-inserts it and a re-inserted iframe reloads. It writes only the attributes the fresh markup states — one it does not carry at all belongs to the client (`--hour-width` lives in `.pg`'s `style`, `data-hour-step`, `data-pg-ready`, `disabled`) — and one the markup names in **`data-morph-keep`**, for the attributes the server writes without owning: `.pg`'s `data-view`, `.tl-page`'s `class`. Without that the screen would be put back on the server's default view and page, and a layout landing in the gap before the screen restores itself would take the reader's scroll with it. What the screen does own it puts back on a `screen:morphed` event, dispatched synchronously in the same task. A morph, like a replacement before it, never happens while the reader is in the middle of a screen — an open sheet, an open day panel or focus in a form field defer it to the next time that screen is shown, and it then runs *after* the screen is visible again, for the same reason the wiring does. Measured on the Program screen: a revalidation that finds no change touches **zero** nodes; one that finds a renamed, re-timed programme touches seven, on a screen holding sixty cards. Screens slide **by tab order** through the View Transitions API: the loader only sets `data-nav` on the root and the animations live in `www/style.css`'s one reduced-motion block, so where the API is missing — or reduced motion is asked for — the swap is instant rather than animated by hand. There is deliberately **no swipe gesture**: a horizontal drag on the timeline means "scroll the hours".

A response that is not a 200 is not a screen: the loader falls back to a plain navigation, so the reader gets the server's own error page instead of an app bar injected into a `<section>`. The participating set is read off the rendered shell — the tab bar's own links plus the profile one, in that order, which is what makes `/profil` count as forward — so it is the five tab destinations and `/profil` and nothing else. The handbook PDF, external links, `/admin/notify` and **every non-GET** stay plain navigations, so logging in reloads the document and empties the cache with it; that is the correctness rule rather than laziness, because login changes both the app bar identity and the registered marking on every programme. Every link stays a real `<a href>` and the loader is an enhancement layer, not a client router: with `www/app.js` absent the app behaves exactly as it did.

Two rules the shell depends on. `<main>` must **never** carry a `view-transition-name`, however natural it looks: naming an element makes it a stacking context, and the sheet and the day panel are fixed children of `<main>` that have to keep painting over the fixed tab bar. Only `.appbar` and `.tabbar` are named, which takes them *out* of the root snapshot so the shell sits still while the screen under it slides. And the per-screen layout rules key off the section (`.screen[data-tab="map"]`, `"programs"`, `"homepage"`) rather than the old `body.screen-*` classes, with `main > .screen[hidden]` restating `display: none` loudly enough to out-specify them.

`ProgramsModule` (`/programy`) is the single Program screen. Its behaviour is `www/programs.js`, not an inline `<script>`: it used to sit in `{% block header %}`, i.e. in `<head>`, which no screen swap can reach. The file exposes one idempotent `window.pgInit(scope)`; the shell loads it for any event carrying the `programs` feature, the loader calls it by dispatching `screen:shown` on the section it has just made visible, and a server-rendered Program screen wires itself on `DOMContentLoaded` so the screen keeps working even if the loader never runs. The hand-authored schedule (`content/schedule.php`) and the separate harmonogram screen are gone: everything the screen shows comes from `ProgramProviderInterface`. When a participant is logged in, the module also calls `getProgramsForIdentity()` and marks their programs `registered` — that marking is the only thing login affects, so keep it working when the screen changes. The API is expected to grow to carry the non-registerable items too (budíček, nástupy, táborák), which is what the old schedule file used to hold.

The screen holds two views of that one data set, built from the Figma flows *Registrace programů* and *Burza (Var. 2)*, and a floating pill above the tab bar switches between them client-side. **Timeline** is a Gantt grid: rows are the distinct `location` values (`location` is reused as the stage axis — the contract has no `stage` field, and programs with a null location fall into a `Bez lokace` row), columns are hours, one page per **day** holds every section's programmes (key `page-YYYYMMDD`), and it is the one place in the app allowed to scroll horizontally. Overlapping programs in one location are packed into sub-tracks by a greedy interval fit. A programme that runs over several days sits on the page of **every calendar day it overlaps**, each piece clipped to its day (`ProgramsModule::segments()`, at most `MAX_DRAWN_DAYS`), so no piece can stretch a day's axis; an end at exactly 00:00 belongs to the day before, so 23:45–00:00 stays one card on its evening. Every piece carries the programme id as its `data-key` — unique among siblings, which is all the morph matches on, because a page holds one piece per programme — opens the one sheet, and has the same registered state and label; a label names both days whenever the run spans more than one. The sheet, and with it the deep link, belongs to the start day's page, and Můj program lists the programme once, under that day. The hour scale is zoomable: everything on the grid is positioned as `calc(var(--hour-width) * n)`, so setting that one property rescales the time axis and nothing else — never `transform: scaleX()`, which would distort the programme names. `--hour-width` runs between `--hour-width-min` and `--hour-width-max` (40–200px, declared in `www/style.css` next to the property), opens at 80px, and is driven by a −/+ pair at the right end of the timeline's pager row, by a two-finger pinch on the grid (`touch-action: pan-x pan-y` on `.tl-scroll` keeps the browser's own pinch out of it; the viewport meta is deliberately left alone so page zoom still works everywhere) and by ctrl+wheel. Every step recomputes `scrollLeft` so the moment under the anchor — the midpoint between the fingers, or the centre of the visible grid for a button — stays put. The scale is kept in `sessionStorage` under `pgZoom:<slug>`, so paging and view switching preserve it and a fresh visit starts at 80px. Below a threshold the ruler thins its text to every second hour while every hour keeps its mark — the script sets `data-hour-step` on the root from the live scale and `www/style.css` hides `.tl-tick:nth-child(even) .tl-tick-label`, so tick positions never move and the leftmost hour is never blanked. The threshold is the rendered label's width plus 19px, measured on the page rather than hardcoded because themix and Montserrat differ by 6px at 14px/700. **Můj program** is a plain list of `getProgramsForIdentity()` only, grouped by **day**, like the timeline — `ProgramsModule::buildDays()` is the one that does it. It does not page at all: every day is in the document, first to last, under its own **sticky heading**, and the reader scrolls the lot. Only that view's strip changed shape — the timeline keeps its `‹ ›` and its zoom pair, and the two strips are separate elements. The list's is an **orientation instrument**: its label names the day being read rather than a page being shown, `↑` goes to the start of the day being read and only then to the day before it (the rule a music player's "previous track" uses) while `↓` goes to the next day's start, both smooth-scrolled unless reduced motion is asked for, and both disabled at their end of the list; tapping the label still opens the day menu, which now scrolls instead of switching. Nothing of this runs on a scroll event: an `IntersectionObserver` watches the day sections against a band starting one pixel below the strip — one pixel, because a day scrolled to its own start puts its top edge and the previous day's bottom edge on the same line and an observer asked about that line answers "both" — and each crossing costs one coalesced `requestAnimationFrame` that reads no geometry. The day owning the top of that band is the day whose heading is stuck there, so the strip and the heading cannot disagree — which holds only because `.pl-head`'s dock line, `bandTop()` and the observer's `rootMargin` all read the **same three tokens**, `--appbar-height` + `--appbar-inset` + `--pager-height`. Leaving the safe-area inset out of any one of them docks the heading behind the strip on a notched install (34px, measured). The observer fixes its margin at creation, so an inset that changed at runtime would leave the band stale until it is rebuilt; nothing does that yet. `.pl-day:last-child` carries a `min-height` of the reading band, or the last day could never dock under the strip and `↓` would land short of it. The screen's scroll offset is live state like everything else, so leaving Můj program and coming back lands where the reader was; switching to the timeline and back does too, because that view is exactly one screenful and the browser clamps the window's scroll while it is up, so `showView` saves and restores it. When a participant is logged in, programs they are not registered for are dimmed with `opacity` — never a colour, because `www/style.css` may not name one; logged out nothing is dimmed, since "not chosen" would be a lie. A perex is plain text whose `\n`s are meant (`docs/kissj-contract.md`), so `.sheet-perex` and `.pl-perex` are `white-space: pre-line` and the template puts nothing but the escaped text inside them. Tapping a program opens a modal, and the `#section-<id>-program-<id>` deep link opens the right one, puts the timeline on its page, and parks the personal list on that programme for when the reader switches to it. An open `.sheet` or `.pager-menu` is a real dialog: everything outside it goes `inert` — the app bar, the tab bar, the skip link, the sibling screens — and Tab rings inside the card, because a modal a reader can tab straight out of is not one. The trap remembers exactly which elements it marked, so closing clears its own and nothing else, and it releases *before* the focus returns to the opener, since an inert element cannot take focus. Everything is read-only: the screen never registers anybody for anything, which is why the Figma heart/favourite component is deliberately absent, along with its photo, capacity and attendee-count fields. `ProgramsModule` does all the grouping in PHP and hands Twig a finished view model; every page is rendered into the DOM so the `#section-<id>-program-<id>` deep link can open a modal on any of them.
