# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Modular support web app for Czech scout events (Obrok). Built on Slim 4 (PHP >= 8.3). One codebase serves multiple events — each event is a config + content directory under `events/<slug>/` plus public assets under `www/events/<slug>/`, selected at runtime by the first path segment: every event lives under `/{slug}/`, and `/` is a picker of the listed ones. Code is in English — comments, docblocks, exception messages, identifiers. Czech is reserved for what users actually read: UI strings in `templates/`, per-event content under `events/<slug>/content/`, user-facing notices, toasts and flash messages, and the weekday names in `HomeModel`, `NewsItems`, `ProgramsModule` and `www/shell.js`. Every surface a reader sees addresses them as *ty*: templates, notices and toasts, push status lines, ARIA labels, `<title>`s. UI strings spell the registration system **KissJ**, and the organisers' messages are **notifikace**, never novinky (the Informace heading, Domů's `Starší notifikace`, the manifest shortcut). The admin page is for organisers and stays neutral and imperative, and per-event content is the organisers' own text. Commit messages and `docs/` are in English without AI-authorship trailers (the existing `docs/kissj-contract.md` predates this and is still Czech).

## Commands

- `docker-compose up` — run the dev server (PHP built-in server inside `php:8.3-alpine`, with `bin/router.php` and `PHP_CLI_SERVER_WORKERS=4`: one worker queued a page behind the service worker's install burst and the loader's warm-up long enough for the worker's 3 s cached-copy fallback), then visit `localhost:8080`
- `composer start` — alternative: run locally via `php -S localhost:8080 -t www/ bin/router.php`. The router is not optional: without it the built-in server 404s any missing path with a dot in it (`/<slug>/precache.json`) before PHP runs
- `composer test` / `vendor/bin/phpunit` — run tests (PHPUnit 11, config in `phpunit.xml`, suites `unit`, `functional`, `browser`). Without a Chrome every `browser`-group test skips itself ("OK, but some tests were skipped!"); CI sets `PANTHER_NO_SKIP=1`, where that is a failure
- `vendor/bin/phpunit --exclude-group browser` — the fast run, no Chrome tests. There is no host PHP: run it as `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine vendor/bin/phpunit --exclude-group browser` and again with `php:8.5-alpine` — 8.3 is the lowest supported PHP and 8.5 is what CI and production run (`.github/php-version`, read by every workflow; `deploy.yml` deploys every push to `master` over FTP once `ci.yml` passes, see `docs/deployment.md`). The fast run keeps the local source's state in temp directories of its own; a `var/stub` it leaves behind is a bug
- `docker compose --profile browser run --rm --use-aliases test vendor/bin/phpunit --group browser` — the Chrome tests: `symfony/panther` drives `selenium/standalone-chrome` (the `chrome` service), and the test case serves the app itself from the `test` container (`--use-aliases` makes it reachable as `test`). `docker compose --profile browser stop chrome` afterwards, and `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine sh -c 'rm -rf var/twig/* var/sessions var/cache var/stub'`, because the `test` service runs as root. There is no Node anywhere
- `vendor/bin/phpunit --filter testGetHomepage` — run a single test
- `docker run -d --name eventapp-korbo --rm -p 8081:8080 -v "$PWD":/app -w /app -e PROGRAM_PROVIDER_KORBO26=local -e APP_DEBUG=1 php:8.3-alpine php -S 0.0.0.0:8080 -t www/ bin/router.php` — serve the `korbo26` dev event (the realistic Korbo camp data from its local fixture files) on `localhost:8081/korbo26/programy`; the `-e` values override `.env`. On Profil, `Přihlásit kódem z KissJ` pairs at once (the `local` source approves the first poll) as the fixture participant 1, Jana Nováková, registered for 6 programmes; korbo26's registration window is open (2020–2099), so the sheet registers and unregisters. Those writes land in `var/stub/korbo26.json`; delete it to get the fixtures' registrations back
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine sh -c 'apk add --no-cache libpng-dev >/dev/null && docker-php-ext-install gd >/dev/null && php bin/event-icons.php <slug> <source.png> <#background>'` — regenerate an event's favicons, apple-touch icon and manifest icons from one drawing (GD is installed on the fly, the stock image lacks it); it prints the `assets.favicon16`/`favicon32`/`appleTouch` lines for the config, and files it wrote as root need a `chown` afterwards
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/kissj-fixtures.php <slug> [--clamp-all-day=HH:MM-HH:MM]` — regenerate `events/<slug>/fixtures/` from `tests/fixtures/kissj/<slug>/` (`programme-list.json`, `participant.json`) through the real `KissjProgramProvider` mapping: `programs.json`, `sections.json`, `registered.json` (the fixture participant's programmes, keyed by their kissj participant id) and `registration.json` (the list's window, removed when it has none); `--clamp-all-day` narrows programmes that kissj stores as whole-day runs to the given window
- `docker compose --profile browser run --rm --use-aliases test php bin/baseline.php` — re-take `docs/baseline/obrok19/*.png` (the four obrok19 screens `home`, `informace`, `profil`, `programy` at 390 × 844 through the local provider, in the browser tests' own server and Chrome, the install button hidden). obrok19 has no `dates`, so Domů shows the date heading of the day it is shot: two runs on the same day give byte-identical PNGs, two on different days differ there. `docker compose --profile browser stop chrome` afterwards; with a local chromedriver, `php bin/baseline.php`
- Local only, not in the repo (`.gitignore`): the mock events' source material under `docs/` and the two converters that read it, with their tests. Only the JSON they produced is committed, so the two commands below work only on a machine that still has those files.
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/obrok-harmonogram.php "docs/Harmonogram celé akce.xlsx"` — convert the organisers' harmonogram spreadsheet into `tests/fixtures/kissj/obrok27/`; then run `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/kissj-fixtures.php obrok27` to regenerate the served `events/obrok27/fixtures/` from it
- `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/miquik-rozvrh.php "docs/MQ-Přednášky - data.xlsx"` — convert Miquik's lecture workbook (the `Rozvrh` room grid joined to the speakers' form answers) into `tests/fixtures/kissj/miquik26/`; then `bin/kissj-fixtures.php miquik26`. The workbook has no date, so every talk sits on the invented `MiquikRozvrh::DATE`

Before running, copy `.env.example` to `.env`, set `APP_DEBUG=1` for dev, keep a `PROGRAM_PROVIDER_<SLUG>` line for every event (`.env.example` sets all five to `local`) and fill in a VAPID pair — `docker run --rm -v "$PWD":/app -w /app php:8.3-alpine php bin/generate-vapid.php` prints the two lines; every event has push, and a push event refuses to boot without valid keys (tests generate their own per run in `tests/bootstrap.php`). There is no event to choose, the URL does (`localhost:8080/obrok19/`, the reference event).

Five events ship: `obrok19` (the reference), `obrok27` (19.-23. 5. 2027, the official brand kit), `korbo26` (the former `korbo`), `navigamus25` and `miquik26` (unlisted: its lecture data is in, its date is invented). obrok19 and obrok27 enable `map`, `programs`, `handbook`, `info` and `push`; korbo26, navigamus25 and miquik26 enable `programs`, `push` and `info`. Two of them are **unlisted**, i.e. absent from the picker but reachable by URL: `miquik26` and `obrok19`, neither of which has a `listed` key at all, so both default to unlisted (obrok19 is served at `/obrok19/`). **korbo26, navigamus25 and miquik26 wear kissj's design**, adjusted to eventApp's contrast rules. A slug matches `/^[a-z0-9-]+$/` and ends in a two-digit year. Every event's fixtures know one participant, kissj's participant id `1` (`registered.json`: korbo26 6 programmes, obrok19 and obrok27 8, miquik26 5, navigamus25 2); only korbo26 names them in `participants.json` (`Jana Nováková`), so elsewhere the paired reader is `Účastník`. Registration windows (`registration.json`): korbo26 open 2020–2099, obrok27 from 15. 3. 2027 18:00 to the event's start; the others have none. An event's `config.php` may also carry `listed` and `dates` (`start`/`end`), which the picker uses to split upcoming from past and Domů uses for its phases; the three listed events carry both, while `miquik26` and `obrok19` carry neither. The optional `website` (an absolute http(s) URL, validated at load; obrok27: `https://obrok.skaut.cz/`) is what a logged-out Profil's "web akce" link opens.

## Architecture

`www/index.php` is a 3-line front controller: it requires the Composer autoloader and calls `App\Kernel::boot($_SERVER['REQUEST_URI'] ?? '/')->run()`, which picks the event from the first path segment (see `Kernel::boot()` below). All bootstrap logic lives in `src/Kernel.php` — no `settings.php`/`dependencies.php`/`middleware.php`/`routes.php` split, no route closures scattered across a routes file.

`Kernel::boot($_SERVER['REQUEST_URI'])` loads `.env` (if present) and looks at the first path segment: if `EventCatalog` knows it, `Kernel::create()` builds the app for that event; otherwise `Kernel::createInstance()` builds the instance-level app that serves the picker at `/` and Slim's 404 for the rest. Nothing is configured per deployment about which event is served. Env vars are per event where they are secrets or choices of an event — `<NAME>_<SLUG>` with the slug upper-cased and `-` turned into `_` (`PROGRAM_PROVIDER_OBROK27`, `KISSJ_API_KEY_OBROK27`, `ADMIN_TOKEN_OBROK27`), read through `EventConfig::env()` (which falls back from `$_ENV` to `getenv`, because php-fpm may leave `$_ENV` empty); `APP_DEBUG`, `PROGRAM_CACHE_TTL`, `VAPID_*`, `PUSH_DB_PATH`, `SESSION_PATH` (`Kernel::sessionPath()`, default `var/sessions`, relative paths against the project root like `PUSH_DB_PATH`; the browser tests point it at a temp dir), `STUB_STATE_PATH` (`Kernel::stubStatePath()`, default `var/stub`, resolved the same way; every test points it at a temp dir), `PUSH_ENDPOINT_HOSTS`, `TRUSTED_PROXY_COUNT`, `TRUSTED_PROXIES`, `SENTRY_DSN`, `SENTRY_TRACES_SAMPLE_RATE` (`.env.example`: 0.05), `SENTRY_PROFILES_SAMPLE_RATE` and `APP_RELEASE` are instance-wide and read from `$_ENV` (`TRUSTED_PROXIES` falls back to `getenv`). There is no instance-wide kissj URL. The reader's address is `Http\ClientIp::of()`: `X-Forwarded-For` is read, `TRUSTED_PROXY_COUNT` hops from its right end, only when the connection comes from a loopback or private address (an IPv4-mapped one judged as its IPv4) or from one `TRUSTED_PROXIES` names (comma-separated addresses or CIDRs, a malformed entry skipped; only the immediate peer is matched, the inner hops are trusted by the count); otherwise it is `REMOTE_ADDR`. Both limits — the pairing start's and the push subscribe one — count by `ClientIp::throttleKey()`, which is that address for IPv4 and its /64 for IPv6, with `::ffff:` unwrapped. A 404 or 405 is not logged (`src/QuietErrorHandler.php`), and `Kernel::TIMEZONE` is `Europe/Prague`.

Observability is Sentry, wired like kissj's. `Telemetry\Telemetry::init()` runs in `boot()` only, right after `.env` — tests build apps through `Kernel::create()`, so no test ever binds a client, and `phpunit.xml` forces `SENTRY_DSN` empty for the few that call `boot()`. It also sets `zend.exception_ignore_args` on, whatever the host's ini says, so a session token or a device code passed as an argument never lands in a trace. With an empty `SENTRY_DSN` every piece below is a no-op. `Telemetry\Collector::collect()` files an exception (`QuietErrorHandler` calls it for everything but a 404/405), `Telemetry\Tracer::span($op, $description, $fn, $data)` wraps a child span (`kissj.list`, `kissj.session`, `kissj.programme-participants`, `kissj.pairing-start`, `kissj.pairing-poll`, `kissj.register`, `kissj.unregister`, `kissj.revoke`, `program.cache`, `push.send`, `push.welcome`, `push.subscribe`, `push.unsubscribe`, `auth.pairing`) whose failure status comes from the HTTP answer when there is one (`Tracer::statusFor()`: kissj's 401 for a device session that is no longer valid is `unauthenticated`, not `internal_error`, and so is the `Program\SessionExpiredException` made from it) and whose `$data` becomes span data — a `Tracer::FROM_RESULT` closure adds data computed from the result; `Tracer::spanTag()` instead tags the running span, and `Tracer::tag()` the transaction (`event`, and the pairing routes' `pairing_outcome`: `rate_limited`, `started`, `provider_failed`, `approved`, `denied`, `expired`). The push counters `push.outcome` (on `push.welcome`), `push.target` (on `push.send`), `push.new` (on `push.subscribe`) and `push.found` (on `push.unsubscribe`) are span tags, while the cache outcome `cache.result` (`hit`, `miss`, `stale`, `locked` for an expired entry served while another request refetches it, or `bypass` for the uncached programme-participants call) with `cache.age`, and the send counts `push.recipients`, `push.sent`, `push.removed` and `push.failed` (refused other than 404/410, or thrown), are span data — none of them is an issue. `TransactionMiddleware` opens one transaction per request and `RouteNameMiddleware` names it by route pattern (`POST /admin/notify/{id:[0-9]+}/hidden`) and tags the event; a request no route matched (a 404 or 405) keeps the fixed name `unmatched` (`TransactionMiddleware::UNMATCHED`), and the instance app names its routes too (`RouteNameMiddleware(null)`, which tags no event). `Telemetry\Scrubber` strips the `token` query parameter, a `token` body field, a whole `/push/subscribe` or `/push/unsubscribe` body, a whole `/admin/notify` form body, the `Authorization`/`Cookie` headers and every stack frame's vars before anything leaves; exception messages are left alone, so none may carry a secret (`SessionExpiredException` says just `Device session is no longer valid` and chains nothing, `RegistrationRefusedException` names only kissj's refusal code, and any other failed kissj call is rethrown as `Program\KissjTransferException` — a `TransferException` that names the endpoint in words, never the URI, and chains nothing either). There are two Monolog loggers: `Psr\Log\LoggerInterface` (`eventapp`: stdout from info up, a Sentry issue from warning up through `LogToSentryIssueHandler`) and `Kernel::ERRORS_LOGGER` (`errors`: stdout only, for the error handler, so an exception is not filed twice); the app log lines are `push.sent` (info) and, from `WebPushSender`, one `push.failed` warning per batch with failures — counts only, filed in Sentry as an issue; a throwable the sender swallows goes to `Collector::collect()`. `GET /health` on the instance app opens the push database, runs `SELECT 1` and answers `200 {"ok":true}` or `503 {"ok":false}` — no migration, no log, no Sentry. The SDK's default integrations stay on, as in kissj (`Telemetry::options()`), so PHP warnings and deprecations reach Sentry as events too. The one routine message, web-push's "GMP or BCMath" advice, is no longer a PHP notice: `WebPushSender::webPush()` hands the library (`minishlink/web-push` ~10.1.0, which also cleared its PHP 8.5 deprecation and requires `ext-mbstring`) the app logger wrapped in `Push\PlatformAdviceFilter`, which drops that one line and passes every real platform warning through.

`Kernel::create()`:
- Calls `Kernel::programSource()` first (see the provider below), then builds a PHP-DI container (`ContainerBuilder`) with the event, the program provider, `Session`, `Auth\Authenticator`, `Auth\PairingThrottle` and Twig as definitions.
- Creates the Slim 4 `App`, adds body-parsing/routing middleware, Twig middleware, and error middleware (`APP_DEBUG` controls whether error details are shown), and then the session-cookie and screen middleware, *outside* the error middleware rather than inside it; the security headers, `Http\CspMiddleware` and `Telemetry\TransactionMiddleware` now wrap it in turn (the next bullet has the full order). A thrown 404 or 500 is answered by the error middleware without ever reaching the route, so a `Vary: X-Screen` set further in would be missing from exactly the responses a shared cache is most likely to keep.
- The middleware stack, innermost to outermost: body parsing, routing (with `Telemetry\RouteNameMiddleware` added before it, i.e. inside it, so the route is known), Twig, error, session cookie (`addSessionCookieMiddleware()`: a `GET` answered 200 with a full HTML page, not a fragment, for a logged-in reader calls `Session::refreshCookie()`), screen (which also sets `Cache-Control: Kernel::PAGE_CACHE_CONTROL`, `no-store, no-cache, must-revalidate`, on every HTML page and fragment that states no policy of its own, cookie or not), security headers (each set only if the response has none, which is how the admin routes keep `Referrer-Policy: no-referrer`), `Http\CspMiddleware`, and `Telemetry\TransactionMiddleware` last — outermost, so the error middleware's 500 is measured. `createInstance()` has the same order without the Twig, session-cookie and screen layers (its route naming is `RouteNameMiddleware(null)`).
- Registers core routes directly — `GET /<slug>/` (Domů), `GET /profil`, the pairing routes `POST /profil/propojit`, `GET /profil/propojit/stav` and `POST /profil/odpojit` (below), the offline page `/offline` and the worker's `/precache.json` — then iterates `$event->features` and registers one module per enabled feature.

`EventConfig` (`src/EventConfig.php`) loads and validates `events/<slug>/config.php` (requires `name`, `colors`, `features`; refuses an event that enables `info` without `push`, because Informace lists the sent notifications; validates `dates`, `website` and `csp`; also carries arbitrary `raw` data via `get()`, and `dir` for locating fixtures/content). `EventConfig::content(string $name)` loads `events/<slug>/content/<name>.php`, a plain PHP file returning an array — these are per-event, not code. `content/links.php` is Informace's `Rychlé odkazy`: a `<ul class="link-list">` of `.link-card`s (the handbook first and tonal, a `highlight` entry tonal too, an optional `note` as a second line, an outward mark on absolute URLs, which open in a new tab — `target="_blank" rel="noopener"`, as do Domů's external `highlight` CTAs and its footer link), while Domů shows only the `highlight` ones as `.highlight` CTAs. `content/emergency.php` (`contacts`: `label`, `phone`, optional `note`; `info`: lines) is Informace's crisis contact (`Krizový kontakt akce`, each contact with a `Zavolat` button that is a `tel:` link, spaces stripped, so it dials from the worker's offline copy); an event without the file shows none; obrok27 carries the real crisis line `+420 704 444 015`.

**Domů** (`GET /`, `templates/homepage.twig`) is built by `Home\HomeModel::build()` from the event's `dates`, read on the Prague calendar: `phase` is `before`, `during` or `after` (`null` for an event without dates, rendered as during). Logged out, in every phase, a `.pair-card` at the top (`Už jsi registrovaný na <event>?` … `Přihlásit se`, linking to Profil). **Before the start**: the install card, then `Co tě čeká` — a window card driven by the provider's `getRegistrationWindow()` (`Přihlašování na programy` with the opening date and time before the window, `Výběr programů` / `Do <end date>` while it is open, with a `Vybrat programy` button when paired and the line `Výběr programů je otevřený. Programy si můžeš prohlédnout v sekci Program.` when not; none without a window) and the countdown `Potkáme se už za N dní` with the event's range (`HomeModel::range()`, `19.–23. 5. 2027`). **From the start** (and after the end): the date heading (`Pátek 21. 5.`, `data-home-date`), today's notifications as full `.news` cards (`NewsItems::today()`, the same markup as Informace; which ones count as today's stays the server's choice), a `Starší notifikace` link to Informace, then `Můj program` (`<section class="next-up" data-next-up>`, `HomeModel`'s `nextUp`, built on `ProgramsModule::nextUp()`): every programme of the participant is a hidden `.link-card.is-highlight.next-card` with `data-start`/`data-end` instants, `data-time`/`data-until` (written as `ProgramsModule::CLOCK`, `9:00`/`do 12:30`) and `data-location`, plus the section's title as a third line; the server hides the box when everything is over, and `www/shell.js` shows the running one and the next two by the device clock, each with its lead line (`Právě · do 12:30 · Žlutý les`, `Za 25 min · 14:00 · Modrý les` within the hour, else `14:00 · Modrý les`); then the install card. Before the start nothing personal is read; from it the participant's programmes, the sections and the messages are read best effort — a `SessionExpiredException` logs the reader out and this very page carries the toast that says why, an outage just leaves its part out. Each card links to `programy#muj-program-<id>`, which `programs.js` opens as Moje scrolled to that programme with its sheet open, and carries `data-deep-link`, which tells `app.js` to keep that cross-screen hash link inside the app (push the entry with its hash, `go()`, and dispatch `hashchange` when the screen was already loaded) instead of a plain navigation. The highlight links and the colophon close the screen. The emergency box is not on Domů any more; it is Informace's crisis contact.

**The install card** (`templates/_install.twig`, on Domů as `installCard: 'home'` and on Profil as `'profile'`) puts the install offer and the notifications button under one heading (`Ulož si <event> na plochu`, then `Zapni si upozornění, ať ti neuteče výběr programů, novinky a varování v průběhu akce.`): the hidden `Uložit jako aplikaci` button (`.install[data-install]`, `.install-btn`), the iOS hint (`[data-install-ios]`), and, for a push event, the `Povolit notifikace` button (`data-push-toggle`) with its `.push-status` line. In an installed app Domů hides the whole card (`data-install-card="home"`) and Profil only the install half.

Modules implement `App\Module\ModuleInterface` (`key()`, `menuItem()`, `registerRoutes()`) and live in `src/Module/`. `ModuleRegistry::classFor($feature)` maps a feature-flag string (from the event's `features` array in its config) to a module class — this is how features are toggled per event: `info` (`InfoModule`), `map` (`MapModule`), `handbook` (`HandbookModule`, no tab of its own: the handbook is the first of Informace's quick links), `programs` (`ProgramsModule`) and `push` (`PushModule`). The tab bar is Domů (the event's `shortName` with its `menuLogo`, or the `fa-home` icon) followed by the enabled modules' items in their `order`: Program (10), Místa (20), Informace (30). `PushModule` (web push notifications) is implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and `GET/POST /admin/notify` sends notifications — the shared link `?token=<ADMIN_TOKEN_<SLUG>>` logs the browser in for 24 hours (session key `admin` = `['since' => int]`) and redirects to the bare URL; the pages after it carry no token and the forms carry a CSRF field (`csrf`), and every admin response is `Cache-Control: no-store` and `Referrer-Policy: no-referrer` — the error page of an exception thrown under the admin routes included, which their middleware renders itself through the container's `ErrorMiddleware` so it is reported once; the send form also carries a one-time `nonce`, issued each time the form renders (up to fifty stay valid in the session, for several open tabs) and consumed under the session lock in `Session::transact()` only right before the send, after validation and the participant-id fetch, so a double tap or a re-send after a 504 sends nothing and answers 409 with the typed text and a neutral notice ("Tento formulář už byl jednou odeslán, nebo je zastaralý…"); its submit button is disabled on submit and re-enabled on `pageshow`; a refused POST (expired day or stale CSRF) answers 403 with a Czech "link expired" page (`templates/admin-expired.twig`) that echoes the typed title and text, and re-opening the link keeps a well-formed `csrf` so a form open in another tab stays valid — through `App\Push\PushSenderInterface`/`WebPushSender`, either to everyone or to one programme — whose participants `ProgramProviderInterface::getParticipantIdsForProgramme()` names. Every send needs a Podpis (log only, never in the notification) and is written to the `messages` log (`App\Push\MessageRepository`, same database) **before** it is sent — `begin()` stores it with NULL counts and `finish()` fills `sent`, `removed`, `failed` and `unreached` (a programme's participants with no subscription) when the send returns, so a send that dies half-way still leaves the message on Informace, with `–` for the counts in the admin log; the result line adds `nedoručeno: N` when anything failed and `přihlášených bez notifikací: N` for a programme send. The log is kept forever: the admin page lists it and can hide a message from readers or show it again, recording who and when, but nothing is ever deleted. Subscriptions carry an `event` column and a send reaches only that event's subscribers; each also carries the participant id (`participant_id`) of the session that saved it — taken from the session, never from the request — which `www/push.js` keeps in step by re-sending the subscription whenever the page's `push-identity` meta (the participant id, empty logged out) differs from the one it last sent (`localStorage['pushIdentity:<base>']`), so a programme send reaches exactly the subscribed browsers of its registered participants. Storage is one `PDO` per request from `Storage\Database::open()` (WAL, `busy_timeout` 5000, foreign keys), the container's `\PDO::class`, migrated on first use by `Storage\Migrator` — numbered steps tracked in `PRAGMA user_version`, one `BEGIN IMMEDIATE` transaction each, `Migrator::VERSION` the highest. It is **1**: one fresh step (`subscriptions` keyed `(event, endpoint)` with `participant_id` and `failures`; `messages` with nullable counts and `failed`; `subscribe_attempts`; `pairing_attempts`), because the earlier steps were collapsed before anything was in production, and a database at a higher version (every file the old five-step migrator made) is refused with a `RuntimeException` rather than taken for current. From the first production deploy on, append a step, never edit a shipped one. Both repositories, `Auth\PairingThrottle` and `Push\SubscribeThrottle` take that `PDO` and run no DDL. Subscriptions are keyed `(event, endpoint)`, so the same browser may subscribe to two events and `delete($event, $endpoint)` touches only its own; `POST /push/subscribe` accepts only endpoints on the known push services (`Push\EndpointPolicy`, extended by `PUSH_ENDPOINT_HOSTS`), because the welcome is a POST to that URL; only keys `Push\SubscriptionKeys::valid()` accepts — a 16-byte auth secret and a `p256dh` that OpenSSL parses as a point on P-256, since a 65-byte `0x04…` value off the curve passes every shape check and then throws inside the library's batch encryption — or it answers 400 `{"saved":false,"error":"invalid-key"}`; and at most `SubscribeThrottle::LIMIT` (300, room for a camp behind one NAT) **new** subscriptions per `(event, throttleKey)` in 10 minutes, then 429 `{"saved":false,"error":"too-many"}` — a known one never counts, a new one counts once saved even if its welcome is then rejected. `PushSenderInterface::sendToSubscription()` returns `Push\SendOutcome` — `Delivered`, `Rejected` (the push service answered 404 or 410, or the row can never be delivered: refused by the allow-list, malformed keys, or no longer stored) or `Failed` (a timeout, any other status, an exception) — and `POST /push/subscribe` answers a new subscription accordingly: 201 `{"saved":true,"welcome":true}`; 201 `{"saved":true,"welcome":false}` with the row kept, because a failure proves nothing about it; or, for `Rejected`, the row deleted and 502 `{"saved":false,"welcome":false,"error":"subscription-rejected"}`. A known subscription (the re-send after a login or logout) is 201 `{"saved":true,"welcome":null}` and sends nothing. The welcome and every send for everyone link to `/<slug>/informace`. `POST /push/unsubscribe` `{endpoint}` deletes `(event, endpoint)` and answers 204 whether or not the endpoint existed (400 without a string `endpoint`; an empty string is a string, so it is a 204 that deletes nothing), so the unauthenticated route tells nobody which endpoints exist. `WebPushSender` gives every push request a 5 s timeout (`TIMEOUT_SECONDS`; the library's 30 s could outlast nginx's 45 s on an admin batch), deletes at send time any row whose endpoint the allow-list refuses (rows from before it existed) or whose keys fail `SubscriptionKeys::valid()`, sends through `Push\IsolatingWebPush` — the library with `prepare()` per notification, so a row whose encryption still throws is set aside and deleted instead of taking the whole batch down (only when *every* row is set aside is it the platform's fault: all count as failed, none is deleted, the first error is reported) — and keeps strikes: a `Failed` send adds one to the row's `failures` — but only when the row's push-service host delivered at least one other notification of the same batch (`WebPushSender::strikable()`), so a send where nothing arrived, or one service's outage, strikes nobody — `MAX_FAILURES` (5) in a row delete it (counted as failed, not removed), and a delivery resets it, as do new keys on a re-subscribe (`save()` upserts and keeps the count when the keys are the same). `sendToEvent()` returns `{recipients, sent, removed, failed}`. It validates `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` in its constructor, and gets its repository as a closure resolved on the first send. `Kernel::create()` builds the sender at boot for every push event, so a misconfigured instance fails on the first request, not on the first tap — and since every event has push, `.env` needs a VAPID pair even in development; `AppTestCase` gives every app a `SpyPushSender`, and `tests/bootstrap.php` generates a throwaway pair per run for the tests that boot the real one. `www/push.js` is a one-way opt-in: there is **no off switch** — once subscribed, the button's `.push-enable` paragraph is hidden and the status line reads `Notifikace máš zapnuté, jupí!` (after a fresh subscribe, the welcome line), so only the browser's own settings turn notifications off; `/push/unsubscribe` stays on the server but nothing in the app calls it. Turning it on registers the worker, shows `Připravuji…` and waits up to 10 s (`READY_TIMEOUT`) for `serviceWorker.ready`, because the browser subscribes only through an active worker and on a first visit it may still be installing; a 429 from the subscribe says `Teď si notifikace zapíná moc lidí najednou, zkus to za chvíli.` and keeps the browser's subscription (the next page re-sends it), a 400 `invalid-key` says `Prohlížeč poslal neplatné údaje, zkus notifikace zapnout znovu.` and drops it like any other failure; without `serviceWorker`/`PushManager` the button is hidden, and on iOS (Safari outside a home-screen app has no `PushManager`) the status line says `Na iPhonu zapneš notifikace, až si aplikaci přidáš na plochu.`. Nothing in it calls `alert()`. `www/sw.js` stays at the docroot root and is registered at scope `/<slug>/` (the `event-base` meta tag) by `www/shell.js` on every page — and again by `push.js`, harmlessly, since `register()` is idempotent — so two events in one browser keep separate workers. A push without a usable payload is shown under the title `Notifikace`. After showing a notification the worker posts `{type: 'news-updated', programme}` to the event's open windows; `programme` (an id or null) travels in the payload from `PushSenderInterface::sendToEvent(…, programme:)` (`WebPushSender::payload()`).

`InfoModule` (`/informace`, tab `Informace`, `templates/info.twig`) is the crisis contact, then `Notifikace` — the message log as readers see it: every visible message, newest first, under Prague day headings (`Push\NewsItems::groups()`, `Čt 20. 5.`, keyed for the morph), each card left-aligned with its full body and a relative time (`NewsItems::relative()`: under a minute `právě teď`, under 60 minutes always `před N min`, even across midnight; the same Prague day `před N h`; the day before `včera H:i`; older a date), `Zatím žádné notifikace.` when there is none — then `Rychlé odkazy` (the handbook and `content/links.php`). A message for everyone is there for every reader; a programme message appears only to a paired participant whose `getParticipant()` programmes include it, under that programme's name (a failing call just leaves those out — Informace logs out only on `SessionExpiredException`), and in that programme's sheet on `/programy` for everyone. Every relative time carries its instant in `data-sent-at`, here, on Domů and in a programme's sheet, and `www/shell.js` redraws it from the device clock with the same bands, so a copy read later or offline still says how long ago it is. There is no archive or detail screen. Because of that `info` requires `push`: `EventConfig::load()` refuses an event that enables one without the other, and every shipped event carries both.

Program/schedule data goes through `App\Program\ProgramProviderInterface`: `getPrograms()` (each with `preregistered`, bool), `getSections()`, `getRegistrationWindow()` (`Program\RegistrationWindow`, `start`/`end` either possibly null; `state($now)` is `none`, `before`, `open` or `after`, the start inside, the end outside), `getParticipant($sessionToken)` (`Program\Participant`: kissj's participant `id`, the `nickname` or null, and their active registrations as `programmes`), `getParticipantIdsForProgramme($id)`, `startPairing($deviceId)` (`Program\Pairing`: device code, user code, verification URL, expiry, interval; `formattedUserCode()` shows `483291` as `483-291`), `pollPairing($deviceCode)` (`Program\PairingPoll`: a `PairingStatus` — `pending`, `slowDown`, `expired`, `denied`, `approved` — and, on approval only, the session token and its expiry), `register()`/`unregister($sessionToken, $id)` and `revokeSession($sessionToken)`. Every method may throw `TransferException` or `ProgramDataException` when the source fails; the session calls throw `SessionExpiredException` when the device session is unknown, expired or revoked (which logs the reader out), and the writes `RegistrationRefusedException` with the contract's code (`notPaid`, `closed`, `notFound`, `notPossible`, `wrongRole`, `alreadyRegistered`, `notRegistered`, `conflict`, `full`) when the source says no. `StubProgramProvider` (the `local` source) reads `events/<slug>/fixtures/programs.json`, `sections.json`, `registered.json` (participant id → programme ids), the optional `participants.json` (participant id → nickname) and the optional `registration.json` (the window) — no network calls, safe for dev and tests. It approves a pairing on the first poll as the first participant of `registered.json` (or `1`), minting a fresh token `stub-<id>-<16 hex>` on every approval, so a logout (which revokes the token) never blocks the next pairing; writes follow kissj's order of checks (session, window, `notFound`, `notPossible`, `alreadyRegistered`/`notRegistered`), and as in kissj a preregistered programme is in nobody's list. Registrations made in the app and revoked tokens live in `<STUB_STATE_PATH>/<slug>.json` (`{"registrations": {...}, "revoked": [...]}`), read-changed-written under one `LOCK_EX`, so two workers writing at once (a double tap) see each other's write; a file that is not valid JSON (a half-written one caught mid-write) counts as empty, and a state file that cannot be created, locked or written is `Program\LocalStateException` — a `TransferException`, so callers treat it as an outage. `KissjProgramProvider` (Guzzle-based) talks to the real kissj programme API (`docs/kissj-contract.md`, contract **2.0**): the list, the device pairing, the participant behind a device session (sent as `X-Kissj-Device-Session` beside the API key), the two writes and the revoke, and validates everything that arrives. A `401` with an empty body on a call that carries a device session is `SessionExpiredException` (a 401 with a body is a rejected API key, an outage, or every reader would be logged out); a `400` with the contract's `{"error": code}` on a write is `RegistrationRefusedException`; every other non-200, and a kissj that never answers, is a `KissjTransferException`. `PROGRAM_PROVIDER_<SLUG>` is required for every event and names the source: `local` (the stub, the event's fixture files) or the http(s) root URL of a kissj instance (`KissjProgramProvider`, which then also requires `KISSJ_API_KEY_<SLUG>`); `Kernel::programSource()` checks it at the top of `Kernel::create()`, before the container is built, and a missing value or anything else (`stub` and `kissj` included) or a URL without the key throws a `RuntimeException` naming the variable, so that event does not boot — no event falls back to the fixtures, and every test pins `local` (`tests/bootstrap.php`, for every directory under `events/` and `tests/fixtures/events/`). The URL must be the address a reader's browser can open, because kissj builds the links it hands out (the pairing's verification URL) from it. Events of one deployment may read different kissj instances; the key is sent as `Authorization: Bearer` on every request and is what tells kissj which event is asking, so no event slug is configured anywhere. Locally the events are `local`; the deployed instance reads kissj staging for now (`obrok19`, which kissj does not have, stays `local`), which needs kissj to implement contract 2.0. The provider also supplies the programme **sections** through `getSections()` — id, title, display order and the optional `subTitle` — from the `sections` of kissj's list response, or from the stub's `fixtures/sections.json`, which is that same list in kissj's shape (`App\Program\Sections` maps both). The event config carries no `sections` key. `Kernel` wraps the kissj provider — never the stub, whose fixture files already are a local copy — in `Program\CachingProgramProvider`, backed by `Cache\FileCache` under `var/cache/<slug>/`: one JSON file per entry, `{"fetchedAt": "<DATE_ATOM>", "data": …}`, written to a temp file and renamed over the old one; the entries are `list` (`{sections, programmes, registration}` from one list response) and `session-<first 32 hex of sha256(token)>` (`CachingProgramProvider::sessionKey()`: one device session's `{id, nickname, programmes}` — the token is a secret and is in no filename). An entry younger than `PROGRAM_CACHE_TTL` seconds (instance-wide, `Kernel::programCacheTtl()`, whole seconds, default 300 for anything else; `0` always refetches) is served without asking kissj; an older or missing one is fetched and rewritten; an expired one is served **however old** when kissj throws `TransferException` or `ProgramDataException` (stale-if-error), and the failure goes to `Collector::collect()` instead of the reader. Only a missing entry lets kissj's trouble reach the modules' notices. `SessionExpiredException` is an answer, not an outage: the entry is deleted and the exception rethrown — but only once it is asked, so a fresh `session-…` entry keeps a device kissj has since revoked marked for up to the TTL. The pairing calls, the revoke and `getParticipantIdsForProgramme()` are never cached; `revokeSession()` deletes the session's entry whatever kissj answers. **A write that succeeds** deletes the session's entry and this request's memo of it, so the very next read — the redirect after the write — asks kissj again; the delete first rewrites the entry's write marker (`written-<key>`, a random value, `WRITTEN_PREFIX`) and then waits for the entry's lock, so a read already under way with kissj's answer from before the write does not store it. A refusal changed nothing and keeps both, except `alreadyRegistered`/`notRegistered` (the cached participant is not what kissj holds: the session entry goes the same way) and `notFound`/`closed`/`notPossible` (the cached list is out of date: the `list` entry goes); an outage keeps the entry. The decorator memoises every resolved read per request (keyed by `Freshness::generation()`) and remembers the inner provider's first failure for the same request, after which an expired entry is served stale and a missing one rethrows that failure without asking kissj again — so an outage costs one timeout per request however many entries a page reads. Across requests three more rules keep kissj from being asked by every request at once, all kept as files beside the entries: **single-flight** — `FileCache::tryLock()` takes a non-blocking `flock` on `<key>.lock`, and while another request holds it a request with an expired entry serves it as `locked` (not marked stale, unless `kissj-down` exists) and one with no entry waits up to 12 s (`$lockWait`; kissj's own timeout is 10 s) via `waitLock()`, then serves the holder's fresh entry, rethrows if the holder failed meanwhile, or fetches itself — a filesystem that cannot lock at all yields a no-op lock rather than "held", and the empty lock files accumulate, one per entry; a **60 s breaker** (`BREAKER_SECONDS`) — a failure writes the `kissj-down` entry and for a minute after it an expired entry is served stale without asking, while a missing one still asks, and a success deletes the marker (one participant's bad answer opens it for the whole event); and **one report per 5 minutes** (`REPORT_SECONDS`, the `kissj-reported` entry, which a success leaves alone, so a flapping kissj is not reported on every flap). An unwritable `var/cache/` makes all three quietly do nothing. An entry of the wrong shape (or a file that is not JSON or has no `fetchedAt`) counts as missing, and a failed write is reported, not thrown. Every read updates the request-scoped `Program\Freshness` (the oldest fetch time served, and whether anything was stale), which the screen middleware resets per request.

**Login is kissj's device pairing** (`docs/kissj-contract.md`, "Device pairing"); there is no TIE code anywhere in eventApp and no external SSO. `Auth\Identity` is a paired participant: kissj's `participantId`, the `nickname` (or null) and the device `sessionToken`, which lives only in the server-side session and never reaches a template or the reader's JavaScript; `displayName()` is the nickname or `Účastník`, `initials()` the first letters of the first and last word, the first two letters of a single word, or null (the generic person icon). `Auth\Authenticator` stores it under the session key `identity` (rotating the session ID first) and drops it on logout (cleared, then rotated). The flow: logged out, Profil's `Přihlásit kódem z KissJ` is `POST /profil/propojit` (`pairing-start`), which asks `Http\SameOrigin::allows()` (else a 403 page), redirects a reader already paired, counts the start in `Auth\PairingThrottle` (`LIMIT` 300 per `(event, throttleKey)` in 10 minutes, every start counts: one phone cannot burn kissj's cap on pending pairings, while a camp behind one NAT still logs in) and calls `startPairing(sha256(Session::id()))` — one browser, one pending pairing, and a second start replaces it at kissj. The pairing is kept in the session under `pairing` (`deviceCode`, `userCode`, `verificationUrl`, `expiresAt`), and Profil shows the code (`483-291`), `Zadej kód v KissJ, nebo`, an `Otevřít KissJ ↗` link to the verification URL in a new tab, `Čekám na potvrzení v KissJ…` and `Začít znovu`. `www/profile.js` polls `GET /profil/propojit/stav` (`pairing-poll`) every 5 s while the code is on a visible screen, stops when the screen is left and resumes with the same code; the answer is always a 200 `{"status": …}` with `Cache-Control: no-store`, and a provider failure (or an approval whose participant read fails) answers `pending`, so the page keeps asking and kissj's re-issued approval is collected later. `approved` stores the identity (the pairing and any old outcome dropped before the ID rotates, so a late poll under the old ID cannot collect a re-issued approval) and leaves the `Jsi přihlášen` toast; `approved`, `denied` and `expired` make the page reload Profil itself — the one way a login reloads the document. A start, poll or session that went wrong leaves `pairingOutcome` (`{code, at}`) in the session, which a logged-out Profil shows for ten minutes as a `.notice`: `denied` `Přihlášení bylo v KissJ zamítnuto.`, `expired` `Kód vypršel, začni znovu.`, `gone` `Propojení s KissJ už neplatí, přihlas se znovu.`, `busy` (the throttle) `Teď se propojuje moc lidí najednou, zkus to za chvíli.`, `unavailable` `Propojení se teď nedaří, zkus to prosím později.`. **Logout exists**: paired, Profil ends with `Odhlásit se z aplikace`, a two-tap button (`data-confirm="Opravdu odhlásit?"`) posting `POST /profil/odpojit` (`pairing-revoke`): `SameOrigin` (else a 403 page), `revokeSession()` at kissj best effort (a `SessionExpiredException` counts as done, anything else is collected), the identity dropped, and the `Odhlášeno` / `Obsah teď můžeš jen prohlížet` toast — only when somebody was logged in. Any screen whose personal read hits `SessionExpiredException` calls `Kernel::sessionGone()`: logged out, outcome `gone`, and a pending login toast dropped; Domů and Program render that page logged out with a toast of their own saying why (`Kernel::goneToast()`). A logged-out Profil shows `Nejsi přihlášen`, the explanation, the start button and, for an event with a `website`, `Nejsi ještě registrovaný účastník? Navštiv web akce ↗ a zjisti víc!`; paired, the avatar (initials or the person icon) with the display name; both then show the install card and, for an event with a dark set, the mode control. The app bar shows who is paired through the `auth_identity()` Twig function rather than a global (`participantId`, `displayName`, `initials`; never the token), because a handler can log the reader out during the same request that renders the bar: the profile link is the initials in a circle (`.appbar-avatar`, hidden from assistive tech; the link reads `Profil`) or the generic person icon.

Sessions are `App\Session`, built per event as `new Session($slug, Kernel::sessionPath($root), appRoot: $root)`, and nothing about them depends on the host's ini (the FTP host's handler and defaults are unknown): before every start it sets the files handler and its path **as a pair** — `var/sessions` (or `SESSION_PATH`; created 0700, refused as a symlink, and outside the app root also refused unless owned by the process user with no group/other bits), else a private `eventapp-sessions-<8 hex of the app root's sha256>` under the system temp dir under the same ownership rules, else the host's own handler *and* path untouched (`Session::storage()`; a fallback is reported through `Collector` once per process) — plus a 30-day `gc_maxlifetime` with its own GC at 1/1000, strict mode, cookie-only IDs, `lazy_write`, `cache_limiter` `''` (the screen middleware states the pages' cache policy instead) and a host-only cookie `eventapp` that is `HttpOnly`, `SameSite=Lax` and `Secure` on HTTPS. `session.auto_start` is the one thing it cannot set at run time and must be off on the host. Reads use `read_and_close`, so a slow kissj call never holds the session lock against the reader's next request (`SessionLockTest`), and a request without the cookie — or, on the app's own files store, with a cookie whose session file does not exist — reads nothing and starts nothing (no file, no `Set-Cookie`); `Session::id()` is the exception, starting a session when there is none, because the pairing's device id is its hash (under CLI a random ID kept in `$_SESSION` stands in). Every write goes through `transact()`, which reopens the session, applies the change to freshly read values under the handler's lock and closes it again — also what makes the admin nonce's check-and-consume and the toast's take atomic — and a reopen resumes the stored ID without sending the cookie again. A cookie the store does not know (collected, invented) still gets a new cookie and an empty file under strict mode — accepted. The cookie lasts `Session::LIFETIME` (30 days) and slides: `refreshCookie()`, called by Kernel's session-cookie middleware on every full logged-in page, re-sends it with a fresh expiry and touches the session file once a day (not on the host's store), because `read_and_close` never updates it and the GC would otherwise count from the last write. There is one session cookie per host, so `Session` namespaces its values per event slug: pairing in one event shows nothing in another, and a logout is local to its event. The values: `identity`, `pairing`, `pairingOutcome`, `toast`, and the admin page's `admin`, `csrf`, nonces and `notifyResult`. Login and logout rotate the session ID with `session_regenerate_id(false)` — rotated before the identity is stored, cleared before the rotation on logout — so the old ID is left holding the logged-out session rather than destroyed: the worker's install and refill bursts send up to ~26 requests with the cookie of the moment, and under strict mode a destroyed ID would answer one of them with a new empty session and a `Set-Cookie` that logs the reader out (`SessionRotationTest` checks it against a real server).

**Toasts.** One component, `templates/_toast.twig` (`<div class="toast" role="status" data-toast data-key="toast">`: a title, an optional second line, a `✕` `[data-toast-close]` with `aria-label="Zavřít"`), a `structure`-filled banner with a hairline at the top of the screen, gone after 6 s on display (`TOAST_MS` in `www/shell.js`, which arms a server toast only once its screen is shown) or on the close tap. The server's ones wait in the session under `toast` (`['title', 'line', 'at' => time()]`, plus a `tag` for a write's success): `Kernel::putToast()` leaves one, `Kernel::takeToast()` takes it on the next **full document the reader asks for** — never a fragment (`X-Screen`, which the loader's warm-up sends) nor the worker's own fill and refill fetches (`X-Worker-Fill: 1`, `Kernel::WORKER_FILL_HEADER`), which would swallow it before the reader sees anything — and drops one older than 60 s (`TOAST_SECONDS`) unsaid. A request with no toast pending never opens the session. Profil takes the login and logout toasts, Program the registration ones. A response carrying a toast goes through `Kernel::markToast()`, which sets `X-Toast: 1` (`Kernel::TOAST_HEADER`), and the worker never stores such a response, so the offline copy is fetched again without it. The shell's own toast is the offline one (below). A toast that leaves while its `✕` has the focus hands the focus to the visible screen — or, with the programme sheet open, to the sheet's card (`removeToast()`).

Theming: each event's `config.php` has a `colors` map (e.g. `base`, `darker`, `primary`, `text`, `text-invert`, and the optional `nav-active`) and an `assets` map (logo/favicon paths under `www/events/<slug>/`). `Kernel` exposes the whole event config as the `event` Twig global; `_layout.twig` emits the colors as `--color-*` CSS custom properties in an inline `<style>` block, and `www/style.css` consumes them (`var(--color-base)`, etc.) — colour lives in the config, never in a stylesheet. An event may add one optional stylesheet for its non-colour look (shapes, type) as `assets.stylesheet`, a path under `www/`: `_layout.twig` links it through `asset_version()` right after `style.css`, `Precache` lists its versioned URL, and `ThemingTest` enforces that it names no colour literal, reads only `var(--role-…)`/`var(--theme-…)` with a fallback, and that every role an event declares is read by `style.css` or by that sheet. A rule there must never alter another event, and it must not give `<main>` a stacking context. `EventConfig::REQUIRED_COLORS` is checked at boot, so a half-themed event fails to start rather than rendering with unset properties. `www/style.css` must never name a colour itself; `ThemingTest::testCoreStylesheetHasNoColorLiterals` enforces that. Type is a seven-step `rem` scale in `:root` (`--fs-2xs` 11 … `--fs-2xl` 24 at a 16px root); two kinds of rule stay in px and `ThemingTest` names them: the chrome glyphs of the fixed-height bars and of the instrument controls (the timeline's zoom pair, the plan's `.plan-zoom-btn` floating on it), whose boxes are measured in pixels — `www/programs.js` reads the bars' heights as plain pixel numbers — and the timeline grid's type (`.tl-tick`, `.tl-now-label`, `.tl-stage`, `.tl-card`), whose geometry is frozen. The focus ring is one global two-tone `:focus-visible` rule in the ground pair (`--on-ground` outline, `--ground` halo); `.tabs-tab`, `.tl-card`, `.sheet-close` and `.day-chip` (its strip scrolls sideways, so it clips) move it inside their clipping box; the sheet's dialog container and the screen section (programmatic focus targets) draw none.

Next to `colors` sits an optional `theme` map (`EventConfig::$theme`, always an array) for the look-and-feel that is not colour — `font`, `font-display`, `font-display-weight`, `radius`/`radius-pill`/`radius-sheet`/`radius-card`, and `motion`. It is emitted as `--theme-*` in the same inline `<style>` block. There is no `font-url` any more: **every font and the icon font are self-hosted**. The `@font-face` rules for themix (400, 700), skautbold and Montserrat (400 to 900; latin and latin-ext, Google's v31 variable files with Google's `unicode-range`, so 800 is a real weight) live at the top of `www/style.css`, one woff2 `src` each, the files under `www/fonts/<family>/`; Font Awesome Free 5.8.1 is `www/vendor/fontawesome-free-5.8.1/` (its `all.min.css` byte-for-byte with its licence header, the three `.woff2` files it names, `LICENSE.txt`), linked by `_layout.twig` as `/vendor/fontawesome-free-5.8.1/css/all.min.css`. So `theme.font` may name only a family `www/style.css` declares (or a system font). `EventConfig::fontFamilies()` is what the event renders with — the first family of `theme.font` and `theme.font-display`, quotes stripped, or `themix`/`skautbold` where unset, plus `Font Awesome` always — and `App\Http\Fonts` is the plain table family → web paths that `Precache` puts into the offline set; `Tests\Unit\FontsTest` keeps that table, the `@font-face` rules and Font Awesome's own `url()`s in step.

The Content-Security-Policy is enforced by `Http\CspMiddleware`: `script-src 'self' 'nonce-…'` with a fresh nonce per request in the Twig global `cspNonce`, so every inline `<script>` carries `nonce="{{ cspNonce }}"` and no element may carry an `on*=` handler (the push button is `data-push-toggle`, bound in `www/push.js`). Styles stay `'unsafe-inline'`: the timeline's per-programme `style` attributes cannot be hashed and must lay the screen out without JS, and an inline style can neither run code nor read data. Fonts and icons are `'self'` (self-hosted, above), so `style-src` is `'self' 'unsafe-inline'` and `font-src` `'self'`; the event's map origin is added automatically; anything else goes in the optional config key `csp` (`EventConfig::$csp`, `['frame-src' => ['https://…']]`, validated at load). `CspTest` renders every participating route and fails on a missing nonce.

Colour is **semantic roles**, not palette keys. No rule in `www/style.css` names a `--color-*` any more; every one reads a role, and the role definitions in `:root` are the only place the palette is touched (`ThemingTest::testNoRuleInTheStylesheetNamesAPaletteKey` enforces exactly that). The rule that keeps the system honest is **one colour, one role** — if an event's green is `state`, green is not also a ground, a surface or a piece of chrome. The set is sized for a 60:30:10 budget: `ground`/`on-ground` with `surface`/`on-surface` as its one block tier (60), `structure`/`on-structure` for the bars, the sheet, the buttons, the toast and the timeline's cards (30), and `action`/`on-action`/`action-link` plus `tonal`/`on-tonal` and `state`/`on-state` sharing the 10, with `edge`, `edge-width`, `heading`, `emphasis` and `scrim` in support, and `now` — the timeline's current-time line and its label, under `on-action` ink — falling back to `action`. `structure` defaults to `--color-darker` rather than `--color-base`: it is the one role that is a filled ground under inverted type at body size, and obrok19's base carries `--color-text-invert` at 3.85:1 where its darker green reaches 6.84:1. Three scopes **rebind** the core roles rather than adding names: a text field, `.sheet-card` and `.tl-scroll` are each their own little surface with their own structure on it, so the grid's cards are simply `structure` in the grid's scope. The rebinding sits on `.tl-scroll` and not on `.pg` because custom properties inherit — on `.pg` it would also reach the day strips and the view tabs.

**Light mode is light and dark mode is dark, all the way through.** `structure` grounds every bar, sheet and card, so in a light set it is the palest thing on the screen and in a dark set the darkest; a filled near-black app bar in light mode is the "black element in the light mode" the system exists to prevent, and a lifted mid-grey card at night is the same mistake upside down (`ThemingTest::testTheLargeFilledAreasFollowTheMode` measures the relative luminance of every role that names a large fill and holds each mode to its own end of the ramp). Two things follow. First, an accent can only be **ink or a small area filled under dark ink**, never a large fill: obrok27's `#e0ff00` is 1.01:1 on its pale ground and obrok19's `#2a9272` is 3.49:1, so the **active tab is filled with the event's colour and carries `on-state`** (15.4:1 and 4.8:1 under near-black ink) rather than tinted type — the fill is the whole tab, not a chip behind the glyph, because tinted type at those ratios is the regression this rule exists to prevent — and `state` has one shape in both modes; the **app bar, the current day chip (`.day-chip[aria-current="true"]`, under `on-state` like the active tab) and the `Přihlášen` tag (`.pl-tag`, a small fill carrying the ground's hairline) are the only other surfaces filled with `state`**, and everything on the app bar — the title and the profile link with its avatar — therefore takes `on-state` too, because that fill does not flip with the mode while `on-structure` does (it used to take `on-structure`, which put obrok19's body grey on green at 2.56:1); a secondary `.btn`, a `.highlight` link CTA and a `.notice` are **`tonal`** — the accent washed almost all the way into the ground, carrying the accent itself at full strength as ink. `.btn-primary` is unchanged in kind, a filled accent under inverted ink. Second, separation cannot come from a tone step alone, because content scrolls under a bar of very nearly its own colour, so **every bar, sheet and card also carries a hairline, in both modes** — `--edge-width`, still 0 for an event that declares nothing. Light hairlines are neutral and dark ones keep the accent tint; each is meant to clear 3:1 against both sides of itself, which is what the 1px content-block outlines replaced the old 4px frames for (obrok27's dark `edge` does not yet, about 1.8:1 on its ground, until its new palette).

One role sits beside `structure` rather than inside it: `signature`/`on-signature`, **structure that carries the identity**. It behaves like structure — a filled band of chrome with type on it — but its value is a quiet cast of the event's own colour, and the **hour ruler is its only use in the app**; painting a second surface with it would return the screen to the state where nothing could read as an accent (`ThemingTest::testTheIdentityRoleIsUsedByTheHourRulerAndNothingElse` holds it to one). It is deliberately *not* the accent at full strength: a saturated slab is the loudest thing on a light screen and a lit panel at night, and the ruler is chrome. The stage column has its own pair (`stage`/`on-stage`) in the grid's scope because the card and the column want different tones out of the same tier — the card separates from the grid by a step plus its hairline, the column is a band behind bold names — but its value is a **plain neutral in both modes**, because a hue on the largest block of the screen is how accents stop reading. Both pairs fall back to the grid's own `structure`, so an event that declares neither renders exactly as it did. The registered card has a pair of its own in the same scope: `registered-bg` (with `registered-line`/`registered-width`) and its ink **`on-registered`** (`--reg-fg`, falling back to `on-structure`), because on an accent fill the grid's card ink can fall far below AA (navigamus25's light set was 2.0:1); every kissj-design event names it in both sets. korbo26's dark set, likewise, carries a lighter orange (`#f08a3c`) as its `action-link`, `heading` and `emphasis` ink, its fill colour `#dd6700` being 4.39:1 on the dark surface.

Every role falls back to exactly the expression its rules used before roles existed, and those **built-in fallbacks are frozen** — they are the pre-round-10 look, dark chrome and all, and the fixture events under `tests/fixtures/events/` are what still exercise them (`testEveryRoleFallsBackToThePalette`, `testStructureDefaultsToThePalettesDeeperTone`). No shipped event uses them: **obrok19 hand-authors a `light` set of its own** and is no longer the frozen control — its tab bar is white, its green fills the app bar, the active tab and the registered programmes, its red is `action`, and `docs/baseline/obrok19/` is re-taken by `bin/baseline.php` at the end of every round, so a diff against it is still how a round shows it disturbed nothing. obrok19 stays **light-only**: no `dark` set, no mode control. An event that wants its own colours declares `roles` as two **hand-authored** sets, `light` and `dark` (`EventConfig::$roles`) — accents do not survive mechanical inversion, so changing a colour is deliberately a two-place edit. `_layout.twig` emits light as the base, then the dark set twice: once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-mode="light"])` so the device's setting works without JS, and once under `:root[data-mode="dark"]` so an explicit choice wins. A tiny **inline script in `<head>`**, before the stylesheet link, sets `data-mode` from `localStorage['obrokColorMode']` (global, not per event) or from `prefers-color-scheme` — never the deferred script at the foot of the page, or the reader sees a frame of the wrong theme. The choice is made on **Profil**, logged in or not (the look is the browser's, not the participant's), and only for an event that declares a dark set: a three-way `<fieldset class="mode-control" data-mode-control>` (`Vzhled`: radios `Světlý`, `Tmavý`, `Podle systému`, one `name="mode"`), handled in `www/app.js` by a delegated `change` listener — `Podle systému` removes the stored choice so the device setting rules again — and re-checked from storage on `DOMContentLoaded`, `screen:shown` and `screen:morphed`. The app bar carries no mode toggle.

Colour reaches the **assets** too, because a bar that follows the mode cannot carry one fixed drawing. `assets.menuLogo` is the tab-bar mark and `menuLogoDark` its dark-mode twin (`.mode-light-only`/`.mode-dark-only` swap them), while `menuLogoOnState` is the drawing for a surface filled with `state` — that fill is the event's own colour, so a mark in that same colour disappears on it. Which drawing goes where follows from what the surface is filled with, and **the tab bar and the app bar are not the same kind of surface**: the tab bar is `structure` and flips with the mode, so it takes the mode pair, but the app bar is `state` and does not, so it takes `menuLogoOnState` exactly as the active tab does. `assets.appBarLogo` overrides that for the app bar alone (precedence `appBarLogo`, `menuLogoOnState`, `menuLogo`); the tab bar never reads it. obrok27 declares `appBarLogo` (the white lilie, on its dark bar in both modes), `mainLogo`/`mainLogoDark` (the wordmark) and no `menuLogo`, so the home tab shows the `fa-home` icon; its `bar`/`tabbar` roles fill the two bars and are read only by `events/obrok27/style.css`, so both bars stay dark in light mode. Each asset is optional and the classes are only emitted when the second drawing exists, so an event with one logo keeps showing it everywhere. `mainLogo`/`mainLogoDark` do the same job on Domů.

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link; the logo's link to Domů carries a visually hidden `<event name> – úvod`, since the logo is decorative and the link would otherwise be announced as the current screen's title), the network banner, and a fixed bottom tab bar built from Domů plus the enabled features, sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Profil is a core route, not a module, and a screen in the stack like the tabs.

Switching screens does not load a document. `<main>` is a **stack of screens** — `<section class="screen" data-screen data-title data-doc-title data-tab data-fetched-at [data-stale] tabindex="-1">`, emitted identically by `_layout.twig` (the first one, server-rendered) and by `_screen.twig` (every one after it). A request carrying `X-Screen: 1` gets the second parent: every participating template picks its own with `{% extends fragment ? '_screen.twig' : '_layout.twig' %}`, against a Twig global that `Kernel`'s screen middleware sets per request. `data-fetched-at` (always, `DATE_ATOM` in Europe/Prague) is when the provider data on the screen was fetched — the request time on a screen that used none, and on every `local` event — and `data-stale="1"` marks an old copy served because kissj failed; both come from the Twig function `data_freshness()` (a function, like `auth_identity()`, because the handler fills it before the layout renders). `www/shell.js` draws the network banner from them. A background revalidation compares `innerHTML`, which leaves the section's own attributes out, so `app.js`'s `syncFreshness()` carries the two attributes over on both the unchanged and the morphed path and dispatches `screen:freshness`. Next to `fragment` the middleware sets `screenPath`, which exists because slim/twig-view resolves `get_uri()`'s runtime exactly once and then keeps it for the life of the `App` — the path would be stale from the second request on, which no single-request web server notices and every test does. A plain request stays byte-identical to what it was, which is what keeps deep links, crawlers, the back button against a cold cache and a reader with JS off working, and `Vary: X-Screen` keeps the two responses apart in anything that caches them.

`www/app.js` fetches a screen **once**, inserts it hidden, and from then on navigation is show/hide. It does not wait for the first tap either: once the first document has loaded (`requestIdleCallback`, at most 3 s), the **warm-up** (`warm()`) fetches every other participating screen one after the other and inserts each hidden, loading the Font Awesome faces first (`warmIcons()`: a hidden screen makes the browser read no font, so the quick links' brand icons would blink in on their first show), stopping at the first failure and skipping itself under `navigator.connection.saveData` (or `window.appWarm === false`, the browser tests' switch, set by `BrowserTestCase::coldScreens()`); `load()` keeps one fetch per path in flight, so a tap on a screen the warm-up is still fetching waits for that fetch rather than inserting the screen twice. The map's iframe is `loading="lazy"`, so a Místa screen warmed into a hidden section does not load Google's map until it is shown. Nothing is ever removed, so state is *live* rather than restored: the map's Google iframe keeps running, the timeline keeps its zoom *and* its horizontal scroll, a scrolled list stays scrolled. Hidden and not detached is the whole point — re-inserting a detached `<iframe>` re-fetches it, which is also why neither `hx-preserve` nor `data-turbo-permanent` could have done this: both persist a node present in *both* documents, and the map exists on one screen only. Order matters, **insert → show → init**: the ruler's label-width measurement and every `scrollLeft` calculation return 0 inside a `hidden` subtree. Showing a cached screen is instant, always; one fetched more than five minutes ago is revalidated in the background, and a screen whose HTML has actually changed is **morphed** into the new one rather than replaced — `innerHTML` would throw away the very state the cache exists to keep. The morph is hand-rolled and small (no diffing library, and deliberately not a vendored Idiomorph): children match on `id`, then `data-key`, then position among same-tag siblings; a subtree already equal to its counterpart is skipped outright; a matched `<iframe>` is never written to *and never moved*, because a move re-inserts it and a re-inserted iframe reloads. It writes only the attributes the fresh markup states — one it does not carry at all belongs to the client (`--hour-width` lives in `.pg`'s `style`, `data-hour-step`, `data-pg-ready`, `disabled`) — and one the markup names in **`data-morph-keep`**, for the attributes the server writes without owning: `.pg`'s `data-view` and `data-step`, `.tl-page`'s `class`, a day chip's `aria-current`, `.mapview`'s `data-view`. Without that the screen would be put back on the server's default view and page, and a layout landing in the gap before the screen restores itself would take the reader's scroll with it. What the screen does own it puts back on a `screen:morphed` event, dispatched synchronously in the same task. A morph, like a replacement before it, never happens while the reader is in the middle of a screen — an open sheet or focus in a form field defer it to the next time that screen is shown, and it then runs *after* the screen is visible again, for the same reason the wiring does. Measured on the Program screen: a revalidation that finds no change touches **zero** nodes; one that finds a renamed, re-timed programme touches seven, on a screen holding sixty cards. Screens slide **by tab order** through the View Transitions API: the loader only sets `data-nav` on the root and the animations live in `www/style.css`'s one reduced-motion block, so where the API is missing — or reduced motion is asked for — the swap is instant rather than animated by hand. There is deliberately **no swipe gesture**: a horizontal drag on the timeline means "scroll the hours".

A response that is not a 200 is not a screen: the loader falls back to a plain navigation, so the reader gets the server's own error page instead of an app bar injected into a `<section>`. So does a screen the reader is waiting for that has not arrived after 8 s (`LOAD_TIMEOUT`, an `AbortController` on `load()`'s fetch), because on lie-fi a fetch that never ends would leave the tap hanging for minutes. `show()` dispatches `screen:hidden` (bubbling) on the section it hides, so a screen's own dialogs do not outlive it. A tap on the tab of the screen already shown navigates nowhere: the loader scrolls that screen to the top (smoothly, unless reduced motion is asked for), as a native tab bar does, instead of letting a plain navigation throw the live app away. The skip link is the other same-origin link the loader handles itself: it names the path the document was first served for, which after a swap is another screen, so a click on it focuses the visible screen's section and navigates nowhere. The participating set is read off the rendered shell — the tab bar's own links plus the profile one, in that order, which is what makes `/profil` count as forward — so it is Domů, the enabled tabs and `/profil` and nothing else. The handbook PDF, external links, `/admin/notify` and **every non-GET** stay plain navigations — the pairing start, the logout, a register or unregister — so a write reloads the document and empties the cache with it; that is the correctness rule rather than laziness, because the identity changes both the app bar and the registered marking on every programme. The end of a pairing is a GET poll answered by JSON, so `www/profile.js` reloads the document itself. Every link stays a real `<a href>` and the loader is an enhancement layer, not a client router: with `www/app.js` absent the app behaves exactly as it did.

**The worker is the offline copy.** Its `install` fetches `/<slug>/precache.json` (with `cache: 'no-store'`; core route `precache`, built by `App\Http\Precache`: `documents` = Domů, every tab in tab order (`Kernel::menu()`), `/profil` and `/offline`; `assets` = the stylesheet and scripts through `AssetVersion` (`style.css`, `app.js`, `shell.js`, `push.js`, `profile.js`; `programs.js` only for an event with the `programs` feature and `map.js` only for one with `map`, as the layout loads them), the manifest, the layout's icons, every non-empty `assets` path, `homepage.footerLogo`, `map.image` (the plan is the map that works offline), the manifest's icons and `Fonts::files(EventConfig::fontFamilies())` — the event's own fonts and Font Awesome, nothing it does not render with — a file missing on disk is left out, because one 404 fails the whole install; `optional` = the handbook when its file exists; `version` = 8 hex of sha256 over the sorted `documents`, `assets` and `optional` lists, so an enabled tab or a new handbook is a new version too) and fills the cache `eventapp-<slug>-<version>` with every document in both forms and every asset, writes the list itself into that cache **last** — after the documents and assets, before the optional entries, which may fail one by one — and then calls `skipWaiting()`. The worker's own document fetches (`storeBoth()`, for the fill and the refill) carry `X-Worker-Fill: 1`, so they take no pending toast. The stored `precache.json` is the completion marker: a fill that fails deletes its own half-filled cache, a target cache that already holds the marker is adopted as it is (a redeployed `sw.js` with an unchanged list reuses it rather than refetching), and `currentCache()` and `activate` adopt only the newest of the event's caches that holds it — never one still filling, or abandoned when the browser killed a worker mid-fill. Two fills of one version (a new worker's install and an old worker's `checkVersion()`) could delete the cache under each other's handle, so `adopt()` first re-checks through a fresh handle that the cache still exists and holds the marker (`isComplete()`: `caches.has()` plus the marker) and deletes the other caches only then, `install` fails when its own fill was lost that way, `activate` clears `cacheName` when nothing was adopted, and a failed fill deletes its cache only if the marker is still missing. `activate` then deletes the event's other caches, `clients.claim()`s and posts `sw-activated` (nothing reloads); when no complete cache exists it deletes nothing. `sw.js` itself is never versioned, so a deploy that changes an asset but not the worker never reaches `install` — the browser reinstalls a worker only when its script changes. That is `checkVersion()`'s job: once per worker lifetime, after a page was served from the network, it fetches `precache.json` with `cache: 'no-cache'` and, on a different `version`, fills the new cache, adopts it, deletes the others and posts `sw-activated` — unless a newer worker has become the active one meanwhile, whose cache it would otherwise delete; it does not run at all (and does not count as done) while a worker is `installing` or `waiting`, because that one fills the version itself; any failure leaves the current cache. The Cache API keys on the URL alone, so a fragment is stored under its URL plus `?x-screen=1` — in the cache only; no page links to it. Strategies: a hashed asset (a root `*.css`/`*.js` with `?v=`) and anything under `/fonts/` or `/vendor/` cache-first; an unversioned file under `/events/<slug>/` stale-while-revalidate, its network leg fetched with `cache: 'no-cache'` because nginx and `.htaccess` give the extension-matched files there (png, svg, jpg, webp, ico, woff2, css, js — not `site.webmanifest`) a year of `immutable` and a plain fetch would never get past the HTTP cache; a page (`navigate`) network-first — after 3 s the cached copy is shown if there is one (without one it keeps waiting), a failed fetch or `navigator.onLine` false goes to the cache, and `/offline` (`templates/offline.twig`) answers when there is neither — a page carries the identity, so it never comes from the cache while the network answers; a fragment from `load()` stale-while-revalidate, posting `screen-updated {path}` to that window when the server's copy differs (compared without `data-fetched-at`/`data-stale`, or every `local` screen would differ on every fetch); a fragment from `revalidate()` (`cache: 'no-cache'`) network-first, its cache fallback carrying `X-From-Cache: 1` so the loader does not take an offline answer for a confirmation — it neither resets the screen's `fetchedAt` nor skips the real check for five minutes once the signal is back. Every successful page and fragment is stored, except one carrying `X-Toast: 1` (`toasted()`), which is shown and never stored; `reconcile()` and `refill()` still run after it, so the offline copy is fetched again without the toast. Every same-scope non-GET except under `/admin/` and `/push/` deletes every `text/html` entry, from **every** `eventapp-<slug>-*` cache (a fill still running holds pages of the identity before too), once the server has answered it and before that answer reaches the page. A write that cannot reach the server — `navigator.onLine` false, where it is not even tried, or a fetch that fails — purges nothing and is answered by the worker with a **303 back to the request's same-origin referrer plus `#offline`** (`offlineRedirect()`; the event's home when the referrer is empty or from elsewhere, never a bare `#offline` on nothing), which the page then serves from the cache like any offline navigation and `shell.js` turns into the offline toast — never the browser's error page, which an installed iOS app has no Back button out of. (Purge on write: a login or a logout never serves a screen rendered for the other identity, and a register or unregister never leaves an old registered marking; a push subscribe or unsubscribe changes no rendered HTML, and purging there would empty the offline copy with nothing to refill it until the next navigation.) The next page that arrives from the network refills the missing documents for the identity now in the cookie. A purge also bumps a counter that every page and fragment write captures when its request starts, and a write that started before a purge is dropped rather than stored for the old identity (a login during the very first install is a request the not-yet-active worker never sees; so every page that arrives from the network is also **reconciled** — `reconcile()` reads its `push-identity` meta, the participant id, and when any other stored full page was rendered for a different identity it purges every page and fragment, which `refill()` then puts back for the cookie's identity). A page whose network answer is a 5xx gets the cached copy when there is one and the server's error page when there is none — never `/offline` while the server answers. A fragment that turns out changed costs two network fetches (the worker's background fetch, then the loader's `no-cache` revalidation after `screen-updated`); an unchanged one costs one. `/admin/*`, `/push/*`, `/precache.json`, the pairing poll `/profil/propojit/stav` (it must reach the server every 5 s, and as a GET it purges nothing), `/health`, other events and other origins (only the map's iframe is left) are never touched. Rollback is a `sw.js` with the push handlers and an `activate` that deletes every `eventapp-<slug>-*` cache.

The loader and the worker: `revalidate()` sends `cache: 'no-cache'` and `load()` does not. `go()` dispatches `screen:loading`/`screen:loaded` on `document` around a fetch the reader waits for, never around a background revalidation (and `screen:loaded` once more on an instant show, so the bar of an overtaken tap goes). The loader listens to the worker: `screen-updated {path}` and `news-updated {programme}` set the entry's `fetchedAt` to 0 (Informace and Domů always, the Program screen too for a programme message) and revalidate the one on show, so a new `.news[data-key]` is morphed in at the top; a path reported before the loader has it waits in `staleOnArrival`. `syncFreshness()` dispatches `screen:freshness` on the section whenever it changes either attribute.

`www/shell.js` holds the installed-app concerns and talks to the loader only through those events. It registers the worker. It draws **the network banner**: one `<p class="netstate" data-netstate aria-hidden="true" hidden>` per document, outside every screen, docked right above the tab bar, which shows only offline (`Jsi offline. Data byla naposledy aktualizována v 10:20 (před 25 min).`) or online with an old copy (`data-stale`: `Nepodařilo se načíst aktuální data. Zobrazuji stav z 10:20 (před 25 min).`) and is otherwise hidden. The time is the visible screen's `data-fetched-at` on the reader's clock, re-read on every draw (`DOMContentLoaded`, `screen:shown`, `screen:morphed`, `screen:freshness`, `online`/`offline`, `visibilitychange`, `pg:tick` and every minute), so switching to a screen fetched earlier changes it at once; the age is `právě teď` under a minute (never `před 0 min`), `před N min` under an hour, then `před N h`, then the date. Its height is published as `--netstate-height` on the root (0px while hidden, kept current by a `ResizeObserver`), which the docked view switcher (Program, a two-view Místa), every screen's bottom padding and `--screen-height` add, so the banner covers nothing. A screen reader hears it through a live region of its own (`<p class="sr-only" role="status" data-netstate-live>`), written only when the state changes and without the ticking age. It runs **the toast** (above): arms server toasts on display, and on `#offline` in the URL shows `Akci není možné provést, protože jsi offline.` / `Zkus to znovu až najdeš místo se signálem.` and strips the hash with `history.replaceState`. It owns **the two-tap confirmations**: a button with `data-confirm` (the logout, the unregister) swaps its label for the question on the first tap and submits on the second, starting over on `screen:hidden`, `sheet:closed` and `pageshow`. It redraws **the clock-driven parts** from `homeNow()` (`window.pgClock` when set): Domů's next-programme cards, the countdown (whole Prague days to the start, `den`/`dny`/`dní`, hidden from the start on), the date heading `data-home-date`, and every `data-sent-at` relative time, on `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `visibilitychange`, `pg:tick` and every minute. It toggles `data-loading` on the root for the 2px `.progress` bar at the tab bar's top edge (`var(--on-structure)`, the bar's own ink, because `state` is under 3:1 on a pale bar; a static bar under reduced motion), and keeps `beforeinstallprompt` (default-prevented, so Chrome shows nothing by itself) for the install card's hidden `Uložit jako aplikaci` button, which shows the kept offer once and is hidden again after the tap, on `appinstalled` and in an installed app (`display-mode: standalone` or iOS's `navigator.standalone`). iOS has no install prompt at all, so on an iPhone or iPad the card's `[data-install-ios]` hint (`Aplikaci si přidáš na plochu v Safari: klepni na Sdílet a pak na Přidat na plochu.`) shows instead, outside an installed app only. Zkus to za chvíli.", both with a link home, and under `APP_DEBUG` a `<details class="error-details">` with Slim's detail set; the instance app uses the plain `templates/instance-error.twig`. Two rules the shell depends on. `<main>` must **never** carry a `view-transition-name`, however natural it looks: naming an element makes it a stacking context, and the sheet is a fixed child of `<main>` that has to keep painting over the fixed tab bar. Only `.appbar` and `.tabbar` are named, which takes them *out* of the root snapshot so the shell sits still while the screen under it slides. And the per-screen layout rules key off the section (`.screen[data-tab="map"]`, `"programs"`, `"homepage"`) rather than the old `body.screen-*` classes, with `main > .screen[hidden]` restating `display: none` loudly enough to out-specify them.

`ProgramsModule` (`/programy`, tab `Program`, title `Programy`) is the single Program screen. Its behaviour is `www/programs.js`, not an inline `<script>`: it used to sit in `{% block header %}`, i.e. in `<head>`, which no screen swap can reach. The file exposes one idempotent `window.pgInit(scope)`; the shell loads it for any event carrying the `programs` feature, the loader calls it by dispatching `screen:shown` on the section it has just made visible, and a server-rendered Program screen wires itself on `DOMContentLoaded` so the screen keeps working even if the loader never runs. Everything the screen shows comes from `ProgramProviderInterface`. When a participant is paired, the module also calls `getParticipant()` and marks their programmes `registered` — that marking is what login changes on the screen, besides the sheet's footer, so keep it working when the screen changes. kissj's session read lists real registrations only, and a preregistered programme (kissj's `isPreregistered`, the internal `preregistered`) belongs to a role, so eventApp cannot tell whose it is: a preregistered programme is **never dimmed** and is in neither Moje nor Domů's `Můj program` (a known limitation until kissj sends the participant's role). Times of day in a range are written one way, `ProgramsModule::CLOCK` (`G:i`: no leading zero on the hour, an unspaced en dash, `8:00–22:00`) — in the sheet's Kdy, the toast, the list rows, the timeline card's name and Domů's cards; a run over two days names both (`čt 3. 6. 22:00 – pá 4. 6. 1:30`); the hour ruler keeps `08:00`.

The screen holds three views of that one data set, in a floating pill above the tab bar (`aria-label="Zobrazení programu"`, in this order): **Přehled** (`far fa-list-alt`), **Harmonogram** (the default, so the now-landing is unchanged) and **Moje** (`far fa-user`). **Harmonogram** (the timeline) is a Gantt grid: rows are the distinct `location` values (`location` is reused as the stage axis — the contract has no `stage` field, and programs with a null location fall into a `Bez lokace` row), columns are hours, one page per **day** holds every section's programmes (key `page-YYYYMMDD`), and it is the one place in the app allowed to scroll horizontally. Overlapping programs in one location are packed into sub-tracks by a greedy interval fit. A programme that runs over several days sits on the page of **every calendar day it overlaps**, each piece clipped to its day (`ProgramsModule::segments()`, at most `MAX_DRAWN_DAYS`), so no piece can stretch a day's axis; an end at exactly 00:00 belongs to the day before, so 23:45–00:00 stays one card on its evening. Every piece carries the programme id as its `data-key` — unique among siblings, which is all the morph matches on, because a page holds one piece per programme — opens the one sheet, and has the same registered state and label; a label names both days whenever the run spans more than one. The sheet, and with it the deep link, belongs to the start day's page, and the lists list the programme once, under that day. The hour scale is zoomable: everything on the grid is positioned as `calc(var(--hour-width) * n)`, so setting that one property rescales the time axis and nothing else — never `transform: scaleX()`, which would distort the programme names. `--hour-width` runs between `--hour-width-min` and `--hour-width-max` (40–200px, declared in `www/style.css` next to the property), opens at 80px, and is driven by a −/+ pair at the right end of the timeline's day strip, by a two-finger pinch on the grid (`touch-action: pan-x pan-y` on `.tl-scroll` keeps the browser's own pinch out of it; the viewport meta is deliberately left alone so page zoom still works everywhere) and by ctrl+wheel. Every step recomputes `scrollLeft` so the moment under the anchor — the midpoint between the fingers, or the centre of the visible grid for a button — stays put. The scale is kept in `sessionStorage` under `pgZoom:<slug>`, so paging and view switching preserve it and a fresh visit starts at 80px. Below a threshold the ruler thins its text to every second hour while every hour keeps its mark — the script sets `data-hour-step` on the root from the live scale and `www/style.css` hides `.tl-tick:nth-child(even) .tl-tick-label`, so tick positions never move and the leftmost hour is never blanked. The threshold is the rendered label's width plus 19px, measured on the page rather than hardcoded because themix and Montserrat differ by 6px at 14px/700. The day holding **now** carries a current-time line: every timeline page states its axis as two instants, `data-axis-start`/`data-axis-end` (`axisStart`/`axisEnd` in the page view model, `DATE_ATOM` with the offset, the provider's wall-clock read as Europe/Prague whatever the server's zone), so `www/programs.js` places now by subtraction on any phone's zone and formats only the label, through `Intl.DateTimeFormat` with `timeZone: 'Europe/Prague'`. What it writes — `data-now` on the one `.tl-page` whose axis holds now and its inline `--now-offset` in hours — the server never writes, so a morph leaves both alone, and `afterMorph()` re-runs `updateNow()` anyway. The line (`.tl-now`, inside `.tl-inner`, which is positioned for it; z-index 2, so over the cards, under the pinned stage column's 3 and the ruler's 6) and its mark on the ruler (`.tl-now-tick` with its `HH:MM` label, inside `.tl-ticks`) are in `--hour-width` units, so the zoom carries them. It updates every 30 s and on `screen:shown`, `visibilitychange` and a morph. The first plain landing inside the event (no `#section-…-program-…` deep link) opens the timeline on today's page with now a third of the way into the visible hours, even from a copy cached days ago whose server-chosen page is stale. A page's axis runs only from its first programme to its last, so before the day's first or after its last now lies on no axis: the landing then falls back to the page keyed `page-` + today's date (`formatDay()`, built from `Intl.DateTimeFormat.formatToParts` in Europe/Prague, not from a locale's printed order) and opens it without a line and without scrolling. `pgNow()` reads `window.pgClock` (a function returning ms) when set, and a `pg:tick` event on `document` re-runs `updateNow()`; both exist for the browser tests, and `BrowserTestCase::pinClock()` installs the clock over CDP before any page script and removes it after the test.

**Přehled** and **Moje** are one list component (the Twig macro `dayList(kind, days)`, built by `ProgramsModule::buildDays($programs, $registeredIds, $mineRead)`): Přehled holds every programme (`overview`), Moje only the participant's (`days`), each grouped by **day** like the timeline, each in its own view container (`#pg-view-overview`, `#pg-view-list`; the morph matches keys among siblings, so the two may reuse the day keys and the programme ids). Neither pages: every day is in the document, first to last, under its own **sticky heading**, and the reader scrolls the lot. Each item (`.pl-item`, `data-key` the programme id, `data-start`/`data-end` as `DATE_ATOM` instants from `ProgramsModule::instant()`) is a start-time column (`.pl-time`), the name as the control that opens the sheet, then `.pl-meta` (`do 12:30 · Žlutý les`), a `Přihlášen` tag (`.pl-tag`) on a registered one — in Přehled on the participant's rows, in Moje on every row — and in Moje the perex. Dimming (`.is-dimmed`, with `opacity` — never a colour, because `www/style.css` may not name one — at a strength that keeps the ink at AA) is Přehled's only among the lists, and the timeline's cards: only when the participant's list was actually read (`mineRead`), and never on a preregistered programme; logged out, or paired while `getParticipant()` failed, nothing is dimmed and Moje shows no `Zatím nemáš přihlášený žádný program.` line (the notice explains), since "not chosen" would be a guess; logged out, Moje is the link `Pro svůj program se přihlas kódem z KissJ.` to Profil. Nor does any view say `Program zatím není k dispozici.` when the list could not be read at all (`programmesUnavailable`). Each view picks its day from a **strip of day chips**, one per view and separate elements (`.pager[data-pg-pager=<kind>]` for kinds `overview`, `timeline`, `list`, holding `<div class="days" role="group" aria-label="Dny" data-pg-days="<kind>">`, the timeline's with its zoom pair beside it) — no arrows, no day menu, no dialog. Every chip is a `<button class="day-chip" data-key data-pg-page data-pg-kind>`, its `data-key` the day's own key (`page-YYYYMMDD` or `day-YYYYMMDD`) so the morph matches it by key, at least 44 × 44, and the current one carries `aria-current="true"` (the others `"false"`) and wears the `state` fill under `on-state`, as the active tab does; `aria-current` is the reader's, so every chip names it in `data-morph-keep`. On Harmonogram a chip switches the page (`showPage()`); in a list the current chip **follows the scroll** and a tap smooth-scrolls (unless reduced motion is asked for) to that day's start — the list behaviour is built per kind for every `[data-pg-pager]` whose kind has a `.pl-day` list. `markChip(kind, key)` marks the chip and brings it into its strip by setting the strip's own `scrollLeft` — never `scrollIntoView()`, which would move the window too — because a strip wider than the phone scrolls sideways (`overflow-x: auto`, no scrollbar); a strip in a hidden view measures nothing, so the view switch brings its chip round when it is shown. The strip keeps `--pager-height`, so the band below stays where it was. Nothing of this runs on a scroll event: an `IntersectionObserver` watches the day sections against a band starting one pixel below the strip — one pixel, because a day scrolled to its own start puts its top edge and the previous day's bottom edge on the same line and an observer asked about that line answers "both" — and each crossing costs one coalesced `requestAnimationFrame` that reads no geometry. The day owning the top of that band is the day whose heading is stuck there, so the strip and the heading cannot disagree — which holds only because `.pl-head`'s dock line, `bandTop()` and the observer's `rootMargin` all read the **same three tokens**, `--appbar-height` + `--appbar-inset` + `--pager-height`. Leaving the safe-area inset out of any one of them docks the heading behind the strip on a notched install (34px, measured). The observer fixes its margin at creation, so an inset that changed at runtime would leave the band stale until it is rebuilt; nothing does that yet. `.pl-day:last-child` carries a `min-height` of the reading band, or the last day could never dock under the strip and its chip would land short of it. In Moje `updateNow()` marks the list from the reader's clock with a client-owned `data-now`: `running` on every item whose span holds now, and `next` on the first item still to start on the day that is today (a list read the evening before shows nothing). CSS hangs a `probíhá` chip in the running card's top-right corner (`.pl-item[data-now="running"]::after`, on the card rather than in `.pl-time`, so it escapes the time's 0.75 opacity, with `.pl-time` padded to leave it room) and draws the "teď" line with its `teď` chip above the next one; both chips are small fills of `--now` under `--on-action`, the timeline label's pair, AA by construction — never `--now` as ink, since it is the action fill and as text on a pale ground falls to 2.8:1 (`ThemingTest::testTheNowChipsCarryTheirInkAtAA` measures the pair in every set). The list never scrolls to it. The screen's scroll offset is live state like everything else, so leaving a list and coming back lands where the reader was; switching to Harmonogram and back does too, because that view is exactly one screenful and the browser clamps the window's scroll while it is up, so `showView` saves and restores it. A perex is plain text whose `\n`s are meant (`docs/kissj-contract.md`), so `.sheet-perex` and `.pl-perex` are `white-space: pre-line` and the template puts nothing but the escaped text inside them.

Tapping a programme opens its **sheet**: the name, the section as a tonal chip (`.sheet-chip`), `<dl class="sheet-facts">` with `Kdy` and `Kde`, `Tvůj program` on a registered one, the organisers' messages about it (`Oznámení`, each with its `data-sent-at` time), the perex, and a `.sheet-footer` with exactly one child keyed by its state (so a morph from unregister to register replaces the form rather than patching it, and no whitespace inside, or `.sheet-footer:empty` stops matching) from `ProgramsModule::footer()`, in this precedence: not paired → `unpaired`, a link to Profil `Pro přihlašování se přihlas kódem z KissJ`; then the window — `before` `Přihlašování začne 15. 3. 2027 v 18:00`, `after` `Přihlašování skončilo`, `none` `Přihlašování zatím není otevřené` (no trailing period); then, paired and open, `fixed` (nothing) for a preregistered programme, nothing at all while the participant's own list could not be read, else `register` (`Přihlásit se`, `.btn-primary`) or `unregister` (`Odhlásit se z programu`, two-tap `Opravdu odhlásit?`). A window that cannot be read leaves every paired footer empty. **Registration** is a plain form POST — `POST /programy/{id}/prihlasit` (`program-register`) and `/odhlasit` (`program-unregister`) — so the worker's purge-on-write and the loader's "every non-GET is a navigation" keep every screen consistent: `SameOrigin` (else a 403 page), not paired → 403 with `Pro přihlašování se přihlas kódem z KissJ.`, then `register`/`unregister()` with the session token, and a toast left in the session: `Přihlášen: <name>` with `ProgramsModule::toastLine()` (`Pá 21. 5. · 9:00–12:30 · Žlutý les`: the capitalised short weekday, `j. n.`, the `CLOCK` range, the place when there is one; a run past midnight names its start day only), `Odhlášen: <name>` with `Místo jsme uvolnili`, a refusal's Czech line from `REFUSALS` (an unknown code `Přihlášení se nepodařilo.` or `Odhlášení se nepodařilo.`), an outage (`TransferException`, `ProgramDataException`, the stub's `LocalStateException`) `Přihlášení se teď nedaří, zkus to prosím později.` or `Odhlášení se teď nedaří, zkus to prosím později.`, and a `SessionExpiredException` the logout as everywhere. A repeat's refusal (`alreadyRegistered` after a register, `notRegistered` after an unregister) does not replace the same write's success toast still waiting unseen (`Kernel::putToastUnlessPending()`, matched by the `tag` `register:<id>`/`unregister:<id>` under one session lock). The answer is a 302 to `/programy#section-<sectionId>-program-<id>`, whose full document takes the toast (the toast is `.pg`'s first child, keyed `toast`) and reopens the sheet under it. `www/programs.js` disables the button on submit (enabled again on `pageshow`) and notes the view the write was sent from in `sessionStorage['pgReturn:<slug>']` (`{id, view, at}`), taken once on landing, so the reader comes back to Přehled, Harmonogram or Moje with the sheet open; a deep link without the note (or for another programme, or older than a minute) opens the timeline as before. The `#section-<id>-program-<id>` deep link opens the right sheet, puts the timeline on its page, and parks the personal list on that programme for when the reader switches to it; `#muj-program` opens Moje and `#muj-program-<id>` opens Moje on that programme with its sheet open. An open `.sheet` is a real dialog — the screen's only one: everything outside it goes `inert` — the app bar, the tab bar, the skip link, the sibling screens — except the toast, which paints above the sheet (a higher `z-index`, never over the sheet's own close button) and whose `✕` stays in the sheet's Tab ring, and Tab rings inside the card, because a modal a reader can tab straight out of is not one. The trap remembers exactly which elements it marked, so closing clears its own and nothing else, and it releases *before* the focus returns to the opener, since an inert element cannot take focus. Opening the sheet also pushes a history entry (`{pgOverlay: true}`, replaced rather than stacked when one is already up), so Android's Back closes it instead of leaving the screen with the rest of the app inert, and closing it any other way goes back over that entry once, with `history.scrollRestoration` held at `manual` while an overlay entry is up so the browser does not restore the scroll it saved; an open asked for while a close's `history.back()` is still in flight waits for it. A day chip opens nothing and pushes no entry. Chrome's history-manipulation intervention may let Back skip an entry pushed without a user gesture (the sheet a deep link opens on landing), so the entry is no guarantee; the backstop is that `popstate` on any entry and `screen:hidden` on the Program screen close the sheet and release the trap, which can leave an orphan entry costing one idle Back — accepted. The sheet's elements are looked up on every use rather than held from the first render, and every child of `.pg` carries a `data-key` (`toast`, `notice`, `pager-<kind>`, `tabs`, `sheet`) or an id (the three views), because the morph matches unkeyed siblings by position and once turned a reference to the sheet into the old day panel. There is no favourite, photo, capacity or attendee count. `ProgramsModule` does all the grouping in PHP and hands Twig a finished view model; every page and every sheet is rendered into the DOM so the deep link can open a sheet on any of them.
