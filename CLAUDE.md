# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Modular support web app for Czech scout events (Obrok). Built on Slim 4 (PHP >= 8.3). One codebase serves multiple events — each event is a config + content directory under `events/<slug>/` plus public assets under `www/events/<slug>/`, selected at runtime via the `EVENT` env var. Code is in English — comments, docblocks, exception messages, identifiers. Czech is reserved for what users actually read: UI strings in `templates/`, per-event content under `events/<slug>/content/`, user-facing notices and flash messages, and the weekday names in `Kernel`. Commit messages and `docs/` are in English without AI-authorship trailers (the existing `docs/deployment.md` and `docs/kissj-contract.md` predate this and are still Czech).

## Commands

- `docker-compose up` — run the dev server (PHP built-in server inside `php:8.3-alpine`), then visit `localhost:8080`
- `composer start` — alternative: run locally via `php -S localhost:8080 -t www/`
- `composer test` / `vendor/bin/phpunit` — run tests (PHPUnit 11, config in `phpunit.xml`, suites `Unit` + `Functional`)
- `vendor/bin/phpunit --filter testGetHomepage` — run a single test

Before running, copy `.env.example` to `.env` and set `EVENT=obrok19` (the reference event) and `APP_DEBUG=1` for dev.

## Architecture

`www/index.php` is a 3-line front controller: it requires the Composer autoloader and calls `App\Kernel::create()->run()`. All bootstrap logic lives in `src/Kernel.php` — no `settings.php`/`dependencies.php`/`middleware.php`/`routes.php` split, no route closures scattered across a routes file.

`Kernel::create()`:
- Loads `.env` (if present) and reads the `EVENT` env var to pick which event to serve; loads `events/<slug>/config.php` via `EventConfig::load()`.
- Builds a PHP-DI container (`ContainerBuilder`) with the event, the program provider, `Session`, `Auth\Authenticator`, `Auth\SkautisGatewayInterface`, and Twig as definitions.
- Creates the Slim 4 `App`, adds body-parsing/routing middleware, Twig middleware, and error middleware (`APP_DEBUG` controls whether error details are shown).
- Registers core routes (`GET /` homepage, `POST /` SkautIS login/logout) directly, then iterates `$event->features` and registers one module per enabled feature.

`EventConfig` (`src/EventConfig.php`) loads and validates `events/<slug>/config.php` (requires `name`, `colors`, `features`; also carries `sections`, arbitrary `raw` data via `get()`, and `dir` for locating fixtures/content). `EventConfig::content(string $name)` loads `events/<slug>/content/<name>.php`, a plain PHP file returning an array (e.g. `content/links.php`, `content/news.php`, `content/schedule.php`) — these are per-event, not code.

Modules implement `App\Module\ModuleInterface` (`key()`, `menuItem()`, `registerRoutes()`) and live in `src/Module/`. `ModuleRegistry::classFor($feature)` maps a feature-flag string (from the event's `features` array in its config) to a module class — this is how features are toggled per event, e.g. `NewsModule`, `LinksModule`, `MapModule`, `HandbookModule`, `ProgramsModule`. `PushModule` (web push notifications) is implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and a token-gated `GET/POST /admin/notify` (shareable link with `?token=<ADMIN_TOKEN>`) sends notifications through `App\Push\PushSenderInterface`/`WebPushSender`.

Program/schedule data goes through `App\Program\ProgramProviderInterface` (`getPrograms()`, `getProgramsForIdentity()`). `StubProgramProvider` reads `events/<slug>/fixtures/programs.json` and `fixtures/registered.json` — no network calls, safe for dev and tests. `KissjProgramProvider` (Guzzle-based) talks to the real kissj registration API. `Kernel` switches between them via `PROGRAM_PROVIDER=stub|kissj` in `.env` (default `stub`); `kissj` additionally requires `KISSJ_BASE_URL` (`Kernel` throws a `RuntimeException` otherwise) and uses the event's slug unless overridden by the per-event config key `kissj.eventSlug`. Confirm `docs/kissj-contract.md` against the real kissj API before flipping a production event to `kissj`.

SkautIS SSO lives under `src/Auth/`: `Authenticator` (session-backed login state), `SkautisGatewayInterface` + `SkautisGateway` (wraps `skautis/skautis`), `Identity` (value object for a logged-in skautis or TIE-code participant), `UnknownParticipantException`. Login happens via `POST /` with a `skautIS_Token` form field; logout via `skautIS_Logout`.

Theming: each event's `config.php` has a `colors` map (e.g. `base`, `darker`, `primary`, `text`, `text-invert`, and the optional `nav-active`) and an `assets` map (logo/favicon paths under `www/events/<slug>/`). `Kernel` exposes the whole event config as the `event` Twig global; `_layout.twig` emits the colors as `--color-*` CSS custom properties in an inline `<style>` block, and `www/style.css` consumes them (`var(--color-base)`, etc.) — no per-event CSS files, one shared stylesheet. `EventConfig::REQUIRED_COLORS` is checked at boot, so a half-themed event fails to start rather than rendering with unset properties. `www/style.css` must never name a colour itself; `ThemingTest::testCoreStylesheetHasNoColorLiterals` enforces that.

Next to `colors` sits an optional `theme` map (`EventConfig::$theme`, always an array) for the look-and-feel that is not colour — `font`, `font-display`, `font-display-weight`, `font-url` (which becomes a stylesheet `<link>` instead of a property), `radius`/`radius-pill`/`radius-sheet`/`radius-card`, and `motion`. It is emitted as `--theme-*` in the same inline `<style>` block.

Colour is **semantic roles**, not palette keys. No rule in `www/style.css` names a `--color-*` any more; every one reads a role, and the role definitions in `:root` are the only place the palette is touched (`ThemingTest::testNoRuleInTheStylesheetNamesAPaletteKey` enforces exactly that). The rule that keeps the system honest is **one colour, one role** — if an event's lime is `state`, lime is not also a ground, a surface or a piece of chrome. The set is sized for a 60:30:10 budget: `ground`/`on-ground` with `surface`/`on-surface` as its one block tier (60), `structure`/`on-structure` for the bars, the buttons and the timeline's chrome (30), and `action`/`on-action`/`action-link` plus `state`/`on-state` sharing the 10, with `edge`, `edge-width`, `heading`, `emphasis` and `scrim` in support. `structure` defaults to `--color-darker` rather than `--color-base`: it is the one role that is a filled ground under inverted type at body size, and obrok19's base carries `--color-text-invert` at 3.85:1 where its darker green reaches 6.84:1. Three scopes **rebind** the core roles rather than adding names: a text field, `.sheet-card` and `.tl-scroll` are each their own little surface with their own structure on it, so the grid's cards are simply `structure` in the grid's scope. The rebinding sits on `.tl-scroll` and not on `.pg` because custom properties inherit — on `.pg` it would also reach the pager, the day panel and the view tabs.

One role sits beside `structure` rather than inside it: `signature`/`on-signature`, **structure that carries the identity**. It behaves like structure — a filled band of chrome with type on it — but its value is the event's own colour, and the **hour ruler is its only use in the app**; painting a second surface with it would return the screen to the state where nothing could read as an accent (`ThemingTest::testTheIdentityRoleIsUsedByTheHourRulerAndNothingElse` holds it to one). The stage column has its own pair (`stage`/`on-stage`) in the grid's scope for the opposite reason: the cards need a fill that separates from the grid on its own, while the column wants a cast of the event's hue and the darkest ink-to-ground ratio it can hold, and one value cannot do both. Both pairs fall back to the grid's own `structure`, so an event that declares neither renders exactly as it did.

Every role falls back to exactly the expression its rules used before roles existed, so an event that declares none renders precisely as it did; obrok19 declares none and proves it with a pixel diff. It is no longer *frozen* — its `structure` tier moved from `--color-base` to `--color-darker` to clear AA, which is the only sanctioned change to it — but it is still the control for every fallback, and a diff against `docs/baseline/obrok19/` is how a round shows it did not disturb one. An event that wants its own colours declares `roles` as two **hand-authored** sets, `light` and `dark` (`EventConfig::$roles`) — accents do not survive mechanical inversion, so changing a colour is deliberately a two-place edit. `_layout.twig` emits light as the base, then the dark set twice: once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-mode="light"])` so the device's setting works without JS, and once under `:root[data-mode="dark"]` so an explicit choice wins. A tiny **inline script in `<head>`**, before the stylesheet link, sets `data-mode` from `localStorage['obrokColorMode']` (global, not per event) or from `prefers-color-scheme` — never the deferred script at the foot of the page, or the reader sees a frame of the wrong theme. A sun/moon `<button>` in the app bar flips it, and appears only for an event that declares a dark set. Dark mode tells structure apart from the ground with a **thin accent edge** (`--edge-width`, 0 in light) rather than a lifted tone, so outlines exist in dark mode and nowhere else.

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link) and a fixed bottom tab bar built from the enabled features and sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Login lives on `/profil` (core routes, not a module) and the app bar reads the current identity through the `auth_identity()` Twig function rather than a global, because a handler can log the user out during the same request that renders the bar.

`ProgramsModule` (`/programy`) is the single Program screen. The hand-authored schedule (`content/schedule.php`) and the separate harmonogram screen are gone: everything the screen shows comes from `ProgramProviderInterface`. When a participant is logged in, the module also calls `getProgramsForIdentity()` and marks their programs `registered` — that marking is the only thing login affects, so keep it working when the screen changes. The API is expected to grow to carry the non-registerable items too (budíček, nástupy, táborák), which is what the old schedule file used to hold.

The screen holds two views of that one data set, built from the Figma flows *Registrace programů* and *Burza (Var. 2)*, and a floating pill above the tab bar switches between them client-side. **Timeline** is a Gantt grid: rows are the distinct `location` values (`location` is reused as the stage axis — the contract has no `stage` field, and programs with a null location fall into a `Bez lokace` row), columns are hours, and it is the one place in the app allowed to scroll horizontally. Overlapping programs in one location are packed into sub-tracks by a greedy interval fit. The hour scale is zoomable: everything on the grid is positioned as `calc(var(--hour-width) * n)`, so setting that one property rescales the time axis and nothing else — never `transform: scaleX()`, which would distort the programme names. `--hour-width` runs between `--hour-width-min` and `--hour-width-max` (40–200px, declared in `www/style.css` next to the property), opens at 80px, and is driven by a −/+ pair at the right end of the timeline's pager row, by a two-finger pinch on the grid (`touch-action: pan-x pan-y` on `.tl-scroll` keeps the browser's own pinch out of it; the viewport meta is deliberately left alone so page zoom still works everywhere) and by ctrl+wheel. Every step recomputes `scrollLeft` so the moment under the anchor — the midpoint between the fingers, or the centre of the visible grid for a button — stays put. The scale is kept in `sessionStorage` under `pgZoom:<slug>`, so paging and view switching preserve it and a fresh visit starts at 80px. Below a threshold the ruler thins its text to every second hour while every hour keeps its mark — the script sets `data-hour-step` on the root from the live scale and `www/style.css` hides `.tl-tick:nth-child(even) .tl-tick-label`, so tick positions never move and the leftmost hour is never blanked. The threshold is the rendered label's width plus 19px, measured on the page rather than hardcoded because themix and Montserrat differ by 6px at 14px/700. **Můj program** is a plain list of `getProgramsForIdentity()` only, and it pages by **day alone** while the timeline pages by (day, section): a participant has roughly eight programmes across the whole event, so nine (day, section) pages would leave most of them empty — `ProgramsModule::buildDays()` is the one that does it. When a participant is logged in, programs they are not registered for are dimmed with `opacity` — never a colour, because `www/style.css` may not name one; logged out nothing is dimmed, since "not chosen" would be a lie. A pager under the app bar steps through pages, and tapping a program opens a modal. Everything is read-only: the screen never registers anybody for anything, which is why the Figma heart/favourite component is deliberately absent, along with its photo, capacity and attendee-count fields. `ProgramsModule` does all the grouping in PHP and hands Twig a finished view model; every page is rendered into the DOM so the `#section-<id>-program-<id>` deep link can open a modal on any of them.

Tests: `tests/Unit/` (`EventConfigTest`, `ModuleRegistryTest`, `StubProgramProviderTest`, `KissjProgramProviderTest`, `KernelProviderSelectionTest` — asserts `PROGRAM_PROVIDER=stub|kissj` picks the right provider — `AuthenticatorTest`, `SessionTest`, `SubscriptionRepositoryTest`, `EnvironmentTest`) and `tests/Functional/` (one app instance per test via `Kernel::create()`, exercising real routes end-to-end: `HomepageTest`, `LoginTest`, `ProgramsTest`, `TieLoginTest`, `NewsModuleTest`, `LinksMapTest`, `HandbookTest`, `ThemingTest`, `Obrok27Test`, `PushSubscribeTest`, `AdminNotifyTest`, `ProviderFailureTest`). `tests/Functional/AppTestCase::createApp()` boots the real app against event fixtures — either a real event under `events/<slug>/` or a minimal fixture event under `tests/fixtures/events/` — and returns the real Slim `App`/response. No test hits a live external API; everything program-related comes from the stub provider's JSON fixtures.
