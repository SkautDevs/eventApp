# Service worker

This document covers `www/sw.js` as the offline copy: what it caches and when, how it serves each kind of request, and how it purges after a write.

## Install and the precache list

**The worker is the offline copy.** Its `install` fetches `/<slug>/precache.json` (with `cache: 'no-store'`; core route `precache`, built by `App\Http\Precache`: `documents` = Domů, every tab in tab order (`Kernel::menu()`), `/profil` and `/offline`; `assets` = the stylesheet and scripts through `AssetVersion` (`style.css`, `app.js`, `shell.js`, `push.js`, `profile.js`; `programs.js` only for an event with the `programs` feature and `map.js` only for one with `map`, as the layout loads them), the manifest, the layout's icons, every non-empty `assets` path, `homepage.footerLogo`, `map.image` (the plan is the map that works offline), the manifest's icons and `Fonts::files(EventConfig::fontFamilies())` — the event's own fonts and Font Awesome, nothing it does not render with — a file missing on disk is left out, because one 404 fails the whole install; `optional` = the handbook when its file exists; `version` = 8 hex of sha256 over the sorted `documents`, `assets` and `optional` lists, so an enabled tab or a new handbook is a new version too) and fills the cache `eventapp-<slug>-<version>` with every document in both forms and every asset, writes the list itself into that cache **last** — after the documents and assets, before the optional entries, which may fail one by one — and then calls `skipWaiting()`. The worker's own document fetches (`storeBoth()`, for the fill and the refill) carry `X-Worker-Fill: 1`, so they take no pending toast. The stored `precache.json` is the completion marker: a fill that fails deletes its own half-filled cache, a target cache that already holds the marker is adopted as it is (a redeployed `sw.js` with an unchanged list reuses it rather than refetching), and `currentCache()` and `activate` adopt only the newest of the event's caches that holds it — never one still filling, or abandoned when the browser killed a worker mid-fill. Two fills of one version (a new worker's install and an old worker's `checkVersion()`) could delete the cache under each other's handle, so `adopt()` first re-checks through a fresh handle that the cache still exists and holds the marker (`isComplete()`: `caches.has()` plus the marker) and deletes the other caches only then, `install` fails when its own fill was lost that way, `activate` clears `cacheName` when nothing was adopted, and a failed fill deletes its cache only if the marker is still missing.

## Activation and new versions

`activate` then deletes the event's other caches, `clients.claim()`s and posts `sw-activated` (nothing reloads); when no complete cache exists it deletes nothing. `sw.js` itself is never versioned, so a deploy that changes an asset but not the worker never reaches `install` — the browser reinstalls a worker only when its script changes. That is `checkVersion()`'s job: once per worker lifetime, after a page was served from the network, it fetches `precache.json` with `cache: 'no-cache'` and, on a different `version`, fills the new cache, adopts it, deletes the others and posts `sw-activated` — unless a newer worker has become the active one meanwhile, whose cache it would otherwise delete; it does not run at all (and does not count as done) while a worker is `installing` or `waiting`, because that one fills the version itself; any failure leaves the current cache.

## Strategies

The Cache API keys on the URL alone, so a fragment is stored under its URL plus `?x-screen=1` — in the cache only; no page links to it. Strategies: a hashed asset (a root `*.css`/`*.js` with `?v=`) and anything under `/fonts/` or `/vendor/` cache-first; an unversioned file under `/events/<slug>/` stale-while-revalidate, its network leg fetched with `cache: 'no-cache'` because nginx and `.htaccess` give the extension-matched files there (png, svg, jpg, webp, ico, woff2, css, js — not `site.webmanifest`) a year of `immutable` and a plain fetch would never get past the HTTP cache; a page (`navigate`) network-first — after 3 s the cached copy is shown if there is one (without one it keeps waiting), a failed fetch or `navigator.onLine` false goes to the cache, and `/offline` (`templates/offline.twig`) answers when there is neither — a page carries the identity, so it never comes from the cache while the network answers; a fragment from `load()` stale-while-revalidate, posting `screen-updated {path}` to that window when the server's copy differs (compared without `data-fetched-at`/`data-stale`, or every `local` screen would differ on every fetch); a fragment from `revalidate()` (`cache: 'no-cache'`) network-first, its cache fallback carrying `X-From-Cache: 1` so the loader does not take an offline answer for a confirmation — it neither resets the screen's `fetchedAt` nor skips the real check for five minutes once the signal is back. Every successful page and fragment is stored, except one carrying `X-Toast: 1` (`toasted()`), which is shown and never stored; `reconcile()` and `refill()` still run after it, so the offline copy is fetched again without the toast.

## Purge on write

Every same-scope non-GET except under `/admin/` and `/push/` deletes every `text/html` entry, from **every** `eventapp-<slug>-*` cache (a fill still running holds pages of the identity before too), once the server has answered it and before that answer reaches the page. A write that cannot reach the server — `navigator.onLine` false, where it is not even tried, or a fetch that fails — purges nothing and is answered by the worker with a **303 back to the request's same-origin referrer plus `#offline`** (`offlineRedirect()`; the event's home when the referrer is empty or from elsewhere, never a bare `#offline` on nothing), which the page then serves from the cache like any offline navigation and `shell.js` turns into the offline toast — never the browser's error page, which an installed iOS app has no Back button out of. (Purge on write: a login or a logout never serves a screen rendered for the other identity, and a register or unregister never leaves an old registered marking; a push subscribe changes no rendered HTML, and purging there would empty the offline copy with nothing to refill it until the next navigation.) The next page that arrives from the network refills the missing documents for the identity now in the cookie. A purge also bumps a counter that every page and fragment write captures when its request starts, and a write that started before a purge is dropped rather than stored for the old identity (a login during the very first install is a request the not-yet-active worker never sees; so every page that arrives from the network is also **reconciled** — `reconcile()` reads its `push-identity` meta, the participant id, and when any other stored full page was rendered for a different identity it purges every page and fragment, which `refill()` then puts back for the cookie's identity).

## Server errors, costs and what is never touched

A page whose network answer is a 5xx gets the cached copy when there is one and the server's error page when there is none — never `/offline` while the server answers. A fragment that turns out changed costs two network fetches (the worker's background fetch, then the loader's `no-cache` revalidation after `screen-updated`); an unchanged one costs one. `/admin/*`, `/push/*`, `/precache.json`, the pairing poll `/profil/propojit/stav` (it must reach the server every 5 s, and as a GET it purges nothing), `/health`, other events and other origins (only the map's iframe is left) are never touched. Rollback is a `sw.js` with the push handlers and an `activate` that deletes every `eventapp-<slug>-*` cache.
