# Bootstrap and config

This document covers the shipped events, how a request becomes an event's app in `src/Kernel.php`, the event config and its content files, and the modules: the registry, core and feature modules, their actions, and the tab bar.

## The events

Five events ship: `obrok19` (the reference), `obrok27` (19.-23. 5. 2027, the official brand kit), `korbo26` (the former `korbo`), `navigamus27` (3.-6. 6. 2027; its programmes are still the 2025 side programme, moved 104 weeks on; its look is the 2027 identity from the organisers' manual, mirrored from kissj's Navigamus 2027 skin: deep purple, Seatren and Luciao Sans, a wavy purple app bar and wavy cards in `www/events/navigamus27/style.css`) and `miquik26` (unlisted: its lecture data is in, its date is invented). obrok19 and obrok27 enable `map`, `programs`, `handbook`, `info` and `push`; navigamus27 enables `programs`, `map`, `push` and `info`; korbo26 and miquik26 enable `programs`, `push` and `info`. Two of them are **unlisted**, i.e. absent from the picker but reachable by URL: `miquik26` and `obrok19`, neither of which has a `listed` key at all, so both default to unlisted (obrok19 is served at `/obrok19/`). **korbo26, navigamus27 and miquik26 wear kissj's design**, adjusted to eventApp's contrast rules. A slug matches `/^[a-z0-9-]+$/` and ends in a two-digit year. Every event's fixtures know one participant, kissj's participant id `1` (`registered.json`: korbo26 6 programmes, obrok19 and obrok27 8, miquik26 5, navigamus27 2); only korbo26 names them in `participants.json` (`Jana Nováková`), so elsewhere the paired reader is `Účastník`. Registration windows (`registration.json`): korbo26 open 2020–2099, obrok27 from 15. 3. 2027 18:00 to the event's start; the others have none. An event's `config.php` may also carry `listed` and `dates` (`start`/`end`), which the picker uses to split upcoming from past and Domů uses for its phases; the three listed events carry both, while `miquik26` and `obrok19` carry neither.

**korbo26 as the dev event.** Served on its own as `CLAUDE.md` shows, with the `local` source. On Profil, `Přihlásit kódem z KissJ` pairs at once (the `local` source approves the first poll) as the fixture participant 1, Jana Nováková, registered for 6 programmes; korbo26's registration window is open (2020–2099), so the sheet registers and unregisters. Those writes land in `var/stub/korbo26.json`; delete it to get the fixtures' registrations back.

## Front controller and boot

`www/index.php` is a 3-line front controller: it requires the Composer autoloader and calls `App\Kernel::boot($_SERVER['REQUEST_URI'] ?? '/')->run()`, which picks the event from the first path segment (see `Kernel::boot()` below). All bootstrap logic lives in `src/Kernel.php` — no `settings.php`/`dependencies.php`/`middleware.php`/`routes.php` split, no route closures scattered across a routes file.

A script request never reaches it. Scripts are linked as `/js/<hash>/<path>` (`script_url()`, `App\Http\ScriptVersion`, registered in `Container\Definitions`; how the hash is made is in [shell-and-loader.md](shell-and-loader.md)), and the server serves that as the file `www/js/<path>`. Three rules do this, one per server, and they must agree: `rewrite "^/js/[0-9a-f]{8}/(.+)$" /js/$1 last;` at server level in `docker/nginx.conf`; `RewriteRule ^js/[0-9a-f]{8}/(.+)$ js/$1 [L]` directly after `RewriteEngine On` in `www/.htaccess` (placed after the two `RewriteCond` lines, it would take them from the front controller rule and send every static file to `index.php`); and `eventapp_script_file()` in `bin/script-path.php`, which `bin/router.php` (the dev server and the browser tests) and `tools/Gate/front.php` (the gates) call, because the PHP built-in server cannot be told to serve a different file. `DeploymentFilesTest` keeps the three in step. Any 8 hex digits are accepted, not only the current hash, and a path with no file under `www/js/` falls through to the app's 404.

`Kernel::boot($_SERVER['REQUEST_URI'])` loads `.env` (if present) and looks at the first path segment: if `EventCatalog` knows it, `Kernel::create()` builds the app for that event; otherwise `Kernel::createInstance()` builds the instance-level app that serves the picker at `/` and Slim's 404 for the rest. Nothing is configured per deployment about which event is served. Every environment variable is read through `App\Environment`, a snapshot `Kernel` takes when it builds an app; its docblock lists the variables, which of them are per event (`<NAME>_<SLUG>`) and which instance-wide, and how each is looked up.

## The reader's address, logging and time zone

The reader's address is `Http\ClientIp::of()`: `X-Forwarded-For` is read, `TRUSTED_PROXY_COUNT` hops from its right end, only when the connection comes from a loopback or private address (an IPv4-mapped one judged as its IPv4) or from one `TRUSTED_PROXIES` names (comma-separated addresses or CIDRs, a malformed entry skipped; only the immediate peer is matched, the inner hops are trusted by the count); otherwise it is `REMOTE_ADDR`. Both limits — the pairing start's and the push subscribe one — count by `ClientIp::throttleKey()`, which is that address for IPv4 and its /64 for IPv6, with `::ffff:` unwrapped. A 404 or 405 is not logged (`src/QuietErrorHandler.php`), and `Time\Zone::PRAGUE` is `Europe/Prague`.

Every read of the current time goes through the container's PSR-20 `ClockInterface` (`Time\SystemClock`), so a test pins the time with a fixed clock, and every date the app formats or compares is a Prague one (`Time\Zone`); both docblocks say why.

## Building an event's app

`Kernel::create()`:
- Calls `Environment::programSource()` first (see the provider below), then builds a PHP-DI container (`ContainerBuilder`) from `Container\Definitions::forEvent()`, with the event, the program provider, `Session`, `Auth\Authenticator`, `Auth\PairingThrottle` and Twig as definitions.
- Creates the Slim 4 `App`, adds body-parsing/routing middleware, Twig middleware, and error middleware (`APP_DEBUG` controls whether error details are shown), and then the session-cookie and screen middleware, *outside* the error middleware rather than inside it; the security headers, `Http\CspMiddleware` and `Telemetry\TransactionMiddleware` now wrap it in turn ([http.md](http.md) has the full order). Why outside: `Http\ScreenMiddleware`'s docblock.
- Registers the routes of every module the event has (`registerModules()`, below): the core ones — `GET /<slug>/` (Domů), `GET /profil`, the pairing routes `POST /profil/propojit`, `GET /profil/propojit/stav` and `POST /profil/odpojit` (below), the offline page `/offline` and the worker's `/precache.json` — and one module per enabled feature, then hands Twig the tab bar.

The full middleware order, innermost to outermost, is in [http.md](http.md); the source `Environment::programSource()` checks is described in [program-provider.md](program-provider.md), and the pairing routes in [auth-and-session.md](auth-and-session.md).

## Event config and content

`EventConfig` (`src/EventConfig.php`) loads and validates `events/<slug>/config.php` (requires `name`, `colors`, `features`; refuses an event that enables `info` without `push`, because Informace lists the sent notifications; validates `dates` and `csp`) into readonly typed properties, one per key the app reads: `slug`, `dir` (for locating fixtures/content), `name`, `shortName`, `listed`, `dates`, `features`, `colors`, `theme`, `roles`, `csp`, `assets`, `homepage`, `map` and `handbook`. The nested ones are value classes under `src/Event/` — `EventDates`, `EventRoles`, `EventAssets`, `EventHomepage`, `EventMap`, `EventHandbook` — and each docblock names its keys. A config of the wrong shape fails at boot like one missing a key: a `name` that is not a string, `features` that are not a list of strings, a `colors`, `theme` or role map whose values are not strings, `roles`, `dates` or `csp` that are not maps. A number in one of those maps is taken as its string (`700` as `'700'`), which is how the layout always printed it, so an integer or float theme value still boots. Every other value is kept as the config gives it: a declared `''` stays `''` and an undeclared key is null, which the templates treat alike. `EventConfig` is the `event` Twig global as it is, so a template's `event.map.image` is a property path.

An event's per-event content, not code, is two plain PHP files under `events/<slug>/content/`, each returning an array: `links()` reads `links.php` as a list of `Event\Link` (`[]` without the file) and `emergency()` reads `emergency.php` as an `Event\Emergency` with its `EmergencyContact`s (null without the file). Both read leniently, a missing field being `''` or null.

Three orders in the config are part of the page, so `EventConfig` keeps each one as the config writes it, and a map stays a PHP array rather than an object with fixed properties: the keys of `colors` and `theme`, which `_layout.twig` emits into the inline `<style>` in that order; the keys of the two role sets, `roles->light` and `roles->dark`, emitted the same way; and the asset paths, which `EventAssets::paths()` hands to `precache.json` in the config's own key order — every declared non-empty path, a key no property names included, the `stylesheet` left out because `Precache` lists it by its versioned URL.

What `content/links.php` and `content/emergency.php` hold, and where they are shown, is in [info.md](info.md).

## Modules, actions and the tab bar

Modules implement `App\Module\ModuleInterface` (`menuItem()`, `script()`, `stylesheet()`, `registerRoutes()`) and live in `src/Module/`. `ModuleRegistry::classFor($feature)` maps a feature-flag string (from the event's `features` array in its config) to a module class — this is how features are toggled per event: `info` (`InfoModule`), `map` (`MapModule`), `handbook` (`HandbookModule`, no tab of its own: the handbook is the first of Informace's quick links), `programs` (`ProgramsModule`) and `push` (`PushModule`). The tab bar is Domů (the event's `shortName` with its `menuLogo`, or the `fa-home` icon) followed by the modules' items in their `order`: Program (10), Místa (20), Informace (30) for the enabled features, and Profil (40, `ProfileModule`, core, so every event has it and it is always the last tab: `fas fa-user-circle`, or the paired reader's initials). obrok19, obrok27 and navigamus27 show five tabs; korbo26 and miquik26, without Místa, four. A `MenuItem`'s `aliases` are route names whose URLs are the tab's other addresses, the views of its screen with a path of their own: Program's are `programs-overview` and `programs-mine`, Místa's `map-plan`. The tab renders them, through `url_for()` and in that order, as `data-screen-aliases="/<slug>/programy/prehled /<slug>/programy/moje"`, and a tab without aliases renders no attribute.

Each module has a directory of its own, `src/Module/<Name>/`: the module class, an action class per route, and whatever only that screen uses (`HomeModel`, the Program screen's builders, the admin page's `AdminSession` and `AdminPageRenderer`). Three modules are **core**, part of every event whatever its `features` (`ModuleRegistry::CORE`): `Shell\ShellModule` (the offline page and the worker's precache list), `Home\HomeModule` (Domů) and `Profile\ProfileModule` (Profil and the pairing routes). `Admin\AdminModule`, the organisers' admin page, is no feature of its own: `ModuleRegistry::classesFor()` adds it to every event that enables `push`. `ModuleRegistry::ORDER` is the one order the modules are taken in, and so the order their routes are registered in; `modulesFor()` is an event's core and feature modules in that order. `Module\Modules` builds them from the container once per app, `Kernel::create()` registers their routes from it, and `Modules::menu()` — every module's `MenuItem`, sorted by `order` — is both the `menu` Twig global the tab bar is drawn from and the tab order of the worker's precache list. `Modules::scripts()` is the layout's script entries and `Modules::sheets()` its stylesheets, both in module order ([shell-and-loader.md](shell-and-loader.md), [theming.md](theming.md)).

**Actions, and why they are lazy.** A module is built for every request, so its constructor takes only what costs nothing to build (`ModuleInterface`'s docblock). Every route is an action class (`ShowAction`, `RegisterAction`, …) that Slim takes from the container only when that route runs, so an action's constructor takes the services its route needs — the provider, a repository, a throttle — without any other page paying for them. The repositories and the throttles are lazy services besides (`Container\Definitions`), so even a running action opens the database only on its first call to one: Domů reads the message log only from the event's start, and the pairing start counts an attempt only after its checks. `KernelBootTest` and `ModuleBootTest` hold both: booting and building every module of every event open no database, and the screens that need none open none.

**Pages.** Every screen's template is rendered from one readonly page object in its module's `View/` directory — `Home\View\HomePage`, `Programs\View\ProgramsPage`, `Map\View\MapPage`, `Info\View\InfoPage`, `Profile\View\ProfilePage` and `Admin\View\AdminPage` — whose public properties are exactly that template's top-level variables; the action renders `View\TemplateContext::of($page)`, the properties by name, so no template variable changed its name. The page's parts are readonly objects too (the `View/` classes, `Push\Notification`, `Event\Link`, …), and none is changed after it is built. Where a template asks whether something is empty, the property stays a PHP list of objects, because an object is always truthy. `error.twig` and `admin-expired.twig` keep their array contexts, because they test with `is defined` for keys that a plain error, or a refused form with nothing typed, leaves out. The two Twig functions hand objects as well: `auth_identity()` an `Auth\IdentityView` (no template ever gets an `Identity`, and with it the device token) and `data_freshness()` a `Program\FreshnessView`. The pure readers that narrow untyped input where it enters are `Http\FormField` (a parsed body's field, as PHP's own conversion reads it) and `Storage\Row` (a fetched row's columns); PHPStan runs at level max over `src` with no baseline.

The push module itself, with the admin page and the subscription store, is in [push.md](push.md).
