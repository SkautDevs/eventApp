# HTTP

This document covers the middleware stack around every route, the Content-Security-Policy and how errors are rendered.

## The middleware stack

The middleware stack, innermost to outermost: body parsing, routing (with `Telemetry\RouteNameMiddleware` and `Http\ScreenAliasMiddleware` added before it, i.e. inside it, so the route is known), Twig, error, session cookie (`Http\SessionCookieMiddleware`), screen (`Http\ScreenMiddleware`), security headers (`Http\SecurityHeadersMiddleware`), `Http\CspMiddleware`, and `Telemetry\TransactionMiddleware` last — outermost, so the error middleware's 500 is measured. What each of the three middle ones does (the sliding login cookie; fragment mode, `Vary: X-Screen` and the pages' `Cache-Control`; the four fixed headers) is in its docblock. The screen middleware sets the Twig globals `screenPath`, the path that names the screen, and `pageAddress`, the address itself (the path, plus `?` and the query when there is one), which the skip link uses so it stays on the address the page was served for. A view address (`/programy/moje`, `/mapa/plan`) is a route with the argument `screen`, and `ScreenAliasMiddleware` then overwrites `screenPath` with the base path plus `screen` (`/obrok19/programy`); it cannot be part of the screen middleware, which sits outside the routing middleware and so never sees the route. Nothing overwrites `pageAddress`. `createInstance()` has the same order without the Twig, session-cookie and screen layers (its route naming is `RouteNameMiddleware(null)`).

## Writes and `X-Write`

The four writes — the register and unregister in a programme's sheet (`program-register`, `program-unregister`), Profil's pairing start (`pairing-start`) and logout (`pairing-revoke`) — answer through `Http\WriteResponse::redirect()`. A plain form POST, which is what a reader without JavaScript sends, gets a `302` with `Location`. A request with `X-Write: 1` (`WriteResponse::HEADER`), which `www/js/shell/write.js` sends for every `form[data-write]`, gets `200`, `Content-Type: application/json`, `Cache-Control: no-store` and the body `{"next":"<location>"}` (`JSON_UNESCAPED_SLASHES`): the script lands there with `location.replace()`, so the write replaces its history entry instead of leaving the POST's own step behind (a redirect a `fetch()` followed could not be landed on without one). The toast the write leaves waits in the session either way, for the next full document. The pairing check, `POST /profil/kontrola` (`pairing-check`), answers through `WriteResponse::redirect()` too, but its form carries no `data-write` (only a reader without JavaScript ever sees it), so it always gets the 302 ([auth-and-session.md](auth-and-session.md)). The 403 refusal pages (a cross-site form, an unpaired register) stay HTML whatever the header.

Any answer the script cannot use — not `200`, or no same-origin `next` — makes it call `form.submit()`, the plain POST, so the reader sees the server's own page. After a 5xx that **sends the write a second time**, which is acceptable because each of the four is idempotent on the server: a repeated register or unregister is refused by the source as `alreadyRegistered` / `notRegistered`, and `RegistrationWriter` keeps the same write's success toast still waiting unseen instead of that refusal; a repeated pairing start replaces this browser's pending pairing at kissj (the device id is the hash of the session ID), or does nothing when the reader is already paired, at the cost of one more count in the per-address throttle; a repeated logout finds nobody logged in, calls nothing at kissj and leaves no toast. A `fetch` that rejects (no worker and no network) sends nothing again: the button comes back with the offline toast.

## Content-Security-Policy

The Content-Security-Policy is enforced by `Http\CspMiddleware`: `script-src 'self' 'nonce-…'` with a fresh nonce per request in the Twig global `cspNonce`, so every inline `<script>` carries `nonce="{{ cspNonce }}"` and no element may carry an `on*=` handler (the push button is `data-push-toggle`, bound in `www/js/push/index.js`). Styles stay `'unsafe-inline'`: the timeline's per-programme `style` attributes cannot be hashed and must lay the screen out without JS, and an inline style can neither run code nor read data. Fonts and icons are `'self'` (self-hosted, above), so `style-src` is `'self' 'unsafe-inline'` and `font-src` `'self'`; the event's map origin is added to `frame-src` automatically, and the program provider's origin to `img-src` (`Environment::programOrigin()`, derived from `PROGRAM_PROVIDER_<SLUG>`: `https://kissj.example/` gives `img-src 'self' data: https://kissj.example`, `local` adds nothing), because the programmes' photos come from there while kissj's API is called by PHP only; `Kernel` passes it to `CspMiddleware::extrasFor()`, and the worker's `imageOrigin` and the provider's image filter read the same value; anything else goes in the optional config key `csp` (`EventConfig::$csp`, `['frame-src' => ['https://…']]`, validated at load). `CspTest` renders every participating route and fails on a missing nonce.

## Error pages

Errors render through `App\Http\TwigErrorRenderer`, registered for `text/html` and as the default on `QuietErrorHandler`: the event's `templates/error.twig` extends the layout — 404 and 405 read "Tohle tady není.", anything else "Něco se pokazilo. Zkus to za chvíli.", both with a link home, and under `APP_DEBUG` a `<details class="error-details">` with Slim's detail set; the instance app uses the plain `templates/instance-error.twig`. The same `error.twig` renders the app's 403 refusals with a `message` and a `back` link of their own (a cross-site pairing start or logout, a cross-site or unpaired register). A fragment request that errors gets the whole document. An error page that itself fails to render falls back to `TwigErrorRenderer::FALLBACK` and is reported through `Collector`; JSON clients keep Slim's JSON.
