# Push

This document covers web push: the admin send page and its message log, the subscription store, the sender, the notifications card and the worker's part.

## The admin page and the message log

`PushModule` and `AdminModule` (web push notifications) are implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and `GET/POST /admin/notify` sends notifications — the shared link `?token=<ADMIN_TOKEN_<SLUG>>` logs the browser in for 24 hours (session key `admin` = `['since' => int]`) and redirects to the bare URL; the pages after it carry no token and the forms carry a CSRF field (`csrf`), and every admin response is `Cache-Control: no-store` and `Referrer-Policy: no-referrer` — the error page of an exception thrown under the admin routes included, which their middleware renders itself through the container's `ErrorMiddleware` so it is reported once; the send form also carries a one-time `nonce`, issued each time the form renders (up to fifty stay valid in the session, for several open tabs) and consumed under the session lock in `Session::transact()` only right before the send, after validation and the participant-id fetch, so a double tap or a re-send after a 504 sends nothing and answers 409 with the typed text and a neutral notice ("Tento formulář už byl jednou odeslán, nebo je zastaralý…"); its submit button is disabled on submit and re-enabled on `pageshow`; a refused POST (expired day or stale CSRF) answers 403 with a Czech "link expired" page (`templates/admin-expired.twig`) that echoes the typed title and text, and re-opening the link keeps a well-formed `csrf` so a form open in another tab stays valid — through `App\Push\PushSenderInterface`/`WebPushSender`, either to everyone or to one programme — whose participants `ProgramProviderInterface::getParticipantIdsForProgramme()` names. How a send is logged before it goes out, and what its result line says, is in `Admin\SendAction`'s docblock. The log is kept forever: the admin page lists it and can hide a message from readers or show it again (`POST /admin/notify/{id}/hidden`, `Admin\HideAction`), recording who and when, but nothing is ever deleted. Subscriptions carry an `event` column and a send reaches only that event's subscribers; each also carries the participant id (`participant_id`) of the session that saved it — taken from the session, never from the request — which `www/js/push/index.js` keeps in step by re-sending the subscription whenever the page's `push-identity` meta (the participant id, empty logged out) differs from the one it last sent (`localStorage['pushIdentity:<base>']`), so a programme send reaches exactly the subscribed browsers of its registered participants.

The admin page is rendered by `Admin\AdminPageRenderer` from an `Admin\View\AdminPage`: the form's `FormValues`, the picker's `ProgrammeGroup`s of `ProgrammeOption`s by day (a programme without a start is listed under today and sorted first), one page of the log and the last send's `NotifyResult`. The session keeps that result as the array `SendAction` flashed under `notifyResult`, unchanged, and `NotifyResult::fromArray()` reads it back. `MessageRepository` hands out the log as `Push\Message`s, whose `sentAt` and `toggledAt` stay the stored `Y-m-d H:i:s` strings that the page formats with Twig's `date` filter, and `SubscriptionRepository` its rows as `Push\Subscription`s; both read a fetched row through `Storage\Row`.

## Storage

Storage is one `PDO` per request from `Storage\Database::open()` (WAL, `busy_timeout` 5000, foreign keys), the container's `\PDO::class`, migrated on first use by `Storage\Migrator` — numbered steps tracked in `PRAGMA user_version`, one `BEGIN IMMEDIATE` transaction each, `Migrator::VERSION` the highest. It is **1**: one fresh step (`subscriptions` keyed `(event, endpoint)` with `participant_id` and `failures`; `messages` with nullable counts and `failed`; `subscribe_attempts`; `pairing_attempts`), because the earlier steps were collapsed before anything was in production, and a database at a higher version (every file the old five-step migrator made) is refused with a `RuntimeException` rather than taken for current. From the first production deploy on, append a step, never edit a shipped one. Both repositories, `Auth\PairingThrottle` and `Push\SubscribeThrottle` take that `PDO` and run no DDL.

## Subscribe

Subscriptions are keyed `(event, endpoint)`, so the same browser may subscribe to two events and `delete($event, $endpoint)` touches only its own; what `POST /push/subscribe` (`Push\SubscribeAction`) accepts, how many new subscriptions it takes, and how it answers is in that action's docblock. The welcome and every send for everyone link to `/<slug>/informace`. There is no unsubscribe route: nothing in the app ever called one, so it was removed.

## Sending

`WebPushSender` sends a batch concurrently, each request with its own short timeout; it deletes the rows that can never be sent to, sets aside a row whose encryption fails instead of losing the batch, and strikes a row only when its push service delivered something else in the same batch, deleting it after `MAX_FAILURES` in a row. Its class docblock has each rule and the reason for it. `sendToEvent()` returns a `Push\SendResult` (`recipients`, `sent`, `removed`, `failed`), whose docblock says what each count holds. It validates `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` in its constructor, and gets its repository as a closure resolved on the first send. `Kernel::create()` builds the sender at boot for every push event, so a misconfigured instance fails on the first request, not on the first tap — and since every event has push, `.env` needs a VAPID pair even in development; `AppTestCase` gives every app a `SpyPushSender`, and `tests/bootstrap.php` generates a throwaway pair per run for the tests that boot the real one.

## The opt-in

**The notifications card** (`templates/_notifications.twig`, rendered only for an event with the `push` feature) is its own card on Domů, right after the install card in both phases, and on Profil, after the install card and before the mode control: `Notifikace`, the line `Pošleme ti změny programu a důležité zprávy od organizátorů.`, the `Zapnout notifikace` button (`.push-enable`, `data-push-toggle`) and its `.push-status` line. The server renders the card `hidden` (with `data-morph-keep="hidden"`, so a morph never writes `hidden` back over a card that is shown), and without JavaScript it stays hidden. `www/js/push/index.js` shows it once `detectSubscription()` has answered and this browser is not subscribed: the module flag `known` turns true when the detection finishes, whatever it found or if it failed, and the `DOMContentLoaded` start-up sets it back to false before its chain runs, so a subscribed reader never sees the card flash. The opt-in is one-way: there is **no off switch** — once subscribed, the card is hidden for good, so only the browser's own settings turn notifications off; there is no unsubscribe route on the server either. A successful subscribe hides the card and says so in a toast (`showToast()`): `Notifikace zapnuté, jupí!`, with the second line `Právě ti přišla uvítací notifikace.` only when the welcome got through (`welcome: true`; without it the toast has no second line). On Profil the card has a quiet line under it, `Notifikace máš zapnuté.` (`.push-on`, `data-push-on`, also rendered `hidden`), which follows: it shows instead of the card in a subscribed browser. Everything else the card says is its status line, with the button still on show: `denied` (`Notifikace máš v prohlížeči zakázané. Povol je v nastavení stránky a zkus to znovu.`), `enableFailed` (`Notifikace se nepodařilo zapnout. Zkontroluj připojení a zkus to znovu.`), `tooMany` (a 429, `Teď si notifikace zapíná moc lidí najednou, zkus to za chvíli.`, which keeps the browser's subscription: the next page re-sends it), `invalidKey` (a 400 `invalid-key`, `Prohlížeč poslal neplatné údaje, zkus notifikace zapnout znovu.`, dropped like any other failure), `preparing` (`Připravuji…`: turning it on registers the worker and waits up to 10 s, `READY_TIMEOUT`, for `serviceWorker.ready`, because the browser subscribes only through an active worker and on a first visit it may still be installing), and `off` (`Notifikace jsou vypnuté.`, after a re-sync the push service rejected). Without `serviceWorker`/`PushManager` there is no card at all, except on iOS (Safari outside a home-screen app has no `PushManager`), where the card shows without its button and its status line says `Na iPhonu zapneš notifikace, až si aplikaci přidáš na plochu.`, known or not. Nothing in it calls `alert()`. Its start-up re-syncs the identity first and only then detects an existing subscription, and it still listens for `DOMContentLoaded` itself, which `PushToggleTest` dispatches again to restart it with its fakes in place. The three pure parts are exported and tested in `tests/js/push.test.js`: `urlB64ToUint8Array()` (the VAPID key's bytes), `classifyFailure(status, body)`, which turns a failed subscribe answer into the `rejected`, `tooMany` and `invalidKey` flags the status line is chosen by, and `cardState({supported, ios, known, subscribed, status})`, which `render()` draws every card, button, status line and Profil line from.

## The worker's part

`www/sw.js` stays at the docroot root and is registered at scope `/<slug>/` (the `event-base` meta tag) by `www/js/shell/worker.js` on every page — and again by `push/index.js`, harmlessly, since `register()` is idempotent — so two events in one browser keep separate workers. A push without a usable payload is shown under the title `Notifikace`. After showing a notification the worker posts `{type: 'news-updated', programme}` to the event's open windows; `programme` (an id or null) travels in the payload from `PushSenderInterface::sendToEvent(…, programme:)` (`WebPushSender::payload()`).
