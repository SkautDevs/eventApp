# Push

This document covers web push: the admin send page and its message log, the subscription store, the sender, the opt-in button and the worker's part.

## The admin page and the message log

`PushModule` and `AdminModule` (web push notifications) are implemented: `POST /push/subscribe` saves a subscription via `App\Push\SubscriptionRepository`, and `GET/POST /admin/notify` sends notifications — the shared link `?token=<ADMIN_TOKEN_<SLUG>>` logs the browser in for 24 hours (session key `admin` = `['since' => int]`) and redirects to the bare URL; the pages after it carry no token and the forms carry a CSRF field (`csrf`), and every admin response is `Cache-Control: no-store` and `Referrer-Policy: no-referrer` — the error page of an exception thrown under the admin routes included, which their middleware renders itself through the container's `ErrorMiddleware` so it is reported once; the send form also carries a one-time `nonce`, issued each time the form renders (up to fifty stay valid in the session, for several open tabs) and consumed under the session lock in `Session::transact()` only right before the send, after validation and the participant-id fetch, so a double tap or a re-send after a 504 sends nothing and answers 409 with the typed text and a neutral notice ("Tento formulář už byl jednou odeslán, nebo je zastaralý…"); its submit button is disabled on submit and re-enabled on `pageshow`; a refused POST (expired day or stale CSRF) answers 403 with a Czech "link expired" page (`templates/admin-expired.twig`) that echoes the typed title and text, and re-opening the link keeps a well-formed `csrf` so a form open in another tab stays valid — through `App\Push\PushSenderInterface`/`WebPushSender`, either to everyone or to one programme — whose participants `ProgramProviderInterface::getParticipantIdsForProgramme()` names. How a send is logged before it goes out, and what its result line says, is in `Admin\SendAction`'s docblock. The log is kept forever: the admin page lists it and can hide a message from readers or show it again, recording who and when, but nothing is ever deleted. Subscriptions carry an `event` column and a send reaches only that event's subscribers; each also carries the participant id (`participant_id`) of the session that saved it — taken from the session, never from the request — which `www/push.js` keeps in step by re-sending the subscription whenever the page's `push-identity` meta (the participant id, empty logged out) differs from the one it last sent (`localStorage['pushIdentity:<base>']`), so a programme send reaches exactly the subscribed browsers of its registered participants.

The admin page is rendered by `Admin\AdminPageRenderer` from an `Admin\View\AdminPage`: the form's `FormValues`, the picker's `ProgrammeGroup`s of `ProgrammeOption`s by day (a programme without a start is listed under today and sorted first), one page of the log and the last send's `NotifyResult`. The session keeps that result as the array `SendAction` flashed under `notifyResult`, unchanged, and `NotifyResult::fromArray()` reads it back. `MessageRepository` hands out the log as `Push\Message`s, whose `sentAt` and `toggledAt` stay the stored `Y-m-d H:i:s` strings that the page formats with Twig's `date` filter, and `SubscriptionRepository` its rows as `Push\Subscription`s; both read a fetched row through `Storage\Row`.

## Storage

Storage is one `PDO` per request from `Storage\Database::open()` (WAL, `busy_timeout` 5000, foreign keys), the container's `\PDO::class`, migrated on first use by `Storage\Migrator` — numbered steps tracked in `PRAGMA user_version`, one `BEGIN IMMEDIATE` transaction each, `Migrator::VERSION` the highest. It is **1**: one fresh step (`subscriptions` keyed `(event, endpoint)` with `participant_id` and `failures`; `messages` with nullable counts and `failed`; `subscribe_attempts`; `pairing_attempts`), because the earlier steps were collapsed before anything was in production, and a database at a higher version (every file the old five-step migrator made) is refused with a `RuntimeException` rather than taken for current. From the first production deploy on, append a step, never edit a shipped one. Both repositories, `Auth\PairingThrottle` and `Push\SubscribeThrottle` take that `PDO` and run no DDL.

## Subscribe

Subscriptions are keyed `(event, endpoint)`, so the same browser may subscribe to two events and `delete($event, $endpoint)` touches only its own; what `POST /push/subscribe` (`Push\SubscribeAction`) accepts, how many new subscriptions it takes, and how it answers is in that action's docblock. The welcome and every send for everyone link to `/<slug>/informace`. There is no unsubscribe route: nothing in the app ever called one, so it was removed.

## Sending

`WebPushSender` gives every push request a 5 s timeout (`TIMEOUT_SECONDS`; the library's 30 s could outlast nginx's 45 s on an admin batch), deletes at send time any row whose endpoint the allow-list refuses (rows from before it existed) or whose keys fail `SubscriptionKeys::valid()`, sends through `Push\IsolatingWebPush` — the library with `prepare()` per notification, so a row whose encryption still throws is set aside and deleted instead of taking the whole batch down (only when *every* row is set aside is it the platform's fault: all count as failed, none is deleted, the first error is reported), and with its own `flush()`, which sends a batch concurrently through Guzzle's promises (web-push 11's sends one request after another, and its `flushPooled()` needs an HTTPlug adapter that does not exist for Guzzle 8) with `http_errors` off, so a 404 or 410 is a report; a throwable that is not a PSR-18 client failure propagates as before — and keeps strikes: a `Failed` send adds one to the row's `failures` — but only when the row's push-service host delivered at least one other notification of the same batch (`WebPushSender::strikable()`), so a send where nothing arrived, or one service's outage, strikes nobody — `MAX_FAILURES` (5) in a row delete it (counted as failed, not removed), and a delivery resets it, as do new keys on a re-subscribe (`save()` upserts and keeps the count when the keys are the same). `sendToEvent()` returns a `Push\SendResult` (`recipients`, `sent`, `removed`, `failed`), whose docblock says what each count holds. It validates `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` in its constructor, and gets its repository as a closure resolved on the first send. `Kernel::create()` builds the sender at boot for every push event, so a misconfigured instance fails on the first request, not on the first tap — and since every event has push, `.env` needs a VAPID pair even in development; `AppTestCase` gives every app a `SpyPushSender`, and `tests/bootstrap.php` generates a throwaway pair per run for the tests that boot the real one.

## The opt-in

`www/push.js` is a one-way opt-in: there is **no off switch** — once subscribed, the button's `.push-enable` paragraph is hidden and the status line reads `Notifikace máš zapnuté, jupí!` (after a fresh subscribe, the welcome line), so only the browser's own settings turn notifications off; there is no unsubscribe route on the server either. Turning it on registers the worker, shows `Připravuji…` and waits up to 10 s (`READY_TIMEOUT`) for `serviceWorker.ready`, because the browser subscribes only through an active worker and on a first visit it may still be installing; a 429 from the subscribe says `Teď si notifikace zapíná moc lidí najednou, zkus to za chvíli.` and keeps the browser's subscription (the next page re-sends it), a 400 `invalid-key` says `Prohlížeč poslal neplatné údaje, zkus notifikace zapnout znovu.` and drops it like any other failure; without `serviceWorker`/`PushManager` the button is hidden, and on iOS (Safari outside a home-screen app has no `PushManager`) the status line says `Na iPhonu zapneš notifikace, až si aplikaci přidáš na plochu.`. Nothing in it calls `alert()`.

## The worker's part

`www/sw.js` stays at the docroot root and is registered at scope `/<slug>/` (the `event-base` meta tag) by `www/shell.js` on every page — and again by `push.js`, harmlessly, since `register()` is idempotent — so two events in one browser keep separate workers. A push without a usable payload is shown under the title `Notifikace`. After showing a notification the worker posts `{type: 'news-updated', programme}` to the event's open windows; `programme` (an id or null) travels in the payload from `PushSenderInterface::sendToEvent(…, programme:)` (`WebPushSender::payload()`).
