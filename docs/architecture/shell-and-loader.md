# Shell and loader

This document covers the app shell in `_layout.twig`, the stack of screens and the loader in `www/app.js`, the toasts, `www/shell.js` and the install card.

## The layout

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link; the logo's link to Domů carries a visually hidden `<event name> – úvod`, since the logo is decorative and the link would otherwise be announced as the current screen's title), the network banner, and a fixed bottom tab bar built from Domů plus the enabled features, sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Profil is a core route, not a module, and a screen in the stack like the tabs.

## A stack of screens

Switching screens does not load a document. `<main>` is a **stack of screens** — `<section class="screen" data-screen data-title data-doc-title data-tab data-fetched-at [data-stale] tabindex="-1">`, emitted identically by `_layout.twig` (the first one, server-rendered) and by `_screen.twig` (every one after it). A request carrying `X-Screen: 1` gets the second parent: every participating template picks its own with `{% extends fragment ? '_screen.twig' : '_layout.twig' %}`, against a Twig global that `Kernel`'s screen middleware sets per request. `data-fetched-at` (always, `DATE_ATOM` in Europe/Prague) is when the provider data on the screen was fetched — the request time on a screen that used none, and on every `local` event — and `data-stale="1"` marks an old copy served because kissj failed; both come from the Twig function `data_freshness()` (a function, like `auth_identity()`, because the handler fills it before the layout renders). `www/shell.js` draws the network banner from them. A background revalidation compares `innerHTML`, which leaves the section's own attributes out, so `app.js`'s `syncFreshness()` carries the two attributes over on both the unchanged and the morphed path and dispatches `screen:freshness`. Next to `fragment` the middleware sets `screenPath`, which exists because slim/twig-view resolves `get_uri()`'s runtime exactly once and then keeps it for the life of the `App` — the path would be stale from the second request on, which no single-request web server notices and every test does. A plain request stays byte-identical to what it was, which is what keeps deep links, crawlers, the back button against a cold cache and a reader with JS off working, and `Vary: X-Screen` keeps the two responses apart in anything that caches them.

## The loader

`www/app.js` fetches a screen **once**, inserts it hidden, and from then on navigation is show/hide. It does not wait for the first tap either: once the first document has loaded (`requestIdleCallback`, at most 3 s), the **warm-up** (`warm()`) fetches every other participating screen one after the other and inserts each hidden, loading the Font Awesome faces first (`warmIcons()`: a hidden screen makes the browser read no font, so the quick links' brand icons would blink in on their first show), stopping at the first failure and skipping itself under `navigator.connection.saveData` (or `window.appWarm === false`, the browser tests' switch, set by `BrowserTestCase::coldScreens()`); `load()` keeps one fetch per path in flight, so a tap on a screen the warm-up is still fetching waits for that fetch rather than inserting the screen twice. The map's iframe is `loading="lazy"`, so a Místa screen warmed into a hidden section does not load Google's map until it is shown. Nothing is ever removed, so state is *live* rather than restored: the map's Google iframe keeps running, the timeline keeps its zoom *and* its horizontal scroll, a scrolled list stays scrolled. Hidden and not detached is the whole point — re-inserting a detached `<iframe>` re-fetches it, which is also why neither `hx-preserve` nor `data-turbo-permanent` could have done this: both persist a node present in *both* documents, and the map exists on one screen only. Order matters, **insert → show → init**: the ruler's label-width measurement and every `scrollLeft` calculation return 0 inside a `hidden` subtree.

## Revalidation and the morph

Showing a cached screen is instant, always; one fetched more than five minutes ago is revalidated in the background, and a screen whose HTML has actually changed is **morphed** into the new one rather than replaced — `innerHTML` would throw away the very state the cache exists to keep. The morph is hand-rolled and small (no diffing library, and deliberately not a vendored Idiomorph): children match on `id`, then `data-key`, then position among same-tag siblings; a subtree already equal to its counterpart is skipped outright; a matched `<iframe>` is never written to *and never moved*, because a move re-inserts it and a re-inserted iframe reloads. It writes only the attributes the fresh markup states — one it does not carry at all belongs to the client (`--hour-width` lives in `.pg`'s `style`, `data-hour-step`, `data-pg-ready`, `disabled`) — and one the markup names in **`data-morph-keep`**, for the attributes the server writes without owning: `.pg`'s `data-view` and `data-step`, `.tl-page`'s `class`, a day chip's `aria-current`, `.mapview`'s `data-view`. Without that the screen would be put back on the server's default view and page, and a layout landing in the gap before the screen restores itself would take the reader's scroll with it. What the screen does own it puts back on a `screen:morphed` event, dispatched synchronously in the same task. A morph, like a replacement before it, never happens while the reader is in the middle of a screen — an open sheet or focus in a form field defer it to the next time that screen is shown, and it then runs *after* the screen is visible again, for the same reason the wiring does. Measured on the Program screen: a revalidation that finds no change touches **zero** nodes; one that finds a renamed, re-timed programme touches seven, on a screen holding sixty cards.

## Transitions

Screens slide **by tab order** through the View Transitions API: the loader only sets `data-nav` on the root and the animations live in `www/style.css`'s one reduced-motion block, so where the API is missing — or reduced motion is asked for — the swap is instant rather than animated by hand. There is deliberately **no swipe gesture**: a horizontal drag on the timeline means "scroll the hours".

## What the loader does not take over

A response that is not a 200 is not a screen: the loader falls back to a plain navigation, so the reader gets the server's own error page instead of an app bar injected into a `<section>`. So does a screen the reader is waiting for that has not arrived after 8 s (`LOAD_TIMEOUT`, an `AbortController` on `load()`'s fetch), because on lie-fi a fetch that never ends would leave the tap hanging for minutes. `show()` dispatches `screen:hidden` (bubbling) on the section it hides, so a screen's own dialogs do not outlive it. A tap on the tab of the screen already shown navigates nowhere: the loader scrolls that screen to the top (smoothly, unless reduced motion is asked for), as a native tab bar does, instead of letting a plain navigation throw the live app away.

The skip link is the other same-origin link the loader handles itself: it names the path the document was first served for, which after a swap is another screen, so a click on it focuses the visible screen's section and navigates nowhere. The participating set is read off the rendered shell — the tab bar's own links plus the profile one, in that order, which is what makes `/profil` count as forward — so it is Domů, the enabled tabs and `/profil` and nothing else. The handbook PDF, external links, `/admin/notify` and **every non-GET** stay plain navigations — the pairing start, the logout, a register or unregister — so a write reloads the document and empties the cache with it; that is the correctness rule rather than laziness, because the identity changes both the app bar and the registered marking on every programme. The end of a pairing is a GET poll answered by JSON, so `www/profile.js` reloads the document itself. Every link stays a real `<a href>` and the loader is an enhancement layer, not a client router: with `www/app.js` absent the app behaves exactly as it did.

## The loader and the worker

The loader and the worker: `revalidate()` sends `cache: 'no-cache'` and `load()` does not. `go()` dispatches `screen:loading`/`screen:loaded` on `document` around a fetch the reader waits for, never around a background revalidation (and `screen:loaded` once more on an instant show, so the bar of an overtaken tap goes). The loader listens to the worker: `screen-updated {path}` and `news-updated {programme}` set the entry's `fetchedAt` to 0 (Informace and Domů always, the Program screen too for a programme message) and revalidate the one on show, so a new `.news[data-key]` is morphed in at the top; a path reported before the loader has it waits in `staleOnArrival`. `syncFreshness()` dispatches `screen:freshness` on the section whenever it changes either attribute.

## Toasts

**Toasts.** One component, `templates/_toast.twig` (`<div class="toast" role="status" data-toast data-key="toast">`: a title, an optional second line, a `✕` `[data-toast-close]` with `aria-label="Zavřít"`), a `structure`-filled banner with a hairline at the top of the screen, gone after 6 s on display (`TOAST_MS` in `www/shell.js`, which arms a server toast only once its screen is shown) or on the close tap. The server's ones wait in the session under `toast` (`['title', 'line', 'at' => time()]`, plus a `tag` for a write's success): `Kernel::putToast()` leaves one, `Kernel::takeToast()` takes it on the next **full document the reader asks for** — never a fragment (`X-Screen`, which the loader's warm-up sends) nor the worker's own fill and refill fetches (`X-Worker-Fill: 1`, `Kernel::WORKER_FILL_HEADER`), which would swallow it before the reader sees anything — and drops one older than 60 s (`TOAST_SECONDS`) unsaid. A request with no toast pending never opens the session. Profil takes the login and logout toasts, Program the registration ones. A response carrying a toast goes through `Kernel::markToast()`, which sets `X-Toast: 1` (`Kernel::TOAST_HEADER`), and the worker never stores such a response, so the offline copy is fetched again without it. The shell's own toast is the offline one (below). A toast that leaves while its `✕` has the focus hands the focus to the visible screen — or, with the programme sheet open, to the sheet's card (`removeToast()`).

## shell.js

`www/shell.js` holds the installed-app concerns and talks to the loader only through those events. It registers the worker.

## The network banner

It draws **the network banner**: one `<p class="netstate" data-netstate aria-hidden="true" hidden>` per document, outside every screen, docked right above the tab bar, which shows only offline (`Jsi offline. Data byla naposledy aktualizována v 10:20 (před 25 min).`) or online with an old copy (`data-stale`: `Nepodařilo se načíst aktuální data. Zobrazuji stav z 10:20 (před 25 min).`) and is otherwise hidden. The time is the visible screen's `data-fetched-at` on the reader's clock, re-read on every draw (`DOMContentLoaded`, `screen:shown`, `screen:morphed`, `screen:freshness`, `online`/`offline`, `visibilitychange`, `pg:tick` and every minute), so switching to a screen fetched earlier changes it at once; the age is `právě teď` under a minute (never `před 0 min`), `před N min` under an hour, then `před N h`, then the date. Its height is published as `--netstate-height` on the root (0px while hidden, kept current by a `ResizeObserver`), which the docked view switcher (Program, a two-view Místa), every screen's bottom padding and `--screen-height` add, so the banner covers nothing. A screen reader hears it through a live region of its own (`<p class="sr-only" role="status" data-netstate-live>`), written only when the state changes and without the ticking age.

## Toast, confirmations, clock, progress, install, map

It runs **the toast** (above): arms server toasts on display, and on `#offline` in the URL shows `Akci není možné provést, protože jsi offline.` / `Zkus to znovu až najdeš místo se signálem.` and strips the hash with `history.replaceState`. It owns **the two-tap confirmations**: a button with `data-confirm` (the logout, the unregister) swaps its label for the question on the first tap and submits on the second, starting over on `screen:hidden`, `sheet:closed` and `pageshow`. It redraws **the clock-driven parts** from `homeNow()` (`window.pgClock` when set): Domů's next-programme cards, the countdown (whole Prague days to the start, `den`/`dny`/`dní`, hidden from the start on), the date heading `data-home-date`, and every `data-sent-at` relative time, on `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `visibilitychange`, `pg:tick` and every minute. It toggles `data-loading` on the root for the 2px `.progress` bar at the tab bar's top edge (`var(--on-structure)`, the bar's own ink, because `state` is under 3:1 on a pale bar; a static bar under reduced motion), and keeps `beforeinstallprompt` (default-prevented, so Chrome shows nothing by itself) for the install card's hidden `Uložit jako aplikaci` button, which shows the kept offer once and is hidden again after the tap, on `appinstalled` and in an installed app (`display-mode: standalone` or iOS's `navigator.standalone`). iOS has no install prompt at all, so on an iPhone or iPad the card's `[data-install-ios]` hint (`Aplikaci si přidáš na plochu v Safari: klepni na Sdílet a pak na Přidat na plochu.`) shows instead, outside an installed app only. It also minds the map offline: Google's iframe is a blank box without a network, so `map.twig` puts a `<p class="empty map-offline" data-map-offline hidden>Mapa potřebuje připojení.</p>` right after the `[data-map]` box (on a two-view Místa the note is `.empty.map-offline.map-offline-plan`, its sentence wrapped in `<span class="map-offline-text">` and followed by a `Zobrazit plán` button, `data-map-view="plan"`, which `map.js` handles — the note itself stays opaque and only the sentence takes `.empty`'s 0.8 fade, because the tonal `.btn` under it falls below AA at that opacity (under AA on a light set); `shell.js` only toggles the note's `hidden` and never rewrites it, and finds the map as the note's `previousElementSibling`, so nothing may come between them), and `shell.js` (on `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `online`, `offline`) hides a map that never loaded behind that note while `navigator.onLine` is false and reloads its iframe once the signal is back; a map that did load (one capture-phase `load` listener marks it `data-map-loaded` while online) stays as it is, with no note.

## Other scripts and asset versions

`www/profile.js` is Profil's pairing poll and nothing else. `_layout.twig` also carries `<noscript><p class="noscript">` as `<main>`'s first child; nothing else is promised without JS. Stylesheet and scripts are linked through the Twig function `asset_version('style.css')` → `style.css?v=<first 8 hex of sha256>` (`App\Http\AssetVersion`, memoised per process by path, mtime and size): nothing is bumped by hand, and `sw.js` is never versioned. The self-hosted fonts and icons under `www/fonts/` and `www/vendor/` carry no hash and follow one rule instead: **a changed file gets a new name** (a new Montserrat is `montserrat-v<N+1>-…`, a new Font Awesome a new `fontawesome-free-<version>/` directory), never new bytes under the old one — nginx and `.htaccess` give both prefixes a year of `immutable` and the worker serves them cache-first, so a file replaced in place would never reach a returning reader.

## Manifest and head icons

Each `site.webmanifest` carries `id`, `lang`, `orientation`, a maskable 512 icon and `shortcuts` for the enabled Program and `Notifikace` (Informace); `<link rel="mask-icon">` is emitted only for an event whose config has `assets.pinnedTab` (obrok19 only). The three head icons default to `events/<slug>/favicon-16x16.png`, `favicon-32x32.png` and `apple-touch-icon.png`; the optional `assets.favicon16`, `favicon32` and `appleTouch` override them, which is how obrok27 serves the set `bin/event-icons.php` generates from its white lilie on `#15133f`: content-hashed `icon-<hash8>-<size>.png` names (nginx and `.htaccess` serve PNGs under `www/events/` as immutable for a year, so new bytes under an old name would never reach a returning browser), favicons transparent when the source is (obrok27's are opaque `#15133f` squares), opaque home-screen icons on the background colour (iOS paints transparency black) and a maskable one inside the 80 % safe zone, with the manifest's icons rewritten in place.

## The install card

**The install card** (`templates/_install.twig`, on Domů as `installCard: 'home'` and on Profil as `'profile'`) puts the install offer and the notifications button under one heading (`Ulož si <event> na plochu`, then `Zapni si upozornění, ať ti neuteče výběr programů, novinky a varování v průběhu akce.`): the hidden `Uložit jako aplikaci` button (`.install[data-install]`, `.install-btn`), the iOS hint (`[data-install-ios]`), and, for a push event, the `Povolit notifikace` button (`data-push-toggle`) with its `.push-status` line. In an installed app Domů hides the whole card (`data-install-card="home"`) and Profil only the install half.

## Two rules

Two rules the shell depends on. `<main>` must **never** carry a `view-transition-name`, however natural it looks: naming an element makes it a stacking context, and the sheet is a fixed child of `<main>` that has to keep painting over the fixed tab bar. Only `.appbar` and `.tabbar` are named, which takes them *out* of the root snapshot so the shell sits still while the screen under it slides. And the per-screen layout rules key off the section (`.screen[data-tab="map"]`, `"programs"`, `"homepage"`) rather than the old `body.screen-*` classes, with `main > .screen[hidden]` restating `display: none` loudly enough to out-specify them.
