# Shell and loader

This document covers the app shell in `_layout.twig`, the stack of screens and the loader in `www/js/loader/`, the toasts, the script modules under `www/js/` and how they load, the shell's own modules in `www/js/shell/`, and the install card.

## The layout

Templates in `templates/` (shared by all events) all extend `_layout.twig`, which renders the app shell: a sticky app bar (event logo, page title, profile link; the logo's link to Domů carries a visually hidden `<event name> – úvod`, since the logo is decorative and the link would otherwise be announced as the current screen's title), the network banner, and a fixed bottom tab bar built from Domů plus the enabled features, sorted by each `menuItem()`'s `order`. The whole app is laid out as a phone — a centred column capped at `--app-width` — at every viewport width. Extending templates set two variables before the layout renders, `pageTitle` (also used for `<title>`) and `activeTab` (matched against a module's feature key); neither is a Twig block. Profil is a core module (no tab of its own) and a screen in the stack like the tabs.

## A stack of screens

Switching screens does not load a document. `<main>` is a **stack of screens** — `<section class="screen" data-screen data-title data-doc-title data-tab data-fetched-at [data-stale] tabindex="-1">`, emitted identically by `_layout.twig` (the first one, server-rendered) and by `_screen.twig` (every one after it). A request carrying `X-Screen: 1` gets the second parent: every participating template picks its own with `{% extends fragment ? '_screen.twig' : '_layout.twig' %}`, against a Twig global that `Http\ScreenMiddleware` sets per request. `data-fetched-at` (always, `DATE_ATOM` in Europe/Prague) is when the provider data on the screen was fetched — the request time on a screen that used none, and on every `local` event — and `data-stale="1"` marks an old copy served because kissj failed; both come from the Twig function `data_freshness()` (a function, like `auth_identity()`, because the handler fills it before the layout renders). `shell/netstate.js` draws the network banner from them. A background revalidation compares `innerHTML`, which leaves the section's own attributes out, so the loader's `syncFreshness()` carries the two attributes over on both the unchanged and the morphed path and dispatches `screen:freshness`. The middleware also sets `screenPath` and `pageAddress`; its docblock says why, and on a view address (`/programy/moje`) `Http\ScreenAliasMiddleware` renames `screenPath` to its screen's path, so `data-screen` names the screen rather than the address ([http.md](http.md)). A plain request stays byte-identical to what it was, which is what keeps deep links, crawlers, the back button against a cold cache and a reader with JS off working, and `Vary: X-Screen` keeps the two responses apart in anything that caches them.

## The loader

The loader (`www/js/loader/loader.js`) fetches a screen **once**, inserts it hidden, and from then on navigation is show/hide. It does not wait for the first tap either: once the first document has loaded (`requestIdleCallback`, at most 3 s), the **warm-up** (`loader/warmup.js`) fetches every other participating screen one after the other and inserts each hidden, loading the Font Awesome faces first (`warmIcons()`: a hidden screen makes the browser read no font, so the quick links' brand icons would blink in on their first show), stopping at the first failure and skipping itself under `navigator.connection.saveData` (or `window.appWarm === false`, the browser tests' switch, set by `BrowserTestCase::coldScreens()`); `load()` keeps one fetch per path in flight, so a tap on a screen the warm-up is still fetching waits for that fetch rather than inserting the screen twice. The map's iframe is `loading="lazy"`, so a Místa screen warmed into a hidden section does not load Google's map until it is shown. Nothing is ever removed, so state is *live* rather than restored: the map's Google iframe keeps running, the timeline keeps its zoom *and* its horizontal scroll, a scrolled list stays scrolled. Hidden and not detached is the whole point — re-inserting a detached `<iframe>` re-fetches it, which is also why neither `hx-preserve` nor `data-turbo-permanent` could have done this: both persist a node present in *both* documents, and the map exists on one screen only. Order matters, **insert → show → init**: the ruler's label-width measurement and every `scrollLeft` calculation return 0 inside a `hidden` subtree.

**One screen, several addresses.** A tab may declare its screen's other addresses in `data-screen-aliases` (the Program tab: `/programy/prehled` and `/programy/moje`, from `MenuItem::$aliases`). `startLoader()` reads them into an alias map (`parseAliases()`), and `screenOf(pathname)` (`resolveScreen()` over that map) names the screen any address shows: an alias resolves to its screen, anything else is its own. Everything the loader keys, compares or fetches is the screen — the `screens` map, `currentPath`, the tab order, which tab is lit, the reload check on Back, the fetch itself — while the history entries carry the real address with `{screen: <screen path>}` as their state. `go(screen, push, url)` pushes `url` and shows `screen`. The loader remembers the address each screen was last on (`lastAddress`, the pathname, recorded by `noteAddress()` on every click before anything else, so a screen's own `pushState` in an inner handler is seen, after every swap and after every Back), and a tab tap goes back to it: a reader who left the Program screen on Moje finds Moje. The tab's `href` stays the screen's path.

A tap on the tab of the screen on show, or on the very address on show, scrolls to the top (below). A link to *another* address of the screen on show that is not its tab (Přehled while on Moje) is pushed and announced with a synthetic `popstate`, so the screen switches as it does on Back; `onPopstate()` returns early for the current screen and the screen's own `popstate` listener reads the address. A deep link (`data-deep-link`, Domů's next-programme card) pushes `url.pathname + url.search + url.hash` for `screenOf(url.pathname)` and shows that screen; it requires an empty query for now. When that screen cannot be fetched, the fallback reloads the entry just pushed (`go(screen, false, null)` → `location.reload()`), so the plain load keeps the whole address, hash included; a `location.href` to it would be a same-document hash change and load nothing. The loader dispatches **no `hashchange`**: a screen reads its address on its first wiring, on `screen:shown` and on `popstate`, and those are the only triggers (the Program screen reads its view and its hash on `screen:shown` once wired, `ctx.syncFromUrl()` in [programs.md](programs.md)).

**Domů underneath.** A reader who lands on another screen from outside the event (a notification, a shared link, a bookmark) would leave the app with the first Back. So `startLoader()` puts Domů under the first entry when `shouldInsertHome()` holds: the screen is not Domů (the first tab), the navigation type (`performance.getEntriesByType('navigation')`) is `navigate`, `history.state` is empty, and `document.referrer` does not start with the event's URL (`location.origin` plus `meta[name="event-base"]`; the app's `Referrer-Policy: same-origin` sends the full URL within the site). It then replaces the entry with `{screen: home}` at Domů's path and pushes the original URL, hash included, with `{screen}`. Domů is not fetched for it: Back lands on that entry, and `onPopstate()` shows Domů from the warm-up's copy or fetches it like any other screen. A reload, a traversal, an entry the loader wrote before, a link from inside the event and Domů itself insert nothing. Otherwise the entry keeps its state and gains its screen (`{...history.state, screen}`), so a reloaded sheet's `pgOverlay` survives. The Domů entry is written at load, without user activation, so Chrome's history-manipulation intervention marks it skippable: the browser's own Back (Android's Back included) passes over it until the reader activates the page with a tap, a click or a key. Scrolling does not count, since a touch that becomes a scroll ends in `pointercancel`, and a notification opened through the worker's `clients.openWindow` brings no activation either. So in Chrome a reader who opens a notification, only reads and scrolls, and presses Back leaves the app, and an installed app opened fresh that way closes. The mark is expected to clear on a later activation, which is unverified on a device; what WebKit does is unverified too.

## Revalidation and the morph

Showing a cached screen is instant, always; one fetched more than five minutes ago is revalidated in the background, and a screen whose HTML has actually changed is **morphed** into the new one rather than replaced — `innerHTML` would throw away the very state the cache exists to keep. The morph (`loader/morph.js`) is hand-rolled and small (no diffing library, and deliberately not a vendored Idiomorph): children match on `id`, then `data-key`, then position among same-tag siblings; a subtree already equal to its counterpart is skipped outright; a matched `<iframe>` is never written to *and never moved*, because a move re-inserts it and a re-inserted iframe reloads. It writes only the attributes the fresh markup states — one it does not carry at all belongs to the client (`--hour-width` lives in `.pg`'s `style`, `data-hour-step`, `data-pg-ready`, `disabled`) — and one the markup names in **`data-morph-keep`**, for the attributes the server writes without owning: `.pg`'s `data-view` and `data-step`, `.tl-page`'s `class`, a day chip's `aria-current`, `.mapview`'s `data-view`. Without that the screen would be put back on the server's default view and page, and a layout landing in the gap before the screen restores itself would take the reader's scroll with it. What the screen does own it puts back on a `screen:morphed` event, dispatched synchronously in the same task. A morph, like a replacement before it, never happens while the reader is in the middle of a screen — an open sheet or focus in a form field defer it to the next time that screen is shown, and it then runs *after* the screen is visible again, for the same reason the wiring does. Measured on the Program screen: a revalidation that finds no change touches **zero** nodes; one that finds a renamed, re-timed programme touches seven, on a screen holding sixty cards.

## Transitions

Screens slide **by tab order** through the View Transitions API: the loader only sets `data-nav` on the root and the animations live in the one reduced-motion block, alone in `www/css/motion.css`, so where the API is missing — or reduced motion is asked for — the swap is instant rather than animated by hand. There is deliberately **no swipe gesture**: a horizontal drag on the timeline means "scroll the hours".

## What the loader does not take over

A response that is not a 200 is not a screen: the loader falls back to a plain navigation, so the reader gets the server's own error page instead of an app bar injected into a `<section>`. So does a screen the reader is waiting for that has not arrived after 8 s (`LOAD_TIMEOUT`, an `AbortController` on `load()`'s fetch), because on lie-fi a fetch that never ends would leave the tap hanging for minutes. `show()` dispatches `screen:hidden` (bubbling) on the section it hides, so a screen's own dialogs do not outlive it. A tap on the tab of the screen already shown, or on a link to the address on show, navigates nowhere: the loader scrolls that screen to the top (smoothly, unless reduced motion is asked for), as a native tab bar does, instead of letting a plain navigation throw the live app away.

The skip link is the other same-origin link the loader handles itself: it names the path the document was first served for, which after a swap is another screen, so a click on it focuses the visible screen's section and navigates nowhere. The participating set is read off the rendered shell — the tab bar's own links plus the profile one, in that order, which is what makes `/profil` count as forward — so it is Domů, the enabled tabs and `/profil` and nothing else. The handbook PDF, external links, `/admin/notify` and **every non-GET** are never the loader's. A write — the pairing start, the logout, a register or unregister, each a `form[data-write]` — is sent by `shell/write.js` instead: a `fetch` POST with `X-Write: 1` that the worker sees and purges on, answered with `{"next": …}`, and then a full navigation to that address with `location.replace()` (a write-and-reload of the entry when only the hash differs), so a write reloads the document and empties the cache with it, and replaces its history entry instead of adding one ([http.md](http.md)); without JavaScript it is the plain POST and its redirect. That is the correctness rule rather than laziness, because the identity changes both the app bar and the registered marking on every programme. The end of a pairing is a GET poll answered by JSON, so `profile/pairing.js` loads Profil again itself, also with `location.replace()`. Every link stays a real `<a href>` and the loader is an enhancement layer, not a client router: without it the app behaves exactly as it did.

## The loader and the worker

The loader and the worker: `revalidate()` sends `cache: 'no-cache'` and `load()` does not. `go()` dispatches `screen:loading`/`screen:loaded` on `document` around a fetch the reader waits for, never around a background revalidation (and `screen:loaded` once more on an instant show, so the bar of an overtaken tap goes). The loader listens to the worker: `screen-updated {path}` and `news-updated {programme}` set the entry's `fetchedAt` to 0 (Informace and Domů always, the Program screen too for a programme message) and revalidate the one on show, so a new `.news[data-key]` is morphed in at the top; a path reported before the loader has it waits in `staleOnArrival`. `syncFreshness()` dispatches `screen:freshness` on the section whenever it changes either attribute.

## Toasts

**Toasts.** One component, `templates/_toast.twig` (`<div class="toast" role="status" data-toast data-key="toast">`: a title, an optional second line, a `✕` `[data-toast-close]` with `aria-label="Zavřít"`), a `structure`-filled banner with a hairline at the top of the screen, gone after 6 s on display (`TOAST_MS` in `shell/toast.js`, which arms a server toast only once its screen is shown) or on the close tap. The server's toasts are `Toast\Toasts`: where one waits, which request takes it, and how a response that carries one is marked `X-Toast: 1` so the worker keeps it out of the offline copy, is in its docblock. Profil takes the login and logout toasts, Program the registration ones. The shell's own toast is the offline one (below). A toast that leaves while its `✕` has the focus hands the focus to the visible screen — or, with the programme sheet open, to the sheet's card (`removeToast()`). Without JavaScript the `✕` is hidden and the toast leaves by CSS after the same 6 s ("Without JavaScript", below).

## The modules

The scripts are native ES modules under `www/js/`, one directory per concern, and no file is an IIFE or sets a `window` global as an entry point. A module whose screen has behaviour returns its entry from `ModuleInterface::script()`, always `<dir>/index.js`; Home, Profile, Programs, Map and Push have one, the shell's is `shell/index.js`, and Info, Handbook and Admin return null.

| Directory | What it holds |
|---|---|
| `events.js` | the eight DOM event names, and the only file that spells them |
| `loader/` | `loader.js` (the screen stack, `startLoader()`), `morph.js`, `warmup.js` |
| `shell/` | the entry, `worker.js` (the worker's registration), `netstate.js`, `toast.js`, `write.js` (the writes, above), `confirm.js`, `progress.js`, `install.js` |
| `ui/` | shared helpers: `clock.js` (`now()`, the Prague calendar, `onClockRedraw()`), `reltime.js`, `screen.js`, `dom.js`, `tabs.js`, `pinch.js` |
| `home/` | Domů's clock-driven parts ([home.md](home.md)) |
| `profile/` | `pairing.js` (the poll, [auth-and-session.md](auth-and-session.md)) and `mode.js` (the colour mode, [theming.md](theming.md)) |
| `map/` | Místa ([map.md](map.md)) |
| `programs/` | the Program screen ([programs.md](programs.md)) |
| `push/` | the notifications opt-in ([push.md](push.md)) |

**`events.js`** holds the names `screen:shown`, `screen:hidden`, `screen:morphed`, `screen:freshness`, `screen:loading`, `screen:loaded`, `sheet:closed` and `pg:tick`. Every other module listens through its `on…()` helpers and dispatches through its `emit…()` helpers, and `JsModuleGraphTest` fails when any other file spells a name. The names are part of the page's contract: the browser tests dispatch `pg:tick` and listen for `screen:morphed` by name.

**The load order.** `_layout.twig` writes a `<link rel="modulepreload">` for every file the entries import (`Http\ScriptGraph::imports()`), so the browser fetches the whole graph at once, then one `<script type="module">` per entry in `Modules::scripts()` order, which is `ModuleRegistry::ORDER`: shell, home, profile, map, programs, push, each only when the event has it. A module evaluates after the modules it imports, in the order it imports them, and the entries in document order. Two things depend on this order, and both need the loader to start first:

- `startLoader()` files the first screen's `innerHTML` as it was served, to compare later revalidations against. A module that drew into that screen before it would make every landing page morph once for nothing. So `shell/index.js` imports its own modules and then calls `startLoader()`, before any screen's entry runs.
- A deep-linked programme sheet extends the loader's history entry. The loader writes that entry in `startLoader()`, so it must exist before the Program screen starts.

No entry is `async`, no module uses a dynamic `import()` or a top-level `await`: several modules draw on `DOMContentLoaded`, and a module that runs later misses it without an error. `JsModuleGraphTest` guards all three.

**The test seams.** The browser tests reach into a page in two ways only. `window.pgClock` replaces the device clock: `ui/clock.js`'s `now()` reads it at each call, never at import, because a test sets it after the page has loaded, and no other module names it. `window.appWarm === false` stops the warm-up (`BrowserTestCase::coldScreens()`). The modules also read `fetch`, `document.startViewTransition` and `navigator.onLine` at call time, because the Chrome tests replace them after load.

## The network banner

`shell/netstate.js` draws **the network banner**: one `<p class="netstate" data-netstate aria-hidden="true" hidden>` per document, outside every screen, docked right above the tab bar, which shows only offline (`Jsi offline. Data byla naposledy aktualizována v 10:20 (před 25 min).`) or online with an old copy (`data-stale`: `Nepodařilo se načíst aktuální data. Zobrazuji stav z 10:20 (před 25 min).`) and is otherwise hidden. The time is the visible screen's `data-fetched-at` on the reader's clock, re-read on every draw (`DOMContentLoaded`, `screen:shown`, `screen:morphed`, `screen:freshness`, `online`/`offline`, `visibilitychange`, `pg:tick` and every minute), so switching to a screen fetched earlier changes it at once; the age is `právě teď` under a minute (never `před 0 min`), `před N min` under an hour, then `před N h`, then the date. Its height is published as `--netstate-height` on the root (0px while hidden, kept current by a `ResizeObserver`), which the docked view switcher (Program, a two-view Místa), every screen's bottom padding and `--screen-height` add, so the banner covers nothing. A screen reader hears it through a live region of its own (`<p class="sr-only" role="status" data-netstate-live>`), written only when the state changes and without the ticking age.

## Toast, confirmations, clock, progress, install

`shell/toast.js` runs **the toast** (above): it arms server toasts on display, and on `#offline` in the URL it shows the offline toast (`showOfflineToast()`: `Akci není možné provést, protože jsi offline.` / `Zkus to znovu až najdeš místo se signálem.`) and strips the hash with `history.replaceState`; `shell/write.js` shows the same toast when a write's `fetch` rejects. `shell/write.js` sends **the writes** (above): it is imported after `toast.js` and before `confirm.js`, and since `confirm.js` stops a two-tap button's first tap at `click`, only the confirming tap reaches its `submit` listener; the Program root's own listener (the `pohled` field) runs before it. It disables the form's buttons while the write is on its way (enabled again when the `fetch` rejects, and on `pageshow`), lands on a usable `next` (`follow()`: `location.replace()`, or, for an address that differs only by its hash, `history.replaceState()` and `location.reload()`, keeping `pgOverlay` in `history.state` only when the address names a programme), and sends any other answer again as the plain form (`form.submit()`). `shell/confirm.js` owns **the two-tap confirmations**: a button with `data-confirm` (the logout, the unregister) swaps its label for the question on the first tap and submits on the second, starting over on `screen:hidden`, `sheet:closed` and `pageshow`. `ui/clock.js` redraws **the clock-driven parts** from `now()`: every module that draws from the device clock subscribes with `onClockRedraw()`, and its subscribers run in order on `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `visibilitychange`, `pg:tick` and every minute. `ui/reltime.js` subscribes first and redraws every `data-sent-at` relative time; Domů's parts follow ([home.md](home.md)). `shell/progress.js` toggles `data-loading` on the root for the 2px `.progress` bar at the tab bar's top edge (`var(--on-structure)`, the bar's own ink, because `state` is under 3:1 on a pale bar; a static bar under reduced motion). `shell/install.js` keeps `beforeinstallprompt` (default-prevented, so Chrome shows nothing by itself) for the install card's hidden `Uložit jako aplikaci` button, which shows the kept offer once and is hidden again after the tap, on `appinstalled` and in an installed app (`display-mode: standalone` or iOS's `navigator.standalone`). iOS has no install prompt at all, so on an iPhone or iPad the card's `[data-install-ios]` hint (`Aplikaci si přidáš na plochu v Safari: klepni na Sdílet a pak na Přidat na plochu.`) shows instead, outside an installed app only. The map's offline note is `map/offline.js`'s ([map.md](map.md)).

## Other scripts and asset versions

`_layout.twig` also carries `<noscript><p class="noscript">` as `<main>`'s first child ("Without JavaScript", below). Nothing is bumped by hand, and `sw.js` is never versioned. The core stylesheets under `www/css/` (base, the registered modules' own, motion; `Module\Modules::sheets()` gives their order, [theming.md](theming.md) why) and the event's own sheet after them are each linked through the Twig function `asset_version('css/base.css')` → `css/base.css?v=<first 8 hex of sha256>` (`App\Http\AssetVersion`, memoised by path, mtime and size for the rest of the request only, since PHP keeps no static property between requests), so a changed sheet changes only its own hash.

The scripts are linked through `script_url('shell/index.js')` → `/js/<hash>/shell/index.js`, in the order above. The hash is one for the whole tree (`App\Http\ScriptVersion`): the first 8 hex of a sha256 over every file under `www/js/`, its relative path and its content, in path order. It is computed at most once per request, and kept across requests with the import graph the preloads come from (`App\Http\ScriptGraph`) in `var/cache/scripts-version-<key>.json` and `scripts-graph-<key>.json` (`App\Http\ScriptTree`), where the key is a sha256 over one stat walk of the tree (every file's path, mtime, size and inode): a changed, added or removed file is seen by the next request, and a new entry removes the old ones. The layout reads the preloads through the Twig function `script_preloads()`, so a fragment, which prints no layout, never reads the graph. So a changed, added or renamed script changes the prefix of every script, not only its own. That is the point: a module's relative imports resolve under its own prefix, so a page asks for all its modules under one deploy's prefix, and the year of `immutable` the servers give `/js/` is safe for the current deploy's URLs. The prefix is not a directory. Three rules strip it, one per server, and they must agree: `docker/nginx.conf` (a server-level `rewrite`), `www/.htaccess` (a `RewriteRule` right after `RewriteEngine On`) and `eventapp_script_file()` in `bin/script-path.php`, which `bin/router.php` and the gates' `tools/Gate/front.php` call. Each serves `/js/<8 hex>/<path>` as the file `www/js/<path>`, for any 8 hex, and `DeploymentFilesTest` keeps the three in step. An import map would have been the other way to version imports. It was declined because it needs Safari 16.4, which would change what old iPhones get. What the rewrite cannot prevent, during an upload and for a page that still holds an older deploy's HTML, is in [deployment.md](../deployment.md).

The self-hosted fonts and icons under `www/fonts/` and `www/vendor/` carry no hash and follow one rule instead: **a changed file gets a new name** (a new Montserrat is `montserrat-v<N+1>-…`, a new Font Awesome a new `fontawesome-free-<version>/` directory), never new bytes under the old one — nginx and `.htaccess` give both prefixes a year of `immutable` and the worker serves them cache-first, so a file replaced in place would never reach a returning reader.

## Manifest and head icons

Each `site.webmanifest` carries `id`, `lang`, `orientation`, a maskable 512 icon and `shortcuts` for the enabled Program and `Notifikace` (Informace); `<link rel="mask-icon">` is emitted only for an event whose config has `assets.pinnedTab` (obrok19 only). The three head icons default to `events/<slug>/favicon-16x16.png`, `favicon-32x32.png` and `apple-touch-icon.png`; the optional `assets.favicon16`, `favicon32` and `appleTouch` override them, which is how obrok27 serves the set `bin/event-icons.php` generates from its white lilie on `#15133f`: content-hashed `icon-<hash8>-<size>.png` names (nginx and `.htaccess` serve PNGs under `www/events/` as immutable for a year, so new bytes under an old name would never reach a returning browser), favicons transparent when the source is (obrok27's are opaque `#15133f` squares), opaque home-screen icons on the background colour (iOS paints transparency black) and a maskable one inside the 80 % safe zone, with the manifest's icons rewritten in place.

## The install card

**The install card** (`templates/_install.twig`, on Domů as `installCard: 'home'` and on Profil as `'profile'`) puts the install offer and the notifications button under one heading (`Ulož si <event> na plochu`, then `Zapni si upozornění, ať ti neuteče výběr programů, novinky a varování v průběhu akce.`): the hidden `Uložit jako aplikaci` button (`.install[data-install]`, `.install-btn`), the iOS hint (`[data-install-ios]`), and, for a push event, the `Povolit notifikace` button (`data-push-toggle`) with its `.push-status` line. In an installed app Domů hides the whole card (`data-install-card="home"`) and Profil only the install half.

## Without JavaScript

The site works in full without JavaScript: every script only enhances what links and forms already do. **The `js` class**: `_layout.twig`'s one inline script in `<head>`, after the `theme-color` meta and before any stylesheet, is rendered for every event and starts with `document.documentElement.classList.add('js');`; on a dark-capable event the mode code follows inside the same script ([theming.md](theming.md)), so a dark event still has exactly one inline script. Since the class is on the root before any sheet applies, the stylesheets key the two kinds of reader off it: a rule for the reader without a script is scoped `:root:not(.js) …`, a part only a script can drive is hidden by `:root:not(.js) <selector> { display: none; }` next to that part's own rules, and a part shown only without a script by `:root.js <selector> { display: none; }`. With JavaScript on, nothing scoped to `:root:not(.js)` ever paints a frame.

**Links and forms first.** Every tab is a link to its own page and every write is a plain form POST answered with a 302 (`X-Write` only changes the answer for the script, [http.md](http.md)), so the loader and its history enhance pages that already exist rather than replace them.

**What is hidden, and why.** Four things are agreed to be JS-only: the notifications (the push opt-in needs the browser's push machinery), the offline copy (the service worker is registered by a script), the install button (Chrome's install offer reaches only a script) and the choice of theme (it lives in `localStorage` and is applied by the head script; without one the device's own setting decides through the media query in the inline `<style>`). So without a script the install card (`[data-install-card]`, `home.css`, which also holds the notifications button), Profil's mode control (`[data-mode-control]`, `profile.css`) and the toast's close button (`.toast-close`, `shell.css`) are hidden; the network banner (`[data-netstate]`) and the map's offline line (`[data-map-offline]`) are rendered `hidden` and only a script shows them. The notice says what is missing: `<noscript><p class="noscript">Bez JavaScriptu nefungují notifikace, offline režim, instalace ani volba vzhledu.</p></noscript>`, `<main>`'s first child in the document, never in a fragment.

**Each screen without a script**, in its area document: on Program each view pill is a link to its view's address, a row's or card's name links its sheet's hash on the current address (query included, through the Twig global `pageAddress`) and the sheet opens on `:target`, its close row and backdrop going to `#zavrit`; a Harmonogram chip links `/programy?den=<YYYYMMDD>`, a list chip its day's id (`#den-…` on Přehled, `#moje-den-…` on Moje), and the zoom pair is hidden ([programs.md](programs.md)). The register and unregister are plain POSTs whose 302 lands on the programme's deep link on the view the form's `pohled` names, so the sheet is open again under the toast; Back afterwards walks to the entry before the POST, an ordinary page, since only the script replaces the entry. On Místa the Mapa and Plán pills are links to `/mapa` and `/mapa/plan` and the plan's zoom pair is hidden ([map.md](map.md)). Domů's `Můj program` cards are drawn by the server for the request's moment, with their leads ([home.md](home.md)). The pairing wait is the `Zkontrolovat přihlášení` button, `POST /profil/kontrola`, which runs the poll's check on the server ([auth-and-session.md](auth-and-session.md)).

**Confirmations submit at once.** A two-tap button (`data-confirm`, the logout and the unregister) is stopped at its first tap only by `shell/confirm.js`; without it the button is an ordinary submit button and the first tap submits the form.

**The toast leaves by CSS.** Nothing removes a server toast without `shell/toast.js`, and its close button is hidden, so `motion.css` makes it leave after the same 6 s the script waits, through the keyframes `toast-gone` (to `opacity: 0; visibility: hidden`). Before the motion block, `:root:not(.js) .toast { animation: toast-gone 0s 6s forwards; }` hides it at once: a 0s animation is no motion, so a reader with reduced motion is not left with a toast that covers the top of the screen and cannot be closed. Inside `@media (prefers-reduced-motion: no-preference)`, `:root:not(.js) .toast { animation: toast-gone var(--motion) ease 6s forwards; }` overrides it by source order with a fade.

`Tests\Browser\NoJsTestCase` runs Chrome with scripts off; what it covers is in [tests.md](tests.md).

## Two rules

Two rules the shell depends on. `<main>` must **never** carry a `view-transition-name`, however natural it looks: naming an element makes it a stacking context, and the sheet is a fixed child of `<main>` that has to keep painting over the fixed tab bar. Only `.appbar` and `.tabbar` are named, which takes them *out* of the root snapshot so the shell sits still while the screen under it slides. And the per-screen layout rules key off the section (`.screen[data-tab="map"]`, `"programs"`, `"homepage"`) rather than the old `body.screen-*` classes, with `main > .screen[hidden]` restating `display: none` loudly enough to out-specify them.
