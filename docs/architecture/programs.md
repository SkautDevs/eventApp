# Programs

This document covers the Program screen: its three views, the day chips, the programme sheet and registration.

## The Program screen

`ProgramsModule` (`/programy`, tab `Program`, title `Programy`) is the single Program screen. Its directory, `src/Module/Programs/`, also holds its actions and the pure builders named below where each does its work. Its behaviour is `www/js/programs/` (see [The script](#the-script) below), not an inline `<script>`, which no screen swap could reach. Everything the screen shows comes from `ProgramProviderInterface`. When a participant is paired, the module also calls `getParticipant()` and marks their programmes `registered` — that marking is what login changes on the screen, besides the sheet's footer, so keep it working when the screen changes. kissj's session read lists real registrations only, and a preregistered programme (kissj's `isPreregistered`, the internal `preregistered`) belongs to a role, so eventApp cannot tell whose it is: a preregistered programme is **never dimmed** and is in neither Moje nor Domů's `Můj program` (a known limitation until kissj sends the participant's role). Times of day in a range are written one way, `Times::CLOCK` (`G:i`: no leading zero on the hour, an unspaced en dash, `8:00–22:00`) — in the sheet's Kdy, the toast, the list rows, the timeline card's name and Domů's cards; a run over two days names both (`čt 3. 6. 22:00 – pá 4. 6. 1:30`); the hour ruler keeps `08:00`.

**Three addresses, one screen.** Each view has a path of its own, and all three are routes to `Programs\ShowAction`: `GET /programy` (name `programs`, argument `view=timeline`), `GET /programy/prehled` (`programs-overview`, `view=overview`) and `GET /programy/moje` (`programs-mine`, `view=list`). The two view addresses also carry the argument `screen=/programy`, so `Http\ScreenAliasMiddleware` renders them as the one Program screen: `data-screen` is `/<slug>/programy` on all three, in a page and in a fragment alike, and the tab declares the other two as `data-screen-aliases` (`MenuItem::$aliases`, [bootstrap-and-config.md](bootstrap-and-config.md)). The view the address names is the first paint: `ProgramsPage::$view` is written into `.pg`'s `data-view`, and its pill carries `aria-selected="true" aria-current="page"` while the other two carry `aria-selected="false"`. The markup writes no `tabindex` on a pill, so every pill is reachable without JavaScript; `ui/tabs.js`'s roving tabindex is put on at wiring (`showView()`, `markSelected()`). Once the script runs, a pill's `aria-selected` and `aria-current` are the reader's, so each pill lists both in its `data-morph-keep`, as a day chip does its `aria-current`. `data-view` stays in `data-morph-keep`, so a background morph from another address never moves the reader off the view on show. Every `.sheet-body` carries the programme's deep link id, `id="section-<sectionId>-program-<id>"` (`Sheet::$sectionId`, 0 when the record names no section).

## Three views

The screen holds three views of that one data set, in a floating pill above the tab bar (`aria-label="Zobrazení programu"`, in this order): **Přehled** (`far fa-list-alt`), **Harmonogram** (the default, so the now-landing is unchanged) and **Moje** (`far fa-user`).

**Links underneath.** Each pill is `<a class="tabs-tab" role="tab" id="pg-tab-<view>" href="…">` to its view's address (`url_for()` of `programs-overview`, `programs` and `programs-mine`), keeping `role="tab"`, `aria-controls` and `aria-selected`; without JavaScript a pill is a plain navigation, and the server paints the view the address names. Every programme's list row (`.pl-open`) and timeline card (`.tl-card`) is a link to its sheet, `{{ pageAddress }}#section-<sectionId>-program-<id>` (`ListItem::$sectionId`, `Card::$sectionId`, the programme's `sectionId` as on the sheet body), so the hash stays on the address the reader is on, query and all (`pageAddress`, [shell-and-loader.md](shell-and-loader.md); a bare `#…` would resolve against `<base href="/">`). A Program screen the loader fetched, or a background morph rewrote, carries the address it was fetched from, the screen's own path, so its links read `/programy#…` on any view; only a click with a modifier key ever follows one with JavaScript on, and it opens that sheet on Harmonogram. The script takes them over: the root's click handler calls `preventDefault()` on a plain primary click (no modifier key) on an `a` carrying `data-pg-view`, `data-pg-open` or `data-pg-close` and then acts as it did for the buttons these were (`selectView()`, `openSheet()`, `closeSheet()`), and the loader's link handler skips a default-prevented click. A click with a modifier key is left to the browser (a new tab on the view's or the sheet's address) and the screen does nothing. Space on one of those links presses it, as it pressed the button (a link answers Enter alone).

**The view is the URL.** `programs/maths.js` maps the two ways: `viewFromPath(pathname, screen)` reads the screen's own path as `timeline`, `screen + '/prehled'` as `overview`, `screen + '/moje'` as `list` and anything else as `null`, and `viewPath(view, screen)` is its inverse. `screen` is the root's `closest('[data-screen]')`'s `data-screen` (`ctx.screen`, `''` for a root in no screen, which then has no address to read or push). A pill, tapped or reached with the arrow keys, calls `ctx.selectView(view)`: it shows the view and pushes `{screen, pgView: view}` for `viewPath(view, screen)`, unless that address is already the one on show, so re-selecting the shown view pushes nothing and five taps on other views mean five Backs. `ctx.showView(view)` only shows (a morph, a deep link, Back) and pushes nothing; it marks the shown pill `aria-selected="true"` and `aria-current="page"` and takes `aria-current` off the others. The view is read from the URL on the three triggers the loader leaves to a screen ([shell-and-loader.md](shell-and-loader.md)): on **wiring** (`ctx.view` starts as `viewFromPath(location.pathname, screen)`, then the server's `data-view`, then `timeline`), on **`screen:shown`** of an already wired screen (`ctx.syncFromUrl()`: the address's view when it names one, then `fromHash()`), and on **`popstate`** while the screen is on show (`views.js`'s listener, registered before the sheet's, shows the address's view; the loader keeps the screen up for an address of the current screen). The wiring reads `location.pathname` rather than `data-view` on purpose: offline, the worker answers all three addresses from the one copy stored under the screen's key, whose `data-view` is the view of whichever address was stored last. The loader learns an address a pill pushed on the next click (`noteAddress()` runs first in its click handler), so a view chosen with the arrow keys is still the one the Program tab comes back to.

## Harmonogram

**Harmonogram** (the timeline) is a Gantt grid: rows are the distinct `location` values (`location` is reused as the stage axis — the contract has no `stage` field, and programs with a null location fall into a `Bez lokace` row), columns are hours, one page per **day** holds every section's programmes (key `page-YYYYMMDD`), and it is the one place in the app allowed to scroll horizontally. Overlapping programs in one location are packed into sub-tracks by a greedy interval fit. A programme that runs over several days sits on the page of **every calendar day it overlaps**, each piece clipped to its day (`TimelineBuilder::segments()`, at most `MAX_DRAWN_DAYS`), so no piece can stretch a day's axis; an end at exactly 00:00 belongs to the day before, so 23:45–00:00 stays one card on its evening. Every piece carries the programme id as its `data-key` — unique among siblings, which is all the morph matches on, because a page holds one piece per programme — opens the one sheet, and has the same registered state and label; a label names both days whenever the run spans more than one. The sheet, and with it the deep link, belongs to the start day's page, and the lists list the programme once, under that day.

## Zoom

The hour scale is zoomable: everything on the grid is positioned as `calc(var(--hour-width) * n)`, so setting that one property rescales the time axis and nothing else — never `transform: scaleX()`, which would distort the programme names. `--hour-width` runs between `--hour-width-min` and `--hour-width-max` (40–200px, declared in `www/css/programs.css` next to the property), opens at 80px, and is driven by a −/+ pair at the right end of the timeline's day strip, by a two-finger pinch on the grid (`touch-action: pan-x pan-y` on `.tl-scroll` keeps the browser's own pinch out of it; the viewport meta is deliberately left alone so page zoom still works everywhere) and by ctrl+wheel. Only the script drives it, so without JavaScript the pair is hidden (`:root:not(.js) .pager-zoom`) and the scale stays at 80px. Every step recomputes `scrollLeft` so the moment under the anchor — the midpoint between the fingers, or the centre of the visible grid for a button — stays put. The scale is kept in `sessionStorage` under `pgZoom:<slug>`, so paging and view switching preserve it and a fresh visit starts at 80px. Below a threshold the ruler thins its text to every second hour while every hour keeps its mark — the script sets `data-hour-step` on the root from the live scale and `www/css/programs.css` hides `.tl-tick:nth-child(even) .tl-tick-label`, so tick positions never move and the leftmost hour is never blanked. The threshold is the rendered label's width plus 19px, measured on the page rather than hardcoded because themix and Montserrat differ by 6px at 14px/700.

## The now-line and the landing

The day holding **now** carries a current-time line: every timeline page states its axis as two instants, `data-axis-start`/`data-axis-end` (`axisStart`/`axisEnd` in the page view model, `DATE_ATOM` with the offset, the provider's wall-clock read as Europe/Prague whatever the server's zone), so `programs/nowline.js` places now by subtraction on any phone's zone and formats only the label (`formatNow()` in `programs/maths.js`), through `Intl.DateTimeFormat` with `timeZone: 'Europe/Prague'`. What it writes — `data-now` on the one `.tl-page` whose axis holds now and its inline `--now-offset` in hours — the server never writes, so a morph leaves both alone, and `afterMorph()` re-runs `updateNow()` anyway. The line (`.tl-now`, inside `.tl-inner`, which is positioned for it; z-index 2, so over the cards, under the pinned stage column's 3 and the ruler's 6) and its mark on the ruler (`.tl-now-tick` with its `HH:MM` label, inside `.tl-ticks`) are in `--hour-width` units, so the zoom carries them. It updates every 30 s and on `screen:shown`, `visibilitychange` and a morph. The first plain landing inside the event (no `#section-…-program-…` deep link) opens the timeline on today's page with now a third of the way into the visible hours, even from a copy cached days ago whose server-chosen page is stale. A page's axis runs only from its first programme to its last, so before the day's first or after its last now lies on no axis: the landing then falls back to the page keyed `page-` + today's date (`formatDay()`, built from `Intl.DateTimeFormat.formatToParts` in Europe/Prague, not from a locale's printed order) and opens it without a line and without scrolling. The clock is `ui/clock.js`'s `now()`, which reads `window.pgClock` (a function returning ms) when set, and a `pg:tick` event on `document` re-runs `updateNow()`; both exist for the browser tests, and `BrowserTestCase::pinClock()` installs the clock over CDP before any page script and removes it after the test.

## Přehled and Moje

**Přehled** and **Moje** are one list component (the Twig macro `dayList(kind, days)`, built by `DayListBuilder::buildDays($programs, $registeredIds, $mineRead)`): Přehled holds every programme (`overview`), Moje only the participant's (`days`), each grouped by **day** like the timeline, each in its own view container (`#pg-view-overview`, `#pg-view-list`; the morph matches keys among siblings, so the two may reuse the day keys and the programme ids). Neither pages: every day is in the document, first to last, under its own **sticky heading**, and the reader scrolls the lot. Each item (`.pl-item`, `data-key` the programme id, `data-start`/`data-end` as `DATE_ATOM` instants from `Times::instant()`) is a start-time column (`.pl-time`), the name as the control that opens the sheet, then `.pl-meta` (`do 12:30 · Žlutý les`), a `Zapsáno` tag (`.pl-tag`) on a registered one — in Přehled on the participant's rows, in Moje on every row — and in Moje the perex. A programme with photos also carries the first one's **thumbnail** (`ListItem::$thumb`, the first image's `thumbUrl`): the row gains `has-thumb`, which adds a third 56px grid column, and a `.pl-thumb-frame` (`data-key="thumb"`, `aria-hidden`, `tonal` with the event's placeholder logo from `_photo_mark.twig`) holding a lazy `.pl-thumb` (`data-photo`, so `gallery.js` marks it `is-loaded` and it fades in as the sheet's photos do, and `data-morph-keep="class"`, so a revalidation morph keeps that mark). A row without photos has no frame and its two columns as before, so the time and the name line up in every row. The thumbnail and the `probíhá` chip both sit at the row's top right, so on a `has-thumb` row the chip moves to the frame's left (`right: calc(14px + 56px + 10px)`). Without a script the thumbnail shows as it loads. Dimming (`.is-dimmed`, with `opacity` — never a colour, because no sheet under `www/css/` may name one — at a strength that keeps the ink at AA) is Přehled's only among the lists, and the timeline's cards: only when the participant's list was actually read (`mineRead`), and never on a preregistered programme; logged out, or paired while `getParticipant()` failed, nothing is dimmed and Moje shows no `Zatím nemáš zapsaný žádný program.` line (the notice explains), since "not chosen" would be a guess; logged out, Moje is the link `Pro svůj program se přihlas kódem z KissJ.` to Profil. Nor does any view say `Program zatím není k dispozici.` when the list could not be read at all (`programmesUnavailable`).

## Day chips

Each view picks its day from a **strip of day chips**, one per view and separate elements (`.pager[data-pg-pager=<kind>]` for kinds `overview`, `timeline`, `list`, holding `<div class="days" role="group" aria-label="Dny" data-pg-days="<kind>">`, the timeline's with its zoom pair beside it) — no arrows, no day menu, no dialog. Every chip is a link, `<a class="day-chip" href data-key data-pg-page data-pg-kind>`, its `data-key` the day's own key (`page-YYYYMMDD` or `day-YYYYMMDD`) so the morph matches it by key, at least 44 × 44, and the current one carries `aria-current="true"` (the others `"false"`) and wears the `state` fill under `on-state`, as the active tab does; `aria-current` is the reader's, so every chip names it in `data-morph-keep`. On Harmonogram a chip switches the page (`showPage()`); in a list the current chip **follows the scroll** and a tap smooth-scrolls (unless reduced motion is asked for) to that day's start — the list behaviour is built per kind for every `[data-pg-pager]` whose kind has a `.pl-day` list. `markChip(kind, key)` marks the chip and brings it into its strip by setting the strip's own `scrollLeft` — never `scrollIntoView()`, which would move the window too — because a strip wider than the phone scrolls sideways (`overflow-x: auto`, no scrollbar); a strip in a hidden view measures nothing, so the view switch brings its chip round when it is shown. The strip keeps `--pager-height`, so the band below stays where it was.

**Without JavaScript the chips are links.** A Harmonogram chip links `/programy?den=<YYYYMMDD>` (`url_for('programs')` plus the day's date): `Programs\ShowAction` reads the query `den`, and when it is an eight-digit string whose `page-<den>` is a timeline page's key, that page is the active one (its `is-active`, its chip's `aria-current="true"`); anything else (another format, an array, a date with no page) leaves today's rule (`ScheduleBuilder::activeKey()`). The page's links are built on `pageAddress`, query included, so a sheet opened and closed on `?den=` stays on that day. A list's chips link to the day's id on the address on show (`pageAddress`): Přehled's `.pl-day` carries `id="den-<YYYYMMDD>"` and Moje's `id="moje-den-<YYYYMMDD>"` (both lists are in the document, so one id per day would collide), and each strip's chips link to their own (`#den-…`, `#moje-den-…`). `.pl-day`'s `scroll-margin-top` is the same three tokens as `bandTop()`, so the browser's own jump docks the day's heading under the strip, where the script's scroll puts it. The morph matches a `.pl-day` on its id, which is as stable as its `data-key`. With JavaScript the root's click listener takes a plain primary click on a chip (`preventDefault()`), so a chip switches the page or scrolls the list without a URL change, while a modified click is left to the browser; Space presses a chip as it did the button. The boot shows the page `denPage(location.search)` (`maths.js`) names when the screen has it, because the worker answers an offline `?den=` visit from the screen's copy stored without the query, rendered on another day; such a landing does not then go to now.

Nothing of this runs on a scroll event: an `IntersectionObserver` watches the day sections against a band starting one pixel below the strip — one pixel, because a day scrolled to its own start puts its top edge and the previous day's bottom edge on the same line and an observer asked about that line answers "both" — and each crossing costs one coalesced `requestAnimationFrame` that reads no geometry. The day owning the top of that band is the day whose heading is stuck there, so the strip and the heading cannot disagree — which holds only because `.pl-head`'s dock line, `bandTop()` and the observer's `rootMargin` all read the **same three tokens**, `--appbar-height` + `--appbar-inset` + `--pager-height`. Leaving the safe-area inset out of any one of them docks the heading behind the strip on a notched install (34px, measured). The observer fixes its margin at creation, so an inset that changed at runtime would leave the band stale until it is rebuilt; nothing does that yet. `.pl-day:last-child` carries a `min-height` of the reading band, or the last day could never dock under the strip and its chip would land short of it.

## Now in Moje, scroll and perex

In Moje `updateNow()` marks the list from the reader's clock with a client-owned `data-now`: `running` on every item whose span holds now, and `next` on the first item still to start on the day that is today (a list read the evening before shows nothing). CSS hangs a `probíhá` chip in the running card's top-right corner (`.pl-item[data-now="running"]::after`, on the card rather than in `.pl-time`, so it escapes the time's 0.75 opacity, with `.pl-time` padded to leave it room) and draws the "teď" line with its `teď` chip above the next one; both chips are small fills of `--now` under `--on-action`, the timeline label's pair, AA by construction — never `--now` as ink, since it is the action fill and as text on a pale ground falls to 2.8:1 (`ThemingTest::testTheNowChipsCarryTheirInkAtAA` measures the pair in every set). The list never scrolls to it. The screen's scroll offset is live state like everything else, so leaving a list and coming back lands where the reader was; switching to Harmonogram and back does too, because that view is exactly one screenful and the browser clamps the window's scroll while it is up, so `showView` saves and restores it. A perex is plain text whose `\n`s are meant (kissj's API contract 3.0), so `.sheet-perex` and `.pl-perex` are `white-space: pre-line` and the template puts nothing but the escaped text inside them.

## The sheet

Tapping a programme opens its **sheet**: the name, the section as a tonal chip (`.sheet-chip`), `<dl class="sheet-facts">` with `Kdy` and `Kde`, `Tvůj program` on a registered one, the organisers' messages about it (`Oznámení`, each with its `data-sent-at` time), the perex, and a `.sheet-footer` with exactly one child keyed by its state (so a morph from unregister to register replaces the form rather than patching it, and no whitespace inside, or `.sheet-footer:empty` stops matching) from `SheetBuilder::footer()`, in this precedence: not paired → `unpaired`, a link to Profil `Pro zápis na programy se přihlas kódem z KissJ` that carries the programme (`profil?program=<id>`), so the login comes back to this sheet ([auth-and-session.md](auth-and-session.md)); then the window — `before` `Přihlašování začne 15. 3. 2027 v 18:00`, `after` `Přihlašování skončilo`, `none` `Přihlašování zatím není otevřené` (no trailing period); then, paired and open, `fixed` (nothing) for a preregistered programme, nothing at all while the participant's own list could not be read, else `register` (`Zapsat program`, `.btn-primary`) or `unregister` (`Zrušit zápis`, two-tap `Opravdu zrušit zápis?`). A window that cannot be read leaves every paired footer empty.

**Photos.** A programme with photos (`Programme::$images`, kissj contract 3.1; `Sheet::$images`) opens its sheet with a **gallery**, the first child of `.sheet-body`, before `.sheet-head`, keyed `gallery`: a `.gallery-strip` that scrolls sideways and snaps frame by frame (`scroll-snap-type: x mandatory`, `overscroll-behavior-x: contain`), one 3:2 `.gallery-frame` per photo, keyed `photo-<key>` by the photo itself (`Sheet::$imageKeys`: `Sheet::imageKey()`, the first 12 hex of the URL's SHA-256, with `-2`, `-3` on a repeated URL so the keys stay unique), never by its position, on `tonal`; a revalidation that reorders or replaces the photos therefore makes the morph insert a fresh frame (faded in, the placeholder on a failure) instead of writing a new `src` into a frame already marked `is-loaded`. A programme without photos has no gallery, and its sheet starts with its name. Each photo is `<img class="gallery-photo" … loading="lazy" decoding="async" crossorigin="anonymous" data-photo data-morph-keep="class">` covering its frame (`object-fit: cover`) with the photo's own `alt`; a closed body is `display: none`, so **nothing is fetched until the sheet opens**. Under the photo the frame holds the **placeholder**, the event's logo (`_photo_mark.twig`, `.photo-mark`, a third of the frame's width, decorative `alt=""`, lazy too): `mainLogo` with `mainLogoDark` as a `mode-light-only`/`mode-dark-only` pair when the event declares both, else `mainLogo` alone, else `menuLogo`, else nothing, the bare `tonal` frame (miquik26). With JavaScript a photo is transparent until `www/js/programs/gallery.js` marks it `is-loaded` (`:root.js [data-photo]:not(.is-loaded) { opacity: 0 }`), and `motion.css` fades it in over `--motion`, at once under reduced motion; a photo that fails is never marked, and the logo stays. Two or more photos make the strip a focusable scroll region (`role="group" tabindex="0" aria-label="Fotky"`), which a keyboard reader scrolls with the arrow keys, and add a row of **dots** (`.gallery-dots`, `aria-hidden`, a 6 px circle per photo, keyed `dot-<key>` like its frame in the sheet's ink, `on-surface` as `.sheet-card` rebinds it, at 40 % opacity, the shown one, `data-active`, at full opacity, so the pair reads on the sheet in every role set, where `edge` would not: it is obrok27's ink itself in light mode and 1.4:1 on its dark sheet); swiping is the only control. One photo has neither. `setupGallery(root)`, called where `index.js` wires each root, listens on the root in the capture phase, because neither `load` nor `scroll` bubbles: a `load` of an `img[data-photo]` adds `is-loaded`, photos already `complete` with a `naturalWidth` are marked at once and again after each morph of the screen, and a strip's `scroll` moves `data-active` to the dot `galleryIndex(scrollLeft, clientWidth, count)` names (the nearest frame, clamped, `0` for a strip with no width). A background morph writes every attribute the fresh markup carries, so the photo keeps its `class` (`is-loaded`) and each dot its `data-active` through `data-morph-keep`; since a dot the morph moved may then not be the strip's, each morph also moves `data-active` back to the dot the strip's scroll names. **Without JavaScript** nothing marks a photo and none needs it: the `:root.js` rule does not match, the `:target` sheet's photo shows as it loads over the logo, and the dots, which only the script moves, are hidden (`:root:not(.js) .gallery-dots`).

**The pin to the place.** `Kde` prints the programme's `location` as the record gives it. When that programme names a place (`Programme::$placeId`, kissj contract 3.1) that Místa can show, the location is a link instead, `<a class="place-pin" href="…" data-deep-link>` with a map-marker icon (`fa-map-marker-alt`, `aria-hidden`) before the same text, so the pin's text and the plain one never differ. Which place Místa can show is `Map\PlaceLinks::route()` ([map.md](map.md) "Places"): only a place with GPS; Plán (`map-plan`) when the event has a plan with `planBounds` and the place lies inside them, the edges included; otherwise Mapa (`map`) when the event has a usable Google embed; otherwise none. A place without GPS (obrok27's `Celý tábor`), a place off the plan of an event that has only a plan, an unknown `placeId`, a programme without a place and an event without Místa (korbo26, miquik26) all keep `Kde` as plain text, and a programme without a `location` has no `Kde` at all. The address is the route's URL with the place twice, `?misto=<id>#misto-<id>` (`/obrok27/mapa/plan?misto=15#misto-15`, or `/<slug>/mapa?misto=<id>#misto-<id>` for a place off the plan): the query is what Místa reads to show the marker and centre the map, the hash scrolls Plán to the marker (`#misto-<id>` is the marker's id) without a script and names nothing on Mapa. `Programs\ShowAction` builds it (`placeHref()`, passed to `Sheet::completed()`): it reads `getPlaces()` only when there is a sheet and `PlaceLinks::possible()`, and a provider that cannot send its places (`ProgramUnavailableException`, `ProgramDataException`) leaves every place as text and adds no notice, since the pins are an extra. The link ink is `action-link` on the sheet's own `surface`, which `ThemingTest::testAccentInkClearsAAOnItsGrounds` holds to AA in both role sets of every event, bold, and the link is at least 44 × 44 px (`TouchTargetTest`, on obrok27's three-letter `Les`). The pin is a full navigation, without JavaScript and, for now, with it: the loader leaves a link with a query to the browser, `data-deep-link` included. Back from Místa lands on the sheet's entry, whose hash opens the sheet again (`:target` without a script, `fromHash()` with one).

**The sheet has an address.** Its entry is the view's path with the open body's id as the hash: `/programy#section-<s>-program-<id>` on Harmonogram, `/programy/prehled#…` on Přehled, `/programy/moje#…` on Moje (`openSheet()` passes `'#' + body.id` to `enterOverlay(hash)`). **The path decides the view, the hash decides the programme**: `deeplink.js`'s `ctx.fromHash()` reads `hashTarget(location.hash)` (`maths.js`, `#section-<s>-program-<id>` only) and opens that sheet on the view the path names — on Moje it parks the list on the programme first (`pendingListTarget`, `enterList()`), on Přehled it scrolls to its row, on Harmonogram it puts the timeline on its page — and with no such hash it closes any open sheet. `openSheet()` never switches the view. `fromHash()` runs from three triggers and from nothing else: the **wiring**, **`screen:shown`** (`ctx.syncFromUrl()`) and, through `sheet.js`, **`popstate`**; nothing listens for `hashchange`. **The landing rule**: the entry under a sheet never carries a programme hash. When a sheet opens on an entry that already names it (a landing on a deep link, a reload, an old hash rewritten), `enterOverlay()` replaces that entry without the hash and pushes the sheet's entry with it; on an overlay entry already up (`history.state.pgOverlay`) it rewrites that entry instead of pushing, so a reload of a sheet's entry (the loader keeps `pgOverlay` on its state) reopens the sheet without a new entry. **Back and Forward**: `sheet.js`'s `popstate` listener, while the root's screen is on show, runs `fromHash()` when the landed entry's hash names a programme of the screen or is an old Moje hash (the sheet opens on that entry, no push; nothing when that sheet is already the open one) and otherwise closes the sheet (`closeSheet(true)`, no history). A same-document hash change fires `popstate` too, so a notification's `client.navigate()` to `/programy#section-…` on a reader already there (the worker's `notificationclick`) opens the sheet as a landing does: the timeline on the programme's page, Moje's target, an old hash rewritten. So Back from a deep-linked sheet closes it on the address without the hash, and the next Back leaves the screen; neither opens it again. **Another screen**: a link inside the sheet (the logged-out `Pro zápis…` link to Profil) pushes the other screen over the sheet's entry, and `screen:hidden` closes the sheet without touching history; Back to the sheet's entry shows the screen, whose `screen:shown` reads the hash and opens the sheet again with the focus in the card. A Program tab tap comes back to the address without a hash (the loader notes only the path), so the sheet stays closed. **The old hashes**: `legacyTarget()` reads `#muj-program` as `{id: null}` and `#muj-program-<id>` as `{id}`; on Harmonogram's path `fromHash()` first replaces the entry with Moje's address (`viewPath('list', screen)` and the query, plus the sheet's hash when the screen has that programme) and shows Moje, then goes on as for the new hash, and the boot does not land on now for either. The closed sheet is hidden by CSS (`visibility: hidden`), which hides it from assistive technology too; neither the server nor the script writes `aria-hidden` on it.

**Without JavaScript the sheet opens on `:target`.** A row's or card's link puts the body's id in the hash; `:root:not(.js) .sheet:has(.sheet-body:target)` takes the open sheet's declarations (visible, the backdrop at its opacity, the card slid up, and the slide's timing in `motion.css`), and `:root:not(.js) .sheet-body:target` shows that one body, as `.is-open` does with a script. The close row, `<a class="sheet-close" href="{{ pageAddress }}#zavrit" data-pg-close>✕ Zavřít</a>`, and the backdrop, the same link with `aria-hidden="true" tabindex="-1"`, go to `#zavrit`, which names no element, so nothing is the target and the sheet closes on the same address. Each `:has()` selector is a rule of its own, never in a list with `.sheet.is-open`: a browser without `:has()` drops the whole rule a selector it cannot parse is in, and the sheet would not open there with JavaScript either (`ThemingTest::testNoHasSelectorSharesItsRule`). With JavaScript the root has `js`, the `:target` rules never match, and `.is-open` alone decides; a landing on `#zavrit` names no programme and opens nothing. The no-JS sheet has accepted limits: the dialog's `aria-labelledby` names the first programme, not the one on show (only the script points it at the open one); after `Zavřít` the focus stays on the close link, now hidden, rather than going back to the row; and each open and close is a hash navigation of its own, so Back from `#zavrit` reopens the sheet that was open before.

## Registration

**Registration** is a form POST — `POST /programy/{id}/prihlasit` (`program-register`) and `/odhlasit` (`program-unregister`) — that the worker sees and that ends in a full navigation, so the worker's purge-on-write keeps every screen consistent: `SameOrigin` (else a 403 page), not paired → 403 with `Pro zápis na programy se přihlas kódem z KissJ.`, then `register`/`unregister()` with the session token, and a toast left in the session: `Zapsáno: <name>` with `RegistrationWriter::toastLine()` (`Pá 21. 5. · 9:00–12:30 · Žlutý les`: the capitalised short weekday, `j. n.`, the `CLOCK` range, the place when there is one; a run past midnight names its start day only), `Zápis zrušen: <name>` with `Místo jsme uvolnili`, a refusal's Czech line from `REFUSALS` (an unknown code `Zápis se nepodařil.` or `Zrušení zápisu se nepodařilo.`), an outage (`ProgramUnavailableException`, the stub's `LocalStateException` among them, or `ProgramDataException`) `Zápis se teď nedaří, zkus to prosím později.` or `Zrušení zápisu se teď nedaří, zkus to prosím později.`, and a `SessionExpiredException` the logout as everywhere. What a repeated write's refusal does to a success toast still waiting is in `RegistrationWriter`'s docblock. Each form carries `<input type="hidden" name="pohled" value="<view>">` with the view the server rendered, and `programs/deeplink.js`'s root `submit` listener overwrites it with the view on show (`ctx.view`) on any `form[data-write]`. The actions read the field (`FormField::text()`) and `RegistrationWriter::write($register, $id, $view)` gives the programme's address on that view: `/programy/prehled#section-<sectionId>-program-<id>` for `overview`, `/programy/moje#…` for `list`, and `/programy#…` for `timeline`, anything else or no field (a page cached before the field). The script sends the form: `shell/write.js`'s `submit` listener on the document (after the root's) disables the button, posts the form with `X-Write: 1`, and the action answers `{"next": "<address>"}` through `WriteResponse` ([http.md](http.md)); without JavaScript it answers a 302 there. The address is usually the sheet's own, which differs from the current one by the hash at most, so the script writes it onto the entry and reloads (`follow()`), keeping the entry's `pgOverlay`: **the write replaces the sheet's entry**, and Back closes the sheet onto the screen under it, a document loaded after the write, never one with the stale `Zapsat program`. Its full document takes the toast (the toast is `.pg`'s first child, keyed `toast`) and reopens the sheet under it, on the view the reader acted from, without JavaScript too. A write whose `fetch` rejects gets the button back and the offline toast; any other answer is sent again as the plain form (http.md says why that is safe); a page restored from the back-forward cache gets its button back on `pageshow`.

## The sheet as a dialog

An open `.sheet` is a real dialog — the screen's only one: everything outside it goes `inert` — the app bar, the tab bar, the skip link, the sibling screens — except the toast, which paints above the sheet (a higher `z-index`, never over the sheet's own close button) and whose `✕` stays in the sheet's Tab ring, and Tab rings inside the card, because a modal a reader can tab straight out of is not one. The trap remembers exactly which elements it marked, so closing clears its own and nothing else, and it releases *before* the focus returns to the opener, since an inert element cannot take focus. Opening the sheet also pushes a history entry (`{pgOverlay: true}` with the sheet's address, replaced rather than stacked when one is already up; see "The sheet has an address" above), so Android's Back closes it instead of leaving the screen with the rest of the app inert, and closing it any other way goes back over that entry once, with `history.scrollRestoration` held at `manual` while an overlay entry is up so the browser does not restore the scroll it saved; an open asked for while a close's `history.back()` is still in flight waits for it. A day chip opens nothing and pushes no entry. Chrome's history-manipulation intervention may let Back skip an entry pushed without a user gesture (the sheet a deep link opens on landing), so the entry is no guarantee; the backstop is that `popstate` on any entry that names no programme and `screen:hidden` on the Program screen close the sheet and release the trap, which can leave an orphan entry costing one idle Back — accepted. Without JavaScript none of this runs: the sheet is the `:target` one (see "The sheet" above), opened and closed by links, each a hash navigation and so one entry, with no trap, no `inert` and no entry of its own. The sheet's elements are looked up on every use rather than held from the first render, and every child of `.pg` carries a `data-key` (`toast`, `notice`, `pager-<kind>`, `tabs`, `sheet`) or an id (the three views), because the morph matches unkeyed siblings by position and once turned a reference to the sheet into the old day panel. There is no favourite, capacity or attendee count. `ScheduleBuilder` does all the grouping in PHP and hands Twig a finished view model; every page and every sheet is rendered into the DOM so the deep link can open a sheet on any of them.

The view model is readonly objects under `src/Module/Programs/View/`, built in two steps that stay two steps. `ScheduleBuilder::buildViewModel()` is pure and returns a `View\Schedule`: the timeline's `TimelinePage`s with their `RulerTick`s and `StageRow`s of `Card`s, the two lists' `Day`s of `ListItem`s, and one `Sheet` per programme, every sheet with no messages and a null footer. `ShowAction` then, only when there is a sheet and in this order, reads the registration window, the messages and the places and replaces each sheet with `Sheet::completed()`, a copy carrying its `SheetMessage`s, its `SheetFooter` and its pin's address (`placeHref`), and builds the `View\ProgramsPage` the template is rendered with. `SheetFooter::$state` is a string, because the template compares it with one, and `Card::$offset`, `Card::$span` and `RulerTick::$offset` are floats that Twig prints as PHP does (`2.0` as `2`); nothing formats them.

## The script

`www/js/programs/index.js` is the entry. Its `init(root)` wires one `[data-pg-root]` once and marks it `data-pg-ready="1"`: a server-rendered screen when the document is ready, so it keeps working even if the loader never runs, and a screen the loader inserts on `screen:shown`, which the loader dispatches only once the section is visible. No `window` function is exposed.

A module is evaluated once per page, but the state belongs to each root, so `init()` builds a **`ctx`** per root and passes it to every part. It starts with `root`, `slug`, `screen`, `cssPx()`, `stageWidth`, `view`, `pageKey`, `hourWidth` and `pendingListTarget`; each part's `setup(ctx)` then attaches the functions the others call, such as `showView`, `selectView`, `syncFromUrl`, `showPageByKey`, `scrollToDay`, `setZoom`, `updateNow`, `openSheet` and `closeSheet`, and keeps its own state private. Two roots in one page therefore share nothing (`tests/js/programs.test.js` checks this).

| File | What it does |
|---|---|
| `chips.js` | marks the current day chip and scrolls the strip to it |
| `timeline.js` | the Harmonogram's pages |
| `daylist.js` | Přehled and Moje as day lists: the current day, scrolling to a day or an item |
| `views.js` | the three views and their tab strip, the view's address, its `popstate` listener |
| `zoom.js` | the hour width: buttons, pinch, wheel, the stored `pgZoom:<slug>`, the ruler's step |
| `nowline.js` | the now-line, Moje's now marks, and the landing on now |
| `deeplink.js` | `fromHash()`: the sheet's `#section-…` address and the old `#muj-program` hashes; the write form's `pohled` and its button |
| `sheet.js` | the programme sheet as a dialog, its history entry and address, its `popstate` listener, `sheet:closed` |
| `maths.js` | the pure arithmetic and formatting, with no DOM: tested in `tests/js/programs.test.js` |

**The setup order** is the order the listeners are registered in: chips, timeline, daylist (these three register none), views (its `popstate` listener), then zoom, nowline, the root's click listener, the document's keydown listener, deeplink, sheet, the `screen:morphed` listener that runs `afterMorph()`, and last, once the boot below has run, the root's `screen:shown` listener. **The boot order** follows it: restore the zoom, show the timeline's active page, then the page a `?den=` names when there is one (`denPage()`), put each list's strip on its first day, show the current view, place now, open on now unless the hash is a deep link or an old Moje hash (`hashTarget()`, `legacyTarget()`) or a `?den=` named a page, and finally open what the hash names (`fromHash()`). Once wired, the root's `screen:shown` listener runs `ctx.syncFromUrl()` on every later show of its screen, which ends in `fromHash()`: a tab tap returns to the address the screen was left on, Back from another screen to a sheet's entry opens that sheet, and the loader's deep link from Domů shows an already wired Program screen with the hash pushed and dispatches no `hashchange` ([shell-and-loader.md](shell-and-loader.md)); `sheet.js`'s `popstate` listener covers Back and Forward on the screen itself. Nothing listens for `hashchange`. It is registered while the root is being wired, so the `screen:shown` that wires it does not reach it and the boot reads the address once.
