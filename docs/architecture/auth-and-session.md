# Auth and session

This document covers logging in through kissj's device pairing, logging out, and the server-side session that holds the identity.

## Device pairing

**Login is kissj's device pairing** (kissj's API contract 3.0, "Device pairing"); there is no TIE code anywhere in eventApp and no external SSO. `Auth\Identity` is a paired participant: kissj's `participantId`, the `nickname` (or null) and the device `sessionToken`, which lives only in the server-side session and never reaches a template or the reader's JavaScript; `displayName()` is the nickname or `Účastník`, `initials()` the first letters of the first and last word, the first two letters of a single word, or null (the generic person icon). `Auth\Authenticator` stores it under the session key `identity` (rotating the session ID first) and drops it on logout (cleared, then rotated). The flow: logged out, Profil's `Přihlásit kódem z KissJ` is `POST /profil/propojit` (`pairing-start`), which asks `Http\SameOrigin::allows()` (else a 403 page), redirects a reader already paired, counts the start in `Auth\PairingThrottle` (`LIMIT` 300 per `(event, throttleKey)` in 10 minutes, every start counts: one phone cannot burn kissj's cap on pending pairings, while a camp behind one NAT still logs in) and calls `startPairing(sha256(Session::id()))` — one browser, one pending pairing, and a second start replaces it at kissj. The pairing is kept in the session under `pairing` (`deviceCode`, `userCode`, `verificationUrl`, `expiresAt`), and Profil shows the code (`483 291`), `Zadej kód v KissJ, nebo`, an `Otevřít KissJ ↗` link to the verification URL in a new tab, `Čekám na potvrzení v KissJ…` (`PairingState::WAITING`), `Zkontrolovat přihlášení` and `Začít znovu`. `www/js/profile/pairing.js` polls `GET /profil/propojit/stav` (`pairing-poll`) every 5 s while the code (`[data-pairing-poll]`) is on a visible screen. It starts on `DOMContentLoaded` (or at once when the document has loaded) and on `screen:shown`, stops on `screen:hidden` and `pagehide`, and resumes with the same code on a `pageshow` from the back/forward cache. One request is in flight at a time, and a failed request or one that is not JSON means ask again; the answer is always a 200 `{"status": …}` (with `next` on `approved`, below) with `Cache-Control: no-store`, and a provider failure (or an approval whose participant read fails) answers `pending`, so the page keeps asking and kissj's re-issued approval is collected later. `approved` stores the identity (the pairing and any old outcome dropped before the ID rotates, so a late poll under the old ID cannot collect a re-issued approval) and leaves the `Jsi přihlášen` toast; `approved` and `expired` make the page navigate itself with `location.replace()` — the one way a login reloads the document — so the next page takes the place of the Profil that showed the code, and Back never shows that one again: `approved` lands on the answer's `next` (below) through `landingUrl()`, which resolves it against the event with `shell/write.js`'s `nextOf()` and falls back to `profil` when it is missing or leaves the origin; `expired` loads Profil, with the line that says why not. **Without JavaScript the reader checks instead of the poll**: `Zkontrolovat přihlášení` is a plain form (no `data-write`; `:root.js .pairing-check { display: none; }` hides it where the script polls) posting `POST /profil/kontrola` (`pairing-check`, `CheckPairingAction`). It asks `SameOrigin` (else the 403 page `Přihlášení se nepodařilo. Načti stránku a zkus to znovu.` with `Zpět na profil`, as the start), then runs the same check as the poll, `Profile\PairingCheck::run()`, and answers in one of three ways, each a 302 (through `WriteResponse`, like every write): approved, to the landing (`<base>/<next>`, below) with the `Jsi přihlášen` toast; still waiting (`pending` or `slowDown`, a provider failure included), to `<base>/profil`, and `PairingState::checked()` stores the time under `pairingChecked` and for 60 s the status line under the code reads `Zatím nepotvrzeno, zkus to za chvilku.` (`PairingState::NOT_YET`, from `waitingLine()`) instead of the waiting one, a line that reading Profil does not consume (the warm-up and the worker read it too) and that a start, an expiry, an approval or a logout clears; expired, to `<base>/profil` with the expired line. A start, poll or session that went wrong leaves an outcome that a logged-out Profil shows as a `.notice`; `Auth\PairingState`'s docblock lists the codes, their lines and how long they last. The four routes are `Module\Profile`'s `StartPairingAction`, `PollPairingAction`, `CheckPairingAction` and `RevokeAction`, beside Profil's own `ShowAction`; the poll and the check share `PairingCheck`. **The start, the logout and the approval each replace their entry**: every `pairing-start` form (`Přihlásit kódem z KissJ`, `Začít znovu`) and the `pairing-revoke` form carry `data-write`, so `shell/write.js` sends them with `X-Write: 1` and the action answers `{"next": "<base>/profil"}` through `Http\WriteResponse` instead of its 302 ([http.md](http.md)), which the script lands on with `location.replace()`; without JavaScript they post as plain forms and get the 302. From Domů, Profil, start, approval: Back goes to Domů.

**Where a login lands.** A programme's sheet sends a logged-out reader to `profil?program=<id>` (its `unpaired` footer link, [programs.md](programs.md)). Profil puts that id into the start form as `<input type="hidden" name="program">` (digits only, `PairingState::programId()`: a positive decimal of at most ten digits, not checked against the provider), and the pending Profil's `Začít znovu` form carries the pairing's own target on (`PairingState::returnProgram()`), so a restart keeps it. The target belongs to the address that named it: the loader revalidates a screen visited for another query than the one its markup was served for, so Profil left and reached again by its tab is morphed to the plain start form without the field, and Back to the `profil?program=<id>` entry morphs it back in ([shell-and-loader.md](shell-and-loader.md)). Until that morph lands the old copy is on show, and a fast tap can still send the old target; that is accepted, since the start validates `program` again and the only effect is a landing on that programme's sheet. The start reads the field after the throttle let it through, and only when it is sent: `StartPairingAction::returnTo()` looks the id up in `getPrograms()` (on an event with `programs`), and only an id the provider lists is kept, as `pairingReturn` `{program, section}` beside the pairing (`PairingState::begin()`); a malformed or unknown id, or a provider failure during that read, drops the target and the pairing still starts. `pairingReturn` goes with every end of the pairing: a failure, the approval, the logout and a start without one. On the approval `PairingCheck::landing()` picks `next`, relative to the event, read before `approved()` drops the target: on an event without Program `profil` (Program would be a 404); else the sheet on Harmonogram, `programy#section-<s>-program-<id>`; else `programy/moje` for a reader with programmes; else `programy/prehled`. The poll answers `{"status":"approved","next":"programy/moje"}` (`PairingAnswer::toArray()`, `JSON_UNESCAPED_SLASHES`; no other status carries `next`), and the check button's 302 goes to `<base>/<next>`. The `Jsi přihlášen` toast is taken by the first full document after the approval, so it shows on the page the reader lands on, after the poll and after the check button alike: Program (Profil on an event without Program). A programme that leaves kissj between the start and the approval leaves a landing that names no sheet, and Harmonogram opens without one.

## Logout and a session that is gone

**Logout exists**: paired, Profil ends with `Odhlásit se z aplikace`, a two-tap button (`data-confirm="Opravdu odhlásit?"`; without JavaScript nothing asks first and it submits on the first tap) posting `POST /profil/odpojit` (`pairing-revoke`): what it does, in order, is in `Profile\RevokeAction`'s docblock. Any screen whose personal read (`Auth\CurrentParticipant::read()`) hits `SessionExpiredException` calls `Authenticator::sessionGone()`: logged out, outcome `gone`, and a pending login toast dropped; Domů and Program render that page logged out with a toast of their own saying why (`Toasts::gone()`). A logged-out Profil shows `Nejsi přihlášen`, the explanation, the start button; paired, the avatar (initials or the person icon) with the display name; both then show the install card, the notifications card ([push.md](push.md)) and, for an event with a dark set, the mode control. The Profil tab shows who is paired through the `auth_identity()` Twig function rather than a global (`participantId`, `displayName`, `initials`; never the token), because a handler can log the reader out during the same request that renders the tab bar: the tab's icon is the initials in a circle (`.tab-avatar`, hidden from assistive tech) or the generic person icon, and the tab reads `Profil`.

## Sessions

Sessions are `App\Session`, one per event, and nothing about them depends on the host's ini, which on the FTP host is unknown. `Session`'s docblock holds the details: the store and its path chosen as a pair (`Session::storage()`), the settings made before every start, the `eventapp` cookie and its flags, the reads with `read_and_close` (`SessionLockTest`), every write through `transact()`, and the 30-day cookie that slides (`Session::LIFETIME`, `refreshCookie()`). `session.auto_start` is the one setting it cannot make at run time, so it must be off on the host.

## Per-event values and ID rotation

There is one session cookie per host, so `Session` namespaces its values per event slug: pairing in one event shows nothing in another, and a logout is local to its event. The values: `identity`, `pairing`, `pairingOutcome`, `pairingChecked`, `pairingReturn`, `toast`, and the admin page's `admin`, `csrf`, nonces and `notifyResult`. Login and logout rotate the session ID with `session_regenerate_id(false)` — rotated before the identity is stored, cleared before the rotation on logout — so the old ID is left holding the logged-out session rather than destroyed: the worker's install and refill bursts send up to ~26 requests with the cookie of the moment, and under strict mode a destroyed ID would answer one of them with a new empty session and a `Set-Cookie` that logs the reader out (`SessionRotationTest` checks it against a real server).
