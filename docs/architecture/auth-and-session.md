# Auth and session

This document covers logging in through kissj's device pairing, logging out, and the server-side session that holds the identity.

## Device pairing

**Login is kissj's device pairing** (kissj's API contract 3.0, "Device pairing"); there is no TIE code anywhere in eventApp and no external SSO. `Auth\Identity` is a paired participant: kissj's `participantId`, the `nickname` (or null) and the device `sessionToken`, which lives only in the server-side session and never reaches a template or the reader's JavaScript; `displayName()` is the nickname or `Účastník`, `initials()` the first letters of the first and last word, the first two letters of a single word, or null (the generic person icon). `Auth\Authenticator` stores it under the session key `identity` (rotating the session ID first) and drops it on logout (cleared, then rotated). The flow: logged out, Profil's `Přihlásit kódem z KissJ` is `POST /profil/propojit` (`pairing-start`), which asks `Http\SameOrigin::allows()` (else a 403 page), redirects a reader already paired, counts the start in `Auth\PairingThrottle` (`LIMIT` 300 per `(event, throttleKey)` in 10 minutes, every start counts: one phone cannot burn kissj's cap on pending pairings, while a camp behind one NAT still logs in) and calls `startPairing(sha256(Session::id()))` — one browser, one pending pairing, and a second start replaces it at kissj. The pairing is kept in the session under `pairing` (`deviceCode`, `userCode`, `verificationUrl`, `expiresAt`), and Profil shows the code (`483 291`), `Zadej kód v KissJ, nebo`, an `Otevřít KissJ ↗` link to the verification URL in a new tab, `Čekám na potvrzení v KissJ…` and `Začít znovu`. `www/js/profile/pairing.js` polls `GET /profil/propojit/stav` (`pairing-poll`) every 5 s while the code (`[data-pairing-poll]`) is on a visible screen. It starts on `DOMContentLoaded` (or at once when the document has loaded) and on `screen:shown`, stops on `screen:hidden` and `pagehide`, and resumes with the same code on a `pageshow` from the back/forward cache. One request is in flight at a time, and a failed request or one that is not JSON means ask again; the answer is always a 200 `{"status": …}` with `Cache-Control: no-store`, and a provider failure (or an approval whose participant read fails) answers `pending`, so the page keeps asking and kissj's re-issued approval is collected later. `approved` stores the identity (the pairing and any old outcome dropped before the ID rotates, so a late poll under the old ID cannot collect a re-issued approval) and leaves the `Jsi přihlášen` toast; `approved` and `expired` make the page reload Profil itself — the one way a login reloads the document. A start, poll or session that went wrong leaves an outcome that a logged-out Profil shows as a `.notice`; `Auth\PairingState`'s docblock lists the codes, their lines and how long they last. The three routes are `Module\Profile`'s `StartPairingAction`, `PollPairingAction` and `RevokeAction`, beside Profil's own `ShowAction`.

## Logout and a session that is gone

**Logout exists**: paired, Profil ends with `Odhlásit se z aplikace`, a two-tap button (`data-confirm="Opravdu odhlásit?"`) posting `POST /profil/odpojit` (`pairing-revoke`): what it does, in order, is in `Profile\RevokeAction`'s docblock. Any screen whose personal read (`Auth\CurrentParticipant::read()`) hits `SessionExpiredException` calls `Authenticator::sessionGone()`: logged out, outcome `gone`, and a pending login toast dropped; Domů and Program render that page logged out with a toast of their own saying why (`Toasts::gone()`). A logged-out Profil shows `Nejsi přihlášen`, the explanation, the start button; paired, the avatar (initials or the person icon) with the display name; both then show the install card and, for an event with a dark set, the mode control. The app bar shows who is paired through the `auth_identity()` Twig function rather than a global (`participantId`, `displayName`, `initials`; never the token), because a handler can log the reader out during the same request that renders the bar: the profile link is the initials in a circle (`.appbar-avatar`, hidden from assistive tech; the link reads `Profil`) or the generic person icon.

## Sessions

Sessions are `App\Session`, one per event, and nothing about them depends on the host's ini, which on the FTP host is unknown. `Session`'s docblock holds the details: the store and its path chosen as a pair (`Session::storage()`), the settings made before every start, the `eventapp` cookie and its flags, the reads with `read_and_close` (`SessionLockTest`), every write through `transact()`, and the 30-day cookie that slides (`Session::LIFETIME`, `refreshCookie()`). `session.auto_start` is the one setting it cannot make at run time, so it must be off on the host.

## Per-event values and ID rotation

There is one session cookie per host, so `Session` namespaces its values per event slug: pairing in one event shows nothing in another, and a logout is local to its event. The values: `identity`, `pairing`, `pairingOutcome`, `toast`, and the admin page's `admin`, `csrf`, nonces and `notifyResult`. Login and logout rotate the session ID with `session_regenerate_id(false)` — rotated before the identity is stored, cleared before the rotation on logout — so the old ID is left holding the logged-out session rather than destroyed: the worker's install and refill bursts send up to ~26 requests with the cookie of the moment, and under strict mode a destroyed ID would answer one of them with a new empty session and a `Set-Cookie` that logs the reader out (`SessionRotationTest` checks it against a real server).
