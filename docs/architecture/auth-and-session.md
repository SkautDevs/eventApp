# Auth and session

This document covers logging in through kissj's device pairing, logging out, and the server-side session that holds the identity.

## Device pairing

**Login is kissj's device pairing** (`docs/kissj-contract.md`, "Device pairing"); there is no TIE code anywhere in eventApp and no external SSO. `Auth\Identity` is a paired participant: kissj's `participantId`, the `nickname` (or null) and the device `sessionToken`, which lives only in the server-side session and never reaches a template or the reader's JavaScript; `displayName()` is the nickname or `Účastník`, `initials()` the first letters of the first and last word, the first two letters of a single word, or null (the generic person icon). `Auth\Authenticator` stores it under the session key `identity` (rotating the session ID first) and drops it on logout (cleared, then rotated). The flow: logged out, Profil's `Přihlásit kódem z KissJ` is `POST /profil/propojit` (`pairing-start`), which asks `Http\SameOrigin::allows()` (else a 403 page), redirects a reader already paired, counts the start in `Auth\PairingThrottle` (`LIMIT` 300 per `(event, throttleKey)` in 10 minutes, every start counts: one phone cannot burn kissj's cap on pending pairings, while a camp behind one NAT still logs in) and calls `startPairing(sha256(Session::id()))` — one browser, one pending pairing, and a second start replaces it at kissj. The pairing is kept in the session under `pairing` (`deviceCode`, `userCode`, `verificationUrl`, `expiresAt`), and Profil shows the code (`483 291`), `Zadej kód v KissJ, nebo`, an `Otevřít KissJ ↗` link to the verification URL in a new tab, `Čekám na potvrzení v KissJ…` and `Začít znovu`. `www/profile.js` polls `GET /profil/propojit/stav` (`pairing-poll`) every 5 s while the code is on a visible screen, stops when the screen is left and resumes with the same code; the answer is always a 200 `{"status": …}` with `Cache-Control: no-store`, and a provider failure (or an approval whose participant read fails) answers `pending`, so the page keeps asking and kissj's re-issued approval is collected later. `approved` stores the identity (the pairing and any old outcome dropped before the ID rotates, so a late poll under the old ID cannot collect a re-issued approval) and leaves the `Jsi přihlášen` toast; `approved` and `expired` make the page reload Profil itself — the one way a login reloads the document. A start, poll or session that went wrong leaves an outcome that a logged-out Profil shows as a `.notice`; `Auth\PairingState`'s docblock lists the codes, their lines and how long they last.

## Logout and a session that is gone

**Logout exists**: paired, Profil ends with `Odhlásit se z aplikace`, a two-tap button (`data-confirm="Opravdu odhlásit?"`) posting `POST /profil/odpojit` (`pairing-revoke`): `SameOrigin` (else a 403 page), `revokeSession()` at kissj best effort (a `SessionExpiredException` counts as done, anything else is collected), the identity dropped, and the `Odhlášeno` / `Obsah teď můžeš jen prohlížet` toast — only when somebody was logged in. Any screen whose personal read hits `SessionExpiredException` calls `Authenticator::sessionGone()`: logged out, outcome `gone`, and a pending login toast dropped; Domů and Program render that page logged out with a toast of their own saying why (`Toasts::gone()`). A logged-out Profil shows `Nejsi přihlášen`, the explanation, the start button; paired, the avatar (initials or the person icon) with the display name; both then show the install card and, for an event with a dark set, the mode control. The app bar shows who is paired through the `auth_identity()` Twig function rather than a global (`participantId`, `displayName`, `initials`; never the token), because a handler can log the reader out during the same request that renders the bar: the profile link is the initials in a circle (`.appbar-avatar`, hidden from assistive tech; the link reads `Profil`) or the generic person icon.

## Sessions

Sessions are `App\Session`, built per event as `new Session($slug, $environment->sessionPath($root), appRoot: $root, clock: $clock)`, and nothing about them depends on the host's ini (the FTP host's handler and defaults are unknown): before every start it sets the files handler and its path **as a pair** — `var/sessions` (or `SESSION_PATH`; created 0700, refused as a symlink, and outside the app root also refused unless owned by the process user with no group/other bits), else a private `eventapp-sessions-<8 hex of the app root's sha256>` under the system temp dir under the same ownership rules, else the host's own handler *and* path untouched (`Session::storage()`; a fallback is reported through `Collector` once per process) — plus a 30-day `gc_maxlifetime` with its own GC at 1/1000, strict mode, cookie-only IDs, `lazy_write`, `cache_limiter` `''` (the screen middleware states the pages' cache policy instead) and a host-only cookie `eventapp` that is `HttpOnly`, `SameSite=Lax` and `Secure` on HTTPS. `session.auto_start` is the one thing it cannot set at run time and must be off on the host. Reads use `read_and_close`, so a slow kissj call never holds the session lock against the reader's next request (`SessionLockTest`), and a request without the cookie — or, on the app's own files store, with a cookie whose session file does not exist — reads nothing and starts nothing (no file, no `Set-Cookie`); `Session::id()` is the exception, starting a session when there is none, because the pairing's device id is its hash (under CLI a random ID kept in `$_SESSION` stands in). Every write goes through `transact()`, which reopens the session, applies the change to freshly read values under the handler's lock and closes it again — also what makes the admin nonce's check-and-consume and the toast's take atomic — and a reopen resumes the stored ID without sending the cookie again. A cookie the store does not know (collected, invented) still gets a new cookie and an empty file under strict mode — accepted. The cookie lasts `Session::LIFETIME` (30 days) and slides: `refreshCookie()`, called by `Http\SessionCookieMiddleware` on every full logged-in page, re-sends it with a fresh expiry and touches the session file once a day (not on the host's store), because `read_and_close` never updates it and the GC would otherwise count from the last write.

## Per-event values and ID rotation

There is one session cookie per host, so `Session` namespaces its values per event slug: pairing in one event shows nothing in another, and a logout is local to its event. The values: `identity`, `pairing`, `pairingOutcome`, `toast`, and the admin page's `admin`, `csrf`, nonces and `notifyResult`. Login and logout rotate the session ID with `session_regenerate_id(false)` — rotated before the identity is stored, cleared before the rotation on logout — so the old ID is left holding the logged-out session rather than destroyed: the worker's install and refill bursts send up to ~26 requests with the cookie of the moment, and under strict mode a destroyed ID would answer one of them with a new empty session and a `Set-Cookie` that logs the reader out (`SessionRotationTest` checks it against a real server).
