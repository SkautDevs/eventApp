# Map

This document covers Místa: the Google map, the self-hosted site plan, how the two share one screen, the places shown on them, and the note that stands in for the map offline.

## Místa

`MapModule` (`/mapa`; the tab, the app bar title, the document title and the screen's label all read **Místa**, while the view pill inside keeps `Mapa` and `Plán`) reads `map.embedUrl` (a Google My Maps embed; a `REPLACE-ME` placeholder counts as none; obrok27's is the 2027 map, `…/maps/d/embed?mid=1KLPkQqPYxomrNmxTc0FfPZ44P5AxLRg`, which renders only if it is shared publicly in My Maps), `map.image` (a path under `www/`, the handbook's own site plan, self-hosted so it works offline and shown as an `<img>`, so an SVG is drawn and never run) and the optional `map.imageAlt` (default `Plán areálu`), and `map.twig` has three branches: the embed alone is `<div data-map-root data-map-event="<slug>" data-view="google">` around the markup it always had (`<div class="map" data-map>` with its iframe, then the offline note), a root so that `map/index.js` wires it too, which changes no layout because `div.map` sets its own height; the plan alone is a `.mapview[data-map-root]` with one plan pane and no switcher; both make `<div class="mapview" data-map-root data-map-event="<slug>" data-view="<view>" data-morph-keep="data-view">` holding two `role="tabpanel"` panes (`#map-view-google`, `#map-view-plan`) and the Program screen's floating pill — the same `.tabs-wrap`/`.tabs`/`.tabs-indicator`/`.tabs-tab` markup and CSS, `aria-label="Zobrazení mapy"`, `Mapa` and `Plán`, `--tabs-height` being declared on `:root` already. A hidden pane is `display: none`, never detached, so Google's iframe keeps running behind the plan. The behaviour is `www/js/map/`, whose entry the layout loads for an event with the `map` feature. `map/index.js` wires each `[data-map-root]` once (marked `data-map-ready="1"`): the document's own screen when the module evaluates, and a screen the loader inserts on `screen:shown`. `map/views.js` (`setupViews(root, plan, onView)`, `onView(view)` called at the end of every `setView()`, a re-assert of the same view included) makes the view the address, as on the Program screen: `mapViewFromPath()` reads `google` from the screen's own path (`data-screen`) and `plan` from that path plus `/plan`, and `mapViewPath()` is its inverse. A pill tap, an arrow key on the pills or the offline note's `Zobrazit plán` button (`select()`) shows the view and pushes `{screen, mapView}` with its address and the query on show (`mapViewPath(view) + location.search`: switching views keeps `?misto=`), so each choice is one Back; the view already on show pushes nothing, which is decided on the path alone (`location.pathname !== mapViewPath(view)`), so a query never makes a duplicate entry. The pills are links (below); the root's click handler calls `preventDefault()` on a plain primary click of one, so the link is not followed and Google's iframe is never reloaded, and leaves a click with a modifier key (a new tab) to the browser. Space presses a pill link as it pressed the button it was (`click()`, once for a held key), and the arrow keys walk the pills as before. The wiring and every `screen:shown` read the view from `location.pathname` (`openingView(online, pathView)`: Plán whenever `navigator.onLine` is false, since offline Google's map is a blank box, else the address's view), never from the markup's `data-view`, because the worker stores both addresses' pages under the screen's key and the copy may be the other view's. Offline on the bare `/mapa` the entry is replaced (`history.replaceState(history.state, '', '<screen>/plan' + location.search)`, the query kept), so the address says Plán and no step is added. A `popstate` while the screen is visible shows the view of the new address and pushes nothing. The offline replace runs only on wiring and on show, not on `popstate`: Back to the bare `/mapa` while offline shows the Google pane with the offline note, whose `Zobrazit plán` button switches to the plan. The view is no longer stored: `sessionStorage['mapView:<slug>']` is never read or written. The plan's zoom stays in `sessionStorage['planZoom:<slug>']` (written after a button step and once when a pinch ends, never on each `pointermove`). `setView()` writes each pill's `aria-selected`, the roving `tabindex` and `aria-current="page"` on the shown one (removed from the other). The morph keeps the pills' `aria-selected` and `aria-current` (`data-morph-keep="aria-selected aria-current"`) and never touches the `tabindex`, which the server does not write; the script still re-asserts the view on `screen:morphed`, since a pill the morph replaced is a new node with the server's state. A Místa with one pane has no pills and no addresses to walk: it keeps the view its markup states. `map/plan.js` (`setupPlan()`) zooms the plan. It zooms by the **width** of its canvas (`[data-plan-canvas]`'s `style.width` at 100–600 %, steps of ×1.4, the first width set without the scroll maths; the image is the canvas's full width, so the markers, placed in % of the canvas, stay on the same point of the drawing at every scale), never a transform, inside a `.plan` box that scrolls both ways with the browser's own panning (`touch-action: pan-x pan-y`); the −/+ pair (`.plan-zoom-btn`, 44 × 44, in `ThemingTest`'s px allowlist beside `.pager-zoom-btn`) anchors on the box's centre and a two-finger pinch on the midpoint between the fingers, each recomputing `scrollLeft`/`scrollTop` so that point stays put, and a button disables at its end of the range. Only the script zooms, so without JavaScript the pair is hidden (`:root:not(.js) .plan-zoom { display: none; }`, in `map.css`) and the plan sits at its box's width, which still scrolls. obrok19 carries a stand-in plan (`www/events/obrok19/plan-example.png`, the CEJ 2022 site map, `Ukázkový plán areálu`) for the reference event and the browser tests; obrok27's is `plan-josefov.png` (`Plán areálu pevnosti Josefov`), drawn in the CEJ plan's style from the participant-facing part of its My Maps layer (north up, portrait); navigamus27's is `plan-navigamus-n27.png` (`Plán areálu Navigamus`), drawn the same way from its own layer but framed in the 2027 identity (Seatren title, Luciao labels, red boundary, N27 badge) (`…/maps/d/embed?mid=10NCIWeMWKOuIGCR9SmckCIazhgMZx5Y`, north up, landscape).

**Two addresses, one screen.** `GET /mapa` (name `map`, argument `view=google`) and `GET /mapa/plan` (`map-plan`, `view=plan`, `screen=/mapa`) are both `Map\ShowAction`. `Http\ScreenAliasMiddleware` renders the plan's address as the one Místa screen (`data-screen="/<slug>/mapa"` on both), and the tab declares it as `data-screen-aliases`. The server paints the view the address names: `MapPage::$view` is `.mapview`'s `data-view`, and its pill carries `aria-selected="true"` and `aria-current="page"`, the other `aria-selected="false"`. The pills are links underneath, `<a class="tabs-tab" role="tab" id="map-tab-google" href="{{ url_for('map') }}" …>` and `<a … id="map-tab-plan" href="{{ url_for('map-plan') }}" …>`, with no `tabindex` (every pill is reachable without a script; `ui/tabs.js`'s roving tabindex is put on at wiring). Without JavaScript a pill is a full page load of its address, painted on its view; with it, `map/views.js` intercepts the click as above. The pills' `:visited` ink is `shell.css`'s `.tabs-tab:visited`, shared with the Program pills. The offline note's `Zobrazit plán` stays a `<button>`: only a script ever shows the note. An event with one pane shows it on either address: with only the plan `view` is `plan` (that branch writes `data-view="plan"` itself), with only the embed it is `google`, and `/mapa/plan` then renders the embed's markup.

## Places

An event's places come from the programme provider (`getPlaces()`, [program-provider.md](program-provider.md)); only a place with GPS can be shown. `map.planBounds` puts it on the plan: the WGS 84 degrees of the plan image's four edges, `['north' => …, 'south' => …, 'west' => …, 'east' => …]` (`App\Event\PlanBounds`; the image is drawn north up without rotation, so a place's share of the span between the edges is its share of the image). obrok27's and navigamus27's are extrapolated from their plans' generators (`docs/<x>_plan/draw.py`, the inverse of its `px()` at the image's corners), demo-grade until the real layers are final; a config with invalid bounds or with bounds and no `map.image` refuses to boot ([bootstrap-and-config.md](bootstrap-and-config.md)).

`Map\ShowAction` reads the places only for an event with the `programs` feature, since only Program links to a place, and only when the event has a plan with bounds or Google's map: an event without `programs` makes no provider call on Místa. A provider that fails (`ProgramUnavailableException`, `ProgramDataException`) leaves Místa as it was before places, with no marker and no places list. Because Místa now reads the provider, its section carries the provider's freshness like Program's (`data-fetched-at`, and `data-stale` while a stale copy is served during an outage), so the network banner can report stale data on Místa too: the markers are programme data.

**Markers.** The plan's image sits in `<div class="plan-canvas" data-plan-canvas>`, with one `<span class="plan-marker" id="misto-<id>" data-key="place-<id>" data-place="<id>" style="left: <x>%; top: <y>%" hidden data-morph-keep="hidden">` per place with GPS inside the bounds (edges included), in the provider's order, holding `<span class="plan-marker-label">` with the place's name. `x` is `(lng − west) / (east − west) × 100` and `y` is `(north − lat) / (north − south) × 100`, two decimals. Every marker is hidden but the one the address names. Its `hidden` is the client's once the script runs (`data-morph-keep="hidden"`): the server's default must not re-hide a marker `map/place.js` showed. It is a defensive keep: the loader revalidates a screen for the query of the visit and drops answers for another one ([shell-and-loader.md](shell-and-loader.md) "A visit for another query"), so an answer rendered without `misto` never reaches a Místa whose address carries one. A marker is filled with `action` and ringed in `on-action`, which tells it apart on a drawing whose colours are anything; its label is on `structure` under `on-structure` with the `edge` hairline, like the zoom pair. `scroll-margin: 40vh 40vw` lands the no-JS `#misto-<id>` jump with the marker away from the box's edge.

**`?misto=<id>`** names a place: a string of one to nine digits without a leading zero (`^[1-9][0-9]{0,8}$`) that is a known place with GPS. Anything else (`abc`, `misto[]=1`, `007`, a longer number, a place without GPS, an unknown id) is ignored: every marker hidden, the plain embed, pills without a query. A valid one:

- shows its marker, when the place lies on the plan;
- centres Google's map on it: the iframe's `src` is `Map\Embed::centred()`, the embed plus `ll=<lat>,<lng>&z=18` (six decimals, after `&` or `?`), while `data-embed` keeps the plain embed;
- stays on both pills: the Mapa pill is `/mapa?misto=<id>` and the Plán pill `/mapa/plan?misto=<id>#misto-<id>`, so without JavaScript Plán scrolls to the marker.

**The places list.** With Google's map, `div.map` also holds `<div data-map-places hidden>` after the iframe: one `<span data-key="place-<id>" data-place="<id>" data-lat="…" data-lng="…">` per place with GPS (six decimals), on the plan or off it, so a script can centre the embed on a place an embed-only event has no marker for. The offline note stays `div.map`'s next sibling.

**Where a pin leads.** `Map\PlaceLinks::route()` decides it for a place: `map-plan` when the event has a plan with bounds and the place lies on it, else `map` when the event has Google's map (`EventMap::usableEmbedUrl()`: none while unset, empty or the `REPLACE-ME` placeholder), else none, since a plan-only event cannot show a place off its plan; a place without GPS has none. `possible()` says whether any place could have one. The pin is the `Kde` link in a programme's sheet ([programs.md](programs.md) "The sheet").

**With JavaScript.** The pin is a `data-deep-link`, so the loader keeps it in the app: it pushes `/mapa/plan?misto=<id>#misto-<id>` and shows Místa for that query, fetching it when it is not stacked yet (`path + search`) or showing the stacked copy, rendered for another address, and revalidating it for the query ([shell-and-loader.md](shell-and-loader.md) "The loader"). Either way the screen on show may have been drawn for another address (a stacked screen, or the stored page the worker answers with offline), so `map/place.js` puts the address's place on show itself. `setupPlace(root, plan)` returns `{sync(), listen()}`; `map/index.js` runs `setupPlan()`, `setupPlace()`, `setupViews(root, plan, () => place.sync())` and then `place.listen()`, so the place's `popstate` listener comes after the views' and the views have switched before it runs. `sync()` acts only on an address of its own Místa (`mapViewFromPath(location.pathname, screen) !== null`): a `popstate` that leaves Místa runs while the screen is still on show (the swap happens inside a view transition), and must neither hide the marker nor reset the iframe. On such an address it reads the place (`placeFromSearch()`: `misto` matching `^[1-9][0-9]{0,8}$`, else none) and:

- shows that place's marker and hides every other one;
- centres Google's iframe on it when the places list has it (`centredEmbed()`, the same string as `Map\Embed::centred()`), or puts the iframe back on its plain `data-embed` when the address names no place; `src` is written only when it differs, since every write reloads Google's map, so a place visited and left reloads it once each way and an address without one leaves an untouched iframe alone;
- on the plan, on show, the first time this place is shown on the plan since Místa was last shown: zooms the canvas to `PLACE_ZOOM` (250 %) and scrolls the box so the marker's centre is in the middle (`centreScroll()`, clamped to the canvas). An image that has not loaded has no height yet, so the marker's top would read 0: the script waits for the image's `load` once and centres then, and the place counts as centred only after a centring with a canvas of some height.

That zoom is not stored: `planZoom:<slug>` stays the reader's own scale, written only by the zoom pair and the pinch. Nor does it outlive the place: once the plan was zoomed for one, an address of Místa that names no place on the plan (no `misto`, or a place off the drawing) and every `screen:hidden` of Místa call `restore()` of `setupPlan()`, which puts the stored `planZoom:<slug>` back (1 when none) and writes nothing, so Back from a pin and a tab tap to the bare Místa show the plan at the reader's own scale, not at 250 %, and a later zoom step starts from that scale. The place is re-centred only when the place or the view changed since Místa was last shown (the key `<id>|plan`, cleared on `screen:hidden` and on an address without a place on the plan), so a reader who zoomed out or panned away is not snapped back by a morph, a re-asserted view or a repeated `popstate`. `sync()` runs at the end of every `setView()` (the wiring, `screen:shown`, a pill, a `popstate` between the two views, a morph's re-assert), and `listen()` adds `screen:shown` for its section, `popstate` while the section is visible, `screen:hidden` (which clears the key and restores the reader's scale) and `screen:morphed` for its root, which re-asserts the markers' `hidden` and zooms nothing. A tab tap back to Místa asks for the address the screen was left on without its query (`lastAddress` carries none), so it shows no marker and the plain iframe. The Mapa and Plán pills keep the query (above), so a place stays named across both views.

**Offline.** A place's address opened as a page is answered from Místa's stored page (the worker's screen key drops the query, [service-worker.md](service-worker.md)), drawn with every marker hidden, and `place.js` shows the place. A pin tapped offline before Místa is in the stack is a full reload instead: the worker keys a fragment by its exact address, query included, with no fallback to the query-less copy, so the loader's fetch fails and it reloads the pushed entry, which the stored page then answers. The warm-up normally stacks Místa long before, so this was accepted rather than given a fragment fallback.

## Offline

Google's iframe is a blank box without a network, so `map.twig` puts a `<p class="empty map-offline" data-map-offline hidden>Mapa potřebuje připojení.</p>` right after the `[data-map]` box. On a two-view Místa the note is `.empty.map-offline.map-offline-plan`: its sentence is wrapped in `<span class="map-offline-text">` and followed by a `Zobrazit plán` button (`data-map-view="plan"`, which `map/views.js` handles). That note stays opaque and only the sentence takes `.empty`'s 0.8 fade, because the tonal `.btn` under it falls below AA at that opacity on a light set. `map/offline.js` only toggles the note's `hidden` and never rewrites it. It finds the map as the note's `previousElementSibling`, so nothing may come between them. On `DOMContentLoaded`, `screen:shown`, `screen:morphed`, `online` and `offline` it hides a map that never loaded behind the note while `navigator.onLine` is false, and reloads its iframe once the signal is back. A map that did load stays as it is, with no note: one capture-phase `load` listener marks it `data-map-loaded` while online. `map/index.js` imports `offline.js` first, so the note's listeners run before the views'.
