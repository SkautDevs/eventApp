# Telemetry

This document covers Sentry, its spans, tags and scrubbing, the two loggers and the health check.

## Sentry

Observability is Sentry, wired like kissj's. `Telemetry\Telemetry::init()` runs in `boot()` only, right after `.env` — tests build apps through `Kernel::create()`, so no test ever binds a client, and `phpunit.xml` forces `SENTRY_DSN` empty for the few that call `boot()`. It also sets `zend.exception_ignore_args` on, whatever the host's ini says, so a session token or a device code passed as an argument never lands in a trace. With an empty `SENTRY_DSN` every piece below is a no-op. `Telemetry\Collector::collect()` files an exception (`QuietErrorHandler` calls it for everything but a 404/405), `Telemetry\Tracer::span($op, $description, $fn, $data)` wraps a child span (`kissj.list`, `kissj.session`, `kissj.programme-participants`, `kissj.pairing-start`, `kissj.pairing-poll`, `kissj.register`, `kissj.unregister`, `kissj.revoke`, `program.cache`, `push.send`, `push.welcome`, `push.subscribe`, `auth.pairing`) whose failure status comes from the HTTP answer when there is one (`Tracer::statusFor()`: kissj's 401 for a device session that is no longer valid is `unauthenticated`, not `internal_error`, and so is the `Program\SessionExpiredException` made from it) and whose `$data` becomes span data — a `Tracer::FROM_RESULT` closure adds data computed from the result; `Tracer::spanTag()` instead tags the running span, and `Tracer::tag()` the transaction (`event`, and the pairing routes' `pairing_outcome`: `rate_limited`, `started`, `provider_failed`, `approved`, `expired`). The push counters `push.outcome` (on `push.welcome`), `push.target` (on `push.send`) and `push.new` (on `push.subscribe`) are span tags, while the cache outcome `cache.result` (`hit`, `miss`, `stale`, `locked` for an expired entry served while another request refetches it, or `bypass` for the uncached programme-participants call) with `cache.age`, and the send counts `push.recipients`, `push.sent`, `push.removed` and `push.failed` (refused other than 404/410, or thrown), are span data — none of them is an issue.

## Transactions and scrubbing

`TransactionMiddleware` opens one transaction per request and `RouteNameMiddleware` names it by route pattern (`POST /admin/notify/{id:[0-9]+}/hidden`) and tags the event; a request no route matched (a 404 or 405) keeps the fixed name `unmatched` (`TransactionMiddleware::UNMATCHED`), and the instance app names its routes too (`RouteNameMiddleware(null)`, which tags no event). `Telemetry\Scrubber` strips the `token` query parameter, a `token` body field, a whole `/push/subscribe` body, the whole body of every admin form (any path with `/admin/` in it: the send, the hide toggle and the inbox's `handled` and `delete`, which carry the `csrf` token and the `Podpis`), the whole body of a participant's message (a path ending in `/zpravy`, the send being `POST /informace/zpravy`: its text and contact), the `Authorization`/`Cookie` headers and every stack frame's vars before anything leaves (the client sets no `data_collection`, so the SDK's legacy `LegacyRequestBodyCollector` attaches the parsed form body to every error event); exception messages are left alone, so none may carry a secret (`SessionExpiredException` says just `Device session is no longer valid` and chains nothing, `RegistrationRefusedException` names only kissj's refusal code, and any other failed kissj call is rethrown as `Program\KissjTransferException` — a `Program\ProgramUnavailableException` that names the endpoint in words, never the URI, and chains nothing either).

## Logs and the health check

There are two Monolog loggers: `Psr\Log\LoggerInterface` (`eventapp`: stdout from info up, a Sentry issue from warning up through `LogToSentryIssueHandler`) and `Kernel::ERRORS_LOGGER` (`errors`: stdout only, for the error handler, so an exception is not filed twice); the app log lines are `push.sent` (info) and, from `WebPushSender`, one `push.failed` warning per batch with failures — counts only, filed in Sentry as an issue; a throwable the sender swallows goes to `Collector::collect()`. `GET /health` on the instance app opens the push database, runs `SELECT 1` and answers `200 {"ok":true}` or `503 {"ok":false}` — no migration, no log, no Sentry. The SDK's default integrations stay on, as in kissj (`Telemetry::options()`), so PHP warnings and deprecations reach Sentry as events too. The one routine message, web-push's "GMP or BCMath" advice, is no longer a PHP notice: `WebPushSender::webPush()` hands the library (`minishlink/web-push` ^11, which requires `ext-mbstring`) the app logger wrapped in `Push\PlatformAdviceFilter`, which drops that one line and passes every real platform warning through.
